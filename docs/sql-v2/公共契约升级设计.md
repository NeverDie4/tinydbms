## 1. 升级范围与拆分原则

升级分成两条独立交付线，不能把它们一次性塞进同一轮公共接口变更：

1. **诊断与脚本恢复线**：增加范围诊断、建议、修复提示、逐语句状态和首错后静态分析。它主要影响新增的 `diagnostic.hpp`、`compiler.hpp`、`core.hpp` 和 CLI，不要求改变 Storage 的记录格式。
2. **SQL v2 能力线**：增加 BIGINT、DOUBLE、BOOLEAN、NULL、UPDATE、ORDER BY、INNER JOIN 和 GROUP BY。它会改变 Value、Catalog、Plan、Storage 请求以及磁盘格式，必须按垂直功能逐项协同。

第一条线可先落地。第二条线不得以“Compiler 已支持语法”为理由直接扩充 Core：每个功能必须同时具备公共契约、Core 执行语义、Storage 能力或明确的内存执行边界、CLI 展示和真实模块测试。

本轮设计不包含：

- Compiler 内部实现方案；
- Storage 页格式、日志、事务或迁移代码；
- 一次性承诺所有 SQL v2 语法；
- 多进程或多 `Database` 实例并行打开；
- 以错误消息文本作为模块间机器可读协议。

## 2. 公共诊断基础类型

### 2.1 位置与范围

新增 `include/tinydbms/diagnostic.hpp`，由 `compiler.hpp` 和 `core.hpp` 显式包含。该头文件包含现有 `common.hpp` 以复用 SourceLocation，而 `SourceLocation` 本身扩展为带 `byte_offset` 的三元端点，`diagnostic.hpp` 定义：

```cpp
struct SourceLocation {
    int line;                 // 从 1 开始
    int column;               // 从 1 开始，按 UTF-8 字节计数
    std::size_t byte_offset;  // 0-based UTF-8 字节偏移
};

struct SourceRange {
    SourceLocation begin;  // 闭区间起点
    SourceLocation end;    // 开区间终点
};

struct FixIt {
    SourceRange range;
    std::string replacement;
};

enum class CompileStage {
    kLex,
    kSyntax,
    kSemantic
};
```

上述坐标规则已作为 A3 决策关闭：半开区间、行列 1-based、offset 0-based，列与偏移都按 UTF-8 字节计算；不再保留其他备选坐标。

约束固定如下：

- 范围统一为 `[begin, end)`，空插入点允许 `begin == end`；
- `line`、`column` 从 1 开始；`byte_offset` 从 0 开始；begin/end 的 line、column 都必须为正数；
- 列号和偏移均按 UTF-8 字节计算，与现有位置契约保持一致，不声称是 Unicode 字符或终端显示宽度；
- 换行规则继承现行消息契约：行按 `\n` 分割；`\r\n` 计一个换行且其中的 `\r` 不占列；单独出现的 `\r`（后面没有 `\n`）视为普通字节并占一列；Tab 按一字节一列计；
- `begin.byte_offset`、`end.byte_offset` 的取值域为 `0..text.size()`（含 `size()`，仅用于 EOF 插入点）；非空区间必须满足 `begin.byte_offset < end.byte_offset`；
- 端点必须落在合法字节边界，且不得落在 `\r\n` 的两个字节之间；跨行范围的端点取下一行行首，跨行区间允许包含换行；
- 同一 SourceRange 的行列与字节偏移必须指向同一段文本；Core 在跨模块边界校验不一致结果并转换为内部错误，不能选择其中一套坐标继续展示；
- `FixIt::range` 使用与主诊断相同的坐标系，Core 做绝对位置换算时必须同时换算两者；
- SourceRange 是结构化定位；消息中不得再编码位置供调用方解析。

`SourceLocation` 留在 `common.hpp`（`byte_offset` 归属于端点），供 `TableMeta` 之外只需要单点位置的代码使用；保留与扩展在同一提交完成。诊断类型独立成文件，避免 Storage 因包含 `common.hpp` 被迫依赖 CompileStage/FixIt。

正式入口继续统一使用 `.hpp`。现有 `src/include/tinydbms/*.h` 只作为旧接口转发层，不得承载新定义；首轮不新增 `diagnostic.h`，除非团队确认仍有只能包含旧 `.h` 路径的外部消费者。

### 2.2 Compiler 错误输出

已确认无外部消费者：直接删除 `CompileErrorKind`，统一改用共享的 `CompileStage`（不保留别名或双接口），并把 `CompileError` 扩展为：

```cpp
struct CompileError {
    CompileStage stage;
    SourceRange source;                 // 相对单条 statement.sql
    std::string message;
    std::optional<std::string> suggestion;
    std::optional<FixIt> fix_it;
};
```

语义如下：

- `message` 是事实性错误说明；
- `suggestion` 是面向用户的可选建议，不保证能自动应用；
- `fix_it` 是机器可用的单处替换建议，必须能在原 SQL 上按范围执行；
- Compiler 可以只返回 message，不要求每个错误都猜测建议；低置信度候选不应填入 suggestion/fix-it；
- 每条语句本阶段最多返回一个 CompileError 和一个可选 fix-it（A8 已关闭）。多错误能力来自“脚本内多条语句分别分析”，不是同一 AST 内强行恢复多个错误；
- Compiler 公共函数不得抛异常，异常应在模块内部转换为约定的结果。Core 仍保留异常兜底，但兜底不属于正常控制流。

### 2.3 分句结果

把 `SplitStatement::start` 扩展为完整的绝对范围：

```cpp
struct SplitStatement {
    std::string sql;
    SourceRange source;  // 在整段脚本中的绝对范围
};
```

`compile()` 返回的 `CompileError::source` 和 `fix_it.range` 都相对 `statement.sql`，Core 根据 `SplitStatement::source.begin` 换算到脚本坐标；`split_statements()` 自身返回的 `CompileError::source` 则相对整段输入，Core 不再二次平移。两类来源的坐标系必须在 Core 实现中显式区分，禁止对同一个范围重复平移。

`sql/source` 的边界固定保持现行行为：`sql` 保留从语句首字符到结尾分号的原文（含前导空白与注释），`source` 与 `sql` 一一对应，包含结尾分号。

分句失败只由两类原因触发：

1. 整段输入超过 `kMaxSqlBytes`；
2. Compiler 返回违反分句契约的结果，例如非法 `SourceRange`、`sql` 与 range 不一致，或范围端点落在非法字节边界。

**未闭合字符串或块注释不是分句失败。** 按现行契约，它们作为残缺语句返回给 `compile()` 报词法错误；这样既保留词法阶段诊断，也避免把数据文本当 SQL 做启发式切割。分句结果类型仍是二选一 variant，不新增“语句列表 + 分句错误”的部分成功结果。

一旦触发分句失败，统一采用保守语义（A4 已关闭）：`statements` 为空，整个脚本只返回一个 `script_error`，Core 不逐句处理、不执行任何语句、不做启发式恢复。

脚本级分句失败没有可信的局部位置，SourceRange 统一使用空插入点 `{1,1,0}-{1,1,0}`：

- 超过 `kMaxSqlBytes` 时返回 `kCompile`、`CompileStage::kLex`，消息说明长度超限；
- Compiler 违反分句契约时由 Core 转换为 `kInternal` script_error，使用同一空插入点并附上契约违反说明。

## 3. Core 公共结果契约

### 3.1 错误结构

在 `ErrorKind` 中增加 `kAnalysis`，并扩展 `include/tinydbms/core.hpp` 中的 `Error`：

```cpp
struct Error {
    ErrorKind kind;
    std::optional<CompileStage> compile_stage;  // 仅 kCompile
    std::optional<SourceRange> source;          // 脚本绝对范围
    std::string message;
    std::optional<std::string> suggestion;
    std::optional<FixIt> fix_it;
};
```

Core 必须保留 Compiler 给出的 stage、range、suggestion 和 fix-it，不再把词法/语法/语义细分类别压扁成不可恢复的字符串。StorageErrorKind 是否也进入 Core Error 不在本轮扩展范围内；CLI 仍不得解析 Storage 消息。

字段不变量：

| `kind` | `compile_stage` | `source` | `suggestion/fix_it` |
|---|---|---|---|
| `kCompile` | 必有 | 必有 | 可选 |
| `kExecute` | 空 | 通常为空；后续可扩展运行时表达式范围 | 空 |
| `kAnalysis` | 空 | 必有 | 空 |
| `kStorage` | 空 | 空 | 空 |
| `kInternal` | 空 | 致命中止时指向发生中止的位置；无法定位时为 `{1,1,0}-{1,1,0}` | 空 |

所有 `source` 均为脚本绝对范围。分句失败、语句数超限等没有可信局部位置的脚本级错误统一使用空插入点 `{1,1,0}-{1,1,0}`；`Error` 的字段组合由 Core 构造时校验，违反按 `kInternal` 处理。

### 3.2 脚本策略与逐语句状态

新增：

```cpp
enum class ScriptErrorPolicy {
    kStopOnFirstError,
    kAnalyzeRemaining
};

enum class StatementStatus {
    kExecuted,
    kCompileError,
    kExecutionError,
    kExecutionIndeterminate,
    kAnalysisError,
    kAnalysisOnly,
    kSkippedExecution
};

inline constexpr std::size_t kMaxStatementsPerScript = 4096;

class StatementResult {
public:
    static StatementResult executed(std::size_t statement_index, SourceRange source, ExecuteResult outcome);
    static StatementResult compile_error(std::size_t statement_index, SourceRange source, Error error);
    static StatementResult execution_error(std::size_t statement_index, SourceRange source, ExecuteResult outcome);
    static StatementResult execution_indeterminate(std::size_t statement_index, SourceRange source);
    static StatementResult analysis_error(std::size_t statement_index, SourceRange source, Error error);
    static StatementResult analysis_only(std::size_t statement_index, SourceRange source);
    static StatementResult skipped(std::size_t statement_index, SourceRange source);

    std::size_t statement_index() const noexcept;      // 分句后 0-based，连续且与脚本顺序一致
    const SourceRange& source() const noexcept;        // 脚本绝对范围
    StatementStatus status() const noexcept;
    const std::optional<ExecuteResult>& outcome() const noexcept;

private:
    StatementResult(
        std::size_t statement_index,
        SourceRange source,
        StatementStatus status,
        std::optional<ExecuteResult> outcome);

    std::size_t statement_index_;
    SourceRange source_;
    StatementStatus status_;
    std::optional<ExecuteResult> outcome_;
};

struct ExecuteScriptRequest {
    std::string text;
    ScriptErrorPolicy error_policy{ScriptErrorPolicy::kStopOnFirstError};
};

struct ExecuteScriptResult {
    std::optional<Error> script_error;
    std::vector<StatementResult> statements;
};
```

`StatementResult` 只能通过命名工厂构造：构造函数私有，数据成员私有且只提供只读访问，禁止默认构造、聚合初始化和直接改写 status/outcome。工厂负责校验状态与 outcome 的组合，并把 `ExecuteResult` 中的 Error kind 约束到下表允许的集合。`kMaxStatementsPerScript = 4096` 是 A7 决策，`ExecuteScriptRequest::error_policy` 默认 `kStopOnFirstError` 是 A1 决策。

为避免重复状态失配，不在结果中存储可由 `statements` 推导的 `first_error_index`、`executed_count` 或独立 diagnostics 数组；需要统计的调用方遍历结果。`script_error` 是否存在同时决定 `kSkippedExecution` 的原因，不需要额外的 skip_reason 字段。

状态不变量：

| 状态 | `outcome` | 允许的 Error kind | 含义 |
|---|---|---|---|
| `kExecuted` | 必有，且无错误 | 无 | 语句真实执行成功 |
| `kCompileError` | 必有，且为 `Error` | `kCompile` | 编译失败，未执行 |
| `kExecutionError` | 必有，为 `Error` 或携带 error 的 `CommandResult` | `kExecute`、`kStorage` | 执行已失败；部分写入数量仍由 CommandResult 表达 |
| `kExecutionIndeterminate` | 空 | 无 | 执行已开始但被致命中止，物理副作用不确定 |
| `kAnalysisError` | 必有，且为 `Error` | `kAnalysis` | 仅分析阶段影子状态更新失败，未执行 |
| `kAnalysisOnly` | 空 | 无 | 编译成功但执行门已关闭；不得伪装成成功执行 |
| `kSkippedExecution` | 空 | 无 | 已识别但执行阶段未开始；原因由 script_error 是否存在推导 |

- `kInternal` 只允许出现在 `script_error`，不允许出现在语句级 outcome；
- 分句成功后 `statements` 覆盖全部已识别语句：`statement_index` 从 0 连续递增，`kSkippedExecution` 也占位，调用方不会把“未处理”误读成“没有该语句”；
- 分句失败或语句数超过 `kMaxStatementsPerScript` 时不产生语句结果：`statements` 为空且 `script_error` 必有值，Core 不编译、不执行、不调用 Storage；
- 执行器返回 `Error{kInternal}`（Plan 不变量失败、Storage 异常后的契约违反等）时不得构造 `kExecutionError`。Core 内部执行入口必须提供“是否可能已产生副作用或已进入 cleanup-pending”的标志：未产生副作用时当前语句起全部 `kSkippedExecution`；可能已产生副作用时当前语句 `kExecutionIndeterminate`、其余 skipped。两种情况都填充 `script_error{kInternal}` 后结束本次脚本。

`script_error` 只承载三类错误：分句阶段失败（`kCompile`）、语句数超限（`kCompile`、`CompileStage::kLex`）与致命中止（`kInternal`，包括 Compiler/Storage 违反契约抛异常、Core 内部不变量失败、影子 Catalog 建立或同步失败、结果聚合失败）。普通单条语句错误必须落入对应 StatementResult。

`kStopOnFirstError` 下，首错后剩余语句全部记 `kSkippedExecution`；没有发生致命中止时 `script_error` 为空。`kAnalyzeRemaining` 下，结构化错误后的边界可信语句继续编译：影子状态无需变化（`kNoCatalogChange`）或成功应用（`kApplied`）时记 `kAnalysisOnly`，编译失败者记 `kCompileError`，影子状态明确拒绝（`kRejected`）者记 `kAnalysisError`。两条策略下，首错后的语句都不得执行。

### 3.3 迁移方式（已确认）

`ExecuteScriptResult::outcomes` 到 `statements`、`CompileErrorKind` 到 `CompileStage` 都是破坏性源代码变更。2026-09-12 已确认项目没有对外消费者，采用一次性迁移：

- 不保留旧枚举别名、旧字段或 `execute_script_v2` 双接口；
- Core、app、fake、真实联调测试和现行契约文档在同一集成窗口内更新；
- 公共头、实现与测试在同一提交批次内保持一致，避免中间态被其他成员拉取使用；
- 同一集成窗口内先完成全部迁移并本地验证，再推送分支；不允许在公共头已破坏编译的中间提交上停留或推送。

## 4. SQL v2 后续公共类型提案

本节不是诊断与脚本恢复线的首轮修改清单。它用于提前锁定边界，避免 Compiler 单方面产出 Core/Storage 无法消费的 Plan。

### 4.1 先决条件：类型升级四层同时闭合

`Type`/`Value` 的权威声明在 `common.hpp`，但一次类型升级必须同时闭合四层，缺一层都不得进入端到端实现：

1. 逻辑类型与转换规则（Compiler 语义、Core 求值）；
2. 公共 `Type`/`Value` 形状与 NULL 表达；
3. Storage 物理编码、行宽、页布局与系统 Catalog 的类型标签；
4. 旧库兼容策略（拒绝、只读、离线迁移或读旧写新）。

现行 Storage 契约只支持 INT/VARCHAR（`storage-contract.md`），历史 V1 metadata 明确不迁移。在 Storage 联合评审关闭第 3、4 层前，不允许修改公共 Type/Value，也不得把 Compiler 的前端解析能力宣传为端到端完成。2026-09-12 已确认（B11）：迁移策略先由 Storage 组给出成本评估，评估完成前不得落地 NullValue 或新 Type 的持久化格式。

### 4.2 Type、Value 与 NULL

建议目标类型：

```cpp
enum class Type {
    kInt,
    kBigInt,
    kDouble,
    kBoolean,
    kVarchar
};

struct NullValue {};

struct Value {
    std::variant<NullValue, std::int32_t, std::int64_t, double, bool, std::string> data;
};

struct ColumnMeta {
    std::string name;
    Type type;
    bool nullable;
};
```

已确认约束（2026-09-12，B9/B10 已关闭）：

- `nullable` 默认语义为 false，以保持 V1 既有表行为；是否在 C++ 字段上提供默认初始化仍由 ABI/API 迁移方案决定；
- DOUBLE 只接受有限值，NaN 和正负无穷在公共契约层非法；
- 不做隐式跨类型转换；算术和比较规则按每个垂直功能单独定义；
- NULL 不等于任何值，`IS NULL`/`IS NOT NULL` 与三值逻辑必须在相应阶段另行冻结；
- Value 的扩展会同时影响 Core 表达式求值、CLI 输出、Storage 编码和磁盘版本，不能只改 `common.hpp`。

### 4.3 多表列引用与绑定

为支持 JOIN、自连接和表别名，ColumnRef 必须携带查询作用域内的绑定，而不是直接指向 TableId：

```cpp
using BindingId = std::uint32_t;  // 查询局部，0..n-1，由 compiler 分配

struct ColumnRef {
    BindingId binding_id;
    ColumnId column_id;
};

struct ScanNode {
    BindingId binding_id;  // 与 ColumnRef 对应
    TableId table_id;      // 实际被扫描的表
};
```

- `BindingId` 只在一次查询编译内有效，与磁盘和 Catalog 中的 ID 无关；
- 自连接与别名通过不同 `BindingId` 区分同一个 `TableId` 的多次出现；
- `ScanNode`（以及未来的 `JoinNode`）是 BindingId 到 TableId、别名的唯一映射来源，Core 用它解析列值；
- 单表查询固定使用 `BindingId 0`，规则与 JOIN 统一，不保留“唯一查询表”的隐含推导；
- Project、GROUP BY、ORDER BY 与结果列头沿用同一绑定坐标系；列头名称由 compiler 给出，Core 不反查 Catalog。

该变更属于 SQL v2 冻结线，在 JOIN 进入实现前随新的 Plan 契约一并落地。

### 4.4 UPDATE 与 Storage 边界

Compiler 输出 UPDATE 的目标表、赋值表达式和谓词；Core 负责扫描、求值、类型/NULL 校验并生成完整新行。Storage 不解释 SQL 表达式，只按 RecordId 写回完整记录：

```cpp
struct RecordUpdate {
    RecordId rid;
    std::vector<Value> values;  // 更新后的完整行，按建表列序
};

struct UpdateRequest {
    TableId table_id;
    std::vector<RecordUpdate> records;
};

struct UpdateResult {
    std::uint64_t updated_count;
    std::optional<StorageError> error;
};
```

部分失败语义沿用 INSERT/DELETE：按请求顺序执行，`updated_count` 是错误前已成功写入数量，Core 立即关闭执行门。原地写、搬迁、页管理和日志属于 Storage 内部实现。

### 4.5 ORDER BY、JOIN、GROUP BY

第一版可由 Core 在内存中执行，不要求立即新增 Storage API：

- ORDER BY：扫描后稳定排序，必须规定 NULL 次序、ASC/DESC 和内存上限；
- INNER JOIN：Core 驱动两个或多个扫描，不把连接条件下推为 Storage 表达式；
- GROUP BY/聚合：Core 定义聚合状态和结果类型，Storage 只提供记录；
- 任一功能若可能突破内存上限，应返回明确错误，不能无界增长或静默退化。

这些功能各自需要独立 Plan 契约和验收文档，不在本提案中提前固定具体节点形状。

垂直功能的实施顺序已确认（2026-09-12，B12）：诊断/恢复 → ORDER BY → 类型逐项 → NULL → UPDATE → INNER JOIN → GROUP BY/聚合。诊断/恢复线不等待后续功能，其余每项在进入实现前仍需各自的联合设计与验收标准。

## 5. System Catalog V2 基线

升级后的 Core 必须按 System Catalog V2 的事实工作：

- `TableId` 0 和 1 保留给系统表；用户表 ID 从 2 开始；
- open 后 Catalog 来自 Storage `list_tables` 的权威结果，不根据文件名推测；`list_tables` 返回 system table 与用户表，Core 的运行时 Catalog 和 Compiler 的 `CatalogView` 都包含这两张系统表，普通 SELECT 可读；
- 空库含 system TableId 0/1 时，`next_table_id = max(table_id) + 1 = 2`；运行时与影子 Catalog 都禁止分配 0/1 或已存在的 ID；
- public `insert`/`delete_records` 对系统表由 Storage 返回 `kInvalidRequest`；CREATE 使用保留名称时由 Catalog 重复检查和 Storage 共同拒绝；候选 ID 从 2 起，0/1 不会进入分配，Core 不另立一套名称规则；
- 分析影子 Catalog 从最后一次确认成功的运行时 Catalog 复制，不重新扫描物理文件；
- 分析态分配的候选 TableId 只存在于当前脚本，绝不写入 Storage 或运行时 Catalog；
- 系统表的可见性和不可变更规则由正式 Storage V2 契约提供，Core 不自行硬编码另一套名称规则。

截至 2026-09-12，本地 `main` 已快进到包含 System Catalog V2 的 `7fc5df7`，公共头未变；本节约束已按合并后的 Storage 契约复核，进入代码阶段前再以真实头文件和存储行为为准做一次最终核对。

## 7. 契约验收标准

诊断与脚本恢复线在进入实现前必须能由文档唯一回答：

- 每种错误处于脚本、语句还是执行结果哪一层，`kInternal` 是否只出现在 `script_error`；
- 所有位置和 fix-it 使用哪一种坐标系，CRLF、Tab 和 EOF 插入点的规则是否唯一；
- 首错后哪些调用仍允许发生，哪些状态绝不允许改变；
- 分句失败只由哪些原因触发，未闭合字符串/注释归属哪一层，脚本级错误的空插入点是否唯一；
- 语句数超过 `kMaxStatementsPerScript = 4096` 时是否在执行前 fail-closed，`statements` 是否为空；
- CLI 如何区分真实执行、编译失败、执行失败、执行不确定、分析失败、仅分析和跳过；
- 分句成功后每个已识别语句是否都能按连续 index 在结果中定位；
- 破坏性迁移是否一次性覆盖 Core、app、fake、真实测试与文档（含 CompileErrorKind 删除）；
- fake 测试如何证明首错后没有 Storage 调用；
- 执行器返回 `kInternal` 时如何区分 `kExecutionIndeterminate` 与 `kSkippedExecution`，且不构造语句级 `kInternal`；
- System Catalog V2 下分析态 TableId 如何分配、64 位计数如何避免回绕且不污染运行态。

SQL v2 能力线在每个垂直功能进入实现前，还必须单独回答 Value 规则、NULL 语义、Plan 形状、Core 执行算法、Storage 物理能力、资源上限、错误路径和持久化兼容。缺少其中任何一项时，不应只凭 Compiler 语法完成度宣称该功能可以联调。
