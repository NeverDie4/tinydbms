# 联调准备与验收清单

本文用于 compiler、core、storage 和 app 进入真实模块联调前的协作与验收，不替代
[消息契约详细设计](消息契约详细设计.md)、[模块交互契约](模块交互契约.md)和各阶段实现规格。
其中“已通过”必须有当前工作区的构建、测试或运行结果支持；未满足的项目保持为阻断项。

## 1. 当前状态

- compiler 已有可链接实现和独立 CTest，能够单独构建与测试；第 3.1 节的契约硬化项尚未全部关闭。
- core/app 已通过 fake compiler、fake storage 的行为测试；这种测试组合不等价于真实模块端到端联调。
- 当前可先进行真实 compiler + fake storage 的 core/CLI 窄联调；该阶段验证已覆盖语句的 compiler、core 和
  app 连接，不验证 storage 的持久化实现，也不宣称 compiler 硬化项已经验收。
- storage 当前仍为占位实现，`TINYDBMS_ENABLE_REAL_MODULES=ON` 的完整产品链路尚未具备可链接的真实
  storage API。
- 合并后的公共 `include/tinydbms/`、`src/core/` 和 `src/app/` 没有新增差异；本阶段不预期修改公共头文件。

## 2. 当前阶段：真实 compiler + fake storage

这是 storage 交付前允许执行的窄联调层，测试目标必须满足；它不替代第 3.1 节的 compiler 契约硬化测试：

- 使用真实 `tinydbms_compiler`、真实 `tinydbms_core_objects`、真实 `CoreSession` 和真实 CLI runner；
- 只使用 `tests/fakes/storage_fake.cpp` 提供 storage 边界，不链接 `tinydbms_storage`；
- 不链接 `tests/fakes/compiler_fake.cpp`，避免真实 compiler 与 fake compiler 混用；
- 至少验证 `CREATE TABLE → INSERT → SELECT → WHERE`、编译错误位置、Catalog 逐条更新和 CLI 退出码。

对应测试目标是 `tinydbms_compiler_core_cli_integration_test`。该测试通过后，只能说明
compiler/core/CLI 连接成立，不能说明真实 storage 或持久化链路成立。

## 3. 完整联调前阻断项

### 3.1 compiler

compiler 成员需要在联调前完成并补充回归测试：

1. 支持负整数文字，正确覆盖 `INT32_MIN` 和 `INT32_MAX`。
2. 将整数范围溢出归类为 `CompileErrorKind::kSemantic`。
3. 在 parser 或后续流水线入口限制表达式深度，不生成超过 `256` 层的 Plan；深树不能依靠 core
   运行时兜底才被发现。
4. 对标识符、字符串和 SQL/单条语句输入设置有界的内存使用策略。整段 SQL 与单条语句的最大长度、
   超限错误类型和责任模块需要在实现前记录为明确决策。
5. 保持 `CompileError.location` 为单条语句相对坐标，且不得让异常越过 compiler 公共 API。

### 3.2 storage

storage 成员需要提供真实实现并满足：

1. `open_storage`、`close_storage`、`list_tables`、`create_table`、`open_table`、`scan_next`、
   `close_cursor`、`insert` 和 `delete_records` 的公共签名与错误语义。
2. 非法生命周期调用、空删除请求、游标结束和重复关闭行为与契约一致。
3. 正常 close 后数据可重启读取；表元数据、TableId 和 RecordId 规则与 core 一致。
4. 公共 API 不让异常越过边界；部分写入/删除失败时返回可靠的部分成功数量。
5. storage 独立测试完成后，才能进行真实 core/app 链路测试。

## 4. 公共文件门禁

- 联调前比较 `include/tinydbms/` 与联调基线的差异。
- 任何公共头文件的字段、函数签名、错误语义或生命周期语义变化，必须先同步
  [消息契约详细设计](消息契约详细设计.md)，并登记到临时的[公共文件修改记录](公共文件修改记录-提交前删除.md)。
- 需要通知依赖该头文件的 compiler、storage、core、app 成员；没有确认兼容性前，不把联调失败归因于实现细节。
- `src/compiler/*.hpp`、`src/core/*.hpp` 等模块内部头文件不属于公共 include，但仍需保持 CMake 目标的私有边界。

## 5. 联调构建顺序

所有 Linux 构建和验证使用 `g++`。建议使用任务专用的构建目录，避免覆盖已有构建产物：

```bash
BUILD_DIR=/tmp/tinydbms-integration-build

cmake -S . -B "$BUILD_DIR" -G Ninja \
  -DCMAKE_CXX_COMPILER=g++ \
  -DCMAKE_BUILD_TYPE=Debug \
  -DTINYDBMS_BUILD_TESTS=ON \
  -DTINYDBMS_ENABLE_REAL_MODULES=OFF
cmake --build "$BUILD_DIR" -j4
ctest --test-dir "$BUILD_DIR" --output-on-failure
```

先确认基线测试仍通过，再切换真实模块：

```bash
REAL_BUILD_DIR=/tmp/tinydbms-integration-build-real

cmake -S . -B "$REAL_BUILD_DIR" -G Ninja \
  -DCMAKE_CXX_COMPILER=g++ \
  -DCMAKE_BUILD_TYPE=Debug \
  -DTINYDBMS_BUILD_TESTS=ON \
  -DTINYDBMS_ENABLE_REAL_MODULES=ON
cmake --build "$REAL_BUILD_DIR" -j4
ctest --test-dir "$REAL_BUILD_DIR" --output-on-failure
```

真实模块配置下，构建失败必须先区分为接口/实现/链接问题；不能用 fake 测试通过代替真实链路验收。

## 6. 联调顺序

1. 各模块分别通过自己的单元测试和契约编译测试。
2. 以空的临时 `data_dir` 启动产品，验证 `open → list_tables → close`。
3. 依次验证 `CREATE TABLE → INSERT → SELECT → WHERE → DELETE → close → reopen → SELECT`。
4. 验证多语句脚本、编译错误位置、执行错误、REPL 继续读取和最终退出码。
5. 验证非法输入不会产生 storage 副作用，包括编译失败、非法 Plan、重复建表、类型错误和越界值。
6. 验证异常与部分成功路径：游标关闭、close_storage、部分 INSERT/DELETE、重启后 Catalog 和数据恢复。
7. 最后运行完整 CTest、`git diff --check` 和公共头文件差异检查。

## 7. 通过标准

真实联调完成必须同时满足：

- `TINYDBMS_ENABLE_REAL_MODULES=ON` 配置、构建和 CTest 全部通过；
- compiler、storage、core、app 的已有测试全部通过，且测试目标没有把 fake 与真实模块混用；
- 上述基本 SQL 生命周期和错误路径在临时数据目录中运行通过；
- close 后重启能够恢复表结构和已提交数据；
- compiler 的负数、整数边界、深表达式和大输入边界测试已覆盖；
- 公共 `include/tinydbms/` 的变更已完成契约同步和成员通知；
- 工作区无调试产物、临时文件和未说明的差异。

在 storage 尚未交付、compiler 阻断项尚未关闭或真实模块构建仍无法链接时，状态只能记为“已准备联调”，
不能记为“真实链路验收通过”。
