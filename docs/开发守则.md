# tinydbms 开发守则

## 1. MiniOB 是架构参考项目

在 `tinydbms` 的后续开发过程中，必须把 MiniOB 作为数据库架构学习、设计和实现的主要参考项目之一。

已复制到本项目的 MiniOB 学习文档位于 [`docs/miniob-study/`](miniob-study/)：

- [architecture.md](miniob-study/architecture.md)：进程入口、SQL 层、执行层、存储层、事务和恢复的总体架构。
- [sql-pipeline.md](miniob-study/sql-pipeline.md)：从 SQL 文本到 Parser、Statement、Logical Plan、Physical Plan、Operator 和存储访问的调用链。
- [storage-engine.md](miniob-study/storage-engine.md)：Table、Record、Page、Buffer Pool、文件、索引和恢复的关系。
- [catalog.md](miniob-study/catalog.md)：Database、Table、Field、TableMeta、IndexMeta 和统计 Catalog 的区别。
- [important-classes.md](miniob-study/important-classes.md)：MiniOB 推荐阅读的类、文件和阅读顺序。

这些文档来自当前 MiniOB 仓库源码分析，而不是对 MiniOB 的抽象猜测。MiniOB 源码版本变化时，应以重新检查后的当前源码为准。

## 2. 开发前必须做架构对照

实现 `tinydbms` 的新模块或新功能前，先回答以下问题：

1. MiniOB 中对应的入口、模块、类和调用链是什么？
2. tinydbms 当前契约中对应的消息、数据结构和生命周期是什么？
3. 哪些设计可以借鉴，哪些部分因为 tinydbms 的简化目标必须省略或改造？
4. 这一功能会影响 Parser、Statement、Plan、Executor、Catalog、Table、Record、Page、Buffer Pool、文件或测试中的哪些边界？
5. 是否需要补充一条从 SQL 到存储的可验证调用链和测试？

开发说明中应尽量写出真实的文件、类和核心函数，而不是只写“增加一个模块”或“调用数据库接口”。

## 3. 参考 MiniOB，但不复制 MiniOB 代码

MiniOB 用于借鉴以下内容：

- 分层方式和模块职责；
- SQL 请求的中间结构转换；
- Logical Operator 与 Physical Operator 的分离；
- Executor、Table、Record、Page、Buffer Pool 的边界；
- Catalog 与持久化元数据的区分；
- 索引、事务、日志、恢复和测试的演进顺序。

不直接复制 MiniOB 的源代码、文件布局或未经确认的实现细节。tinydbms 应优先保持自身契约、C++20 跨平台要求和最小数据库目标的一致性。

## 4. 发生差异时的处理原则

当 MiniOB 的真实结构与 tinydbms 当前设计不一致时：

- 以 tinydbms 当前代码和已确认契约为实现依据；
- 在设计文档中说明与 MiniOB 的差异；
- 说明是为了简化、跨平台、教学目的还是当前阶段尚未实现；
- 不把 MiniOB 中可选路径、历史兼容路径或默认配置之外的路径误当成 tinydbms 必须实现的内容。

例如，MiniOB 的完整版本包含多种事务、存储引擎、网络协议和恢复路径，而 tinydbms 当前是单进程、单线程、无网络、无事务的最小骨架。这些能力应按 tinydbms 的阶段计划逐步引入，而不是一次性照搬。

## 5. 功能实现顺序

优先沿着一条完整的垂直链路开发和验证：

```text
入口
→ SQL 文本
→ Parser
→ Statement / AST
→ Logical Plan
→ Physical Plan
→ Executor / Operator
→ Table
→ Record
→ Page
→ Buffer Pool
→ Disk / File
```

每完成一个阶段，都应能够说明：输入是什么、输出是什么、对象由谁拥有、错误如何返回、下一层由谁调用，并用测试验证边界。

## 6. 文档和验证要求

- 重要架构决策必须写入 `docs/`；
- 跨模块消息变化必须同步检查契约文档和公共头文件；
- 新增存储路径时必须说明磁盘格式、Page 生命周期和恢复行为；
- 新增 SQL 时必须补充 Parser、语义检查、计划、执行和存储访问链路；
- 完成功能前必须运行构建和测试，并记录无法运行的验证项；
- 不以“代码已经写好”代替“调用链和测试已经验证”。

这份守则适用于后续 tinydbms 的设计、编码、调试、代码审查和文档维护。
