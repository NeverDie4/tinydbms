# tinydbms 技术决策

本文记录当前已实现代码的冻结决策。公共头文件和测试是最终可执行依据；本文不定义第二套接口。

## 工程基线

- 使用 C++20 的保守子集，不使用 ranges、coroutines 或 modules。
- 本仓库的编译与验证统一使用 g++。
- 使用 CMake 描述工程，Ninja 执行构建，CTest 运行测试。
- 初版使用自写断言，不引入第三方测试框架。
- 单进程、单线程、顺序执行；一个可执行入口，三层静态库 `tinydbms_compiler`、`tinydbms_storage`、`tinydbms_core`。

## 公共契约

唯一正式入口是：

```text
include/tinydbms/common.hpp
include/tinydbms/compiler.hpp
include/tinydbms/core.hpp
include/tinydbms/storage.hpp
```

`src/include/tinydbms/*.h` 只转发到对应 `.hpp`，不再定义 `Type`、`Value`、Storage、Compiler 或 Core API。

## 类型与物理格式

public type 只有：

| SQL 类型 | C++ Value | 物理编码 |
|---|---|---|
| `INT` | `std::int32_t` | 4-byte little-endian signed int32 |
| `VARCHAR` | `std::string` | uint32 little-endian byte length，随后为 UTF-8 字节 |

VARCHAR 必须是合法 UTF-8，长度不超过 1024 字节；单行逻辑载荷不超过 4096 字节。Storage metadata 写入 `INT32`，读取时接受 `INT` 和 `INT32`。历史 `INT64`、`FLOAT`、`DOUBLE`、`BOOL` metadata 不是支持类型，必须显式失败。

## Storage 与 Catalog

`storage.meta` 是 V2 bootstrap：它只标识已初始化的格式，不能保存或恢复用户 schema。
持久化 schema 的权威是两个 Storage 管理的特殊 HeapTable：TableId 0 的
`tdb_sys_tables` 保存每张用户表的 ID、名称与列数，TableId 1 的 `tdb_sys_columns` 保存列定义。
正常 open 先验证 bootstrap 与这两个 PageFile，再扫描 catalog 表重建 `StorageState.tables`；Core
随后通过 `storage::list_tables` 重建运行时 Catalog。Core Catalog 仍是逻辑副本，不是第二份持久化 catalog。

TableId 0 与 1 为保留 system table ID，普通用户表必须从 2 开始。特殊表可作为只读表被
`SELECT`，但普通 `CREATE`、`INSERT` 和 `DELETE` 均不得修改；Storage 内部写入 catalog 时，先写
`tdb_sys_columns`，最后写 `tdb_sys_tables` 的 table row 作为 commit marker，marker 写入必须 flush 成功后才发布内存表元数据。

Core 从已恢复表的最大 ID 加一分配；使用更宽值计算，达到 `UINT32_MAX` 后停止分配，不回绕。

Storage 是同进程 singleton。正常数据操作只在 Storage 处于 open 时可用；同表存在未关闭 cursor 时阻止非空 INSERT/DELETE。Core 必须在 EOF 和所有失败路径关闭 cursor，DELETE 固定采用扫描、收集 RID、关闭 cursor、批量删除的顺序。

## Database ownership 与生命周期

可以存在多个 `core::Database` 对象，但同一进程最多一个对象处于 open 或 cleanup-pending 状态。第二个 `Database::open` 返回 Core `kExecute`，且不调用 Storage。

成功 close 才释放 ownership。`close_storage` 返回错误时，Storage 保持 Closing，Database 保持 cleanup-pending，只允许原 owner 重试 `close()`；清理成功前不允许其他 Database open。重试返回 `kInvalidRequest` 表示 Storage 已经结束生命周期，可以按清理完成处理。

Storage 抛异常或 Core 遇到无法确认副作用的模块异常时，Core 先 best-effort 调用 `close_storage`，清空 Catalog 并使当前会话失效。若清理调用返回错误或抛异常，实例保留 cleanup-pending 与重试状态。该路径不能回滚已经发生的 CREATE/INSERT/DELETE 部分副作用，后续 open 必须从 Storage System Catalog 恢复 Catalog。

Database 可移动、不可复制。移动赋值若遇到未完成的关闭清理，必须保留当前 Impl 和重试入口，不能因为转移所有权而丢失 Storage owner。

## 执行边界

Compiler 负责 SQL 到 typed Plan；Core 不重新解析 SQL，并执行 `CreateTablePlan`、`InsertPlan`、`QueryPlan`、`DeletePlan`。Core 只依赖 Storage 的 public requests/results，不能访问 HeapTable、BufferPool、RecordPage 或 PageFile 私有实现。

`split_statements` 成功时返回 SplitStatement 列表，整段 SQL 超过 `kMaxSqlBytes` 时返回
`SplitStatementsResult` 中的 CompileError，不抛 `std::length_error`。Core 对分句错误直接返回
`ErrorKind::kCompile`，此时尚未执行 Plan，不得关闭 Storage 或使 Database 会话失效。

SELECT 在完整 Storage Record 上计算 predicate，再进行投影。DELETE 在 cursor 成功关闭后才调用批量删除。INSERT 和 DELETE 的部分成功分别以 `InsertResult.rids.size()` 与 `DeleteResult.deleted_count` 作为已影响行数，不回滚。

## CLI 边界

入口只负责参数解析、输入读取、结果展示和退出码，不拆句、不解析 SQL、不包含数据库业务逻辑。初版 REPL 按行提交，支持一行内多条完整语句；跨行 SQL 属于后续升级项。

默认构建使用不可用 Session 适配器，以便独立验证 CLI 和 core fake 行为。真实 compiler、core、storage 联调通过 `TINYDBMS_ENABLE_REAL_MODULES=ON` 启用。

## 暂不纳入范围

本阶段不实现 FSM、Index、WAL、Transaction、MVCC、NULL、隐式类型转换、函数、LIKE、算术、跨进程文件锁、V1 自动迁移、DROP 或新的 SQL 语法。正常 close 后的重启可见不等同于崩溃恢复或逐操作 fsync 承诺。
