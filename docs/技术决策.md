# tinydbms 技术决策

本文记录当前已实现代码的冻结决策。公共头文件和测试是最终可执行依据；本文不定义第二套接口。

## 公共契约

唯一正式入口是 `include/tinydbms/common.hpp`、`compiler.hpp`、`core.hpp` 和 `storage.hpp`。旧的 `src/include/tinydbms/*.h` 只转发到对应 `.hpp`，不再定义 `Type`、`Value`、Storage、Compiler 或 Core API。

## 类型与物理格式

public type 只有：

| SQL 类型 | C++ Value | 物理编码 |
|---|---|---|
| `INT` | `std::int32_t` | 4-byte little-endian signed int32 |
| `VARCHAR` | `std::string` | uint32 little-endian byte length，随后为 UTF-8 字节 |

VARCHAR 必须是合法 UTF-8，长度不超过 1024 字节；单行逻辑载荷不超过 4096 字节。Storage metadata 写入 `INT32`，读取时接受 `INT` 和 `INT32` 作为 canonical `kInt`。历史 `INT64`、`FLOAT`、`DOUBLE`、`BOOL` metadata 是不受支持的 canonical schema，必须显式失败，不能静默映射。

## Storage 与 catalog

Storage 的 `storage.meta` 是 schema 的持久化权威。Core 在 `Database::open` 后通过 `storage::list_tables` 恢复内存 catalog；它只是逻辑副本，不是第二份持久化 catalog。System Catalog 特殊表尚未实现。

`TableId` 的 0..UINT32_MAX 都合法，0 没有保留含义。Core 从当前最大 ID 加一分配；使用更宽值计算，达到 UINT32_MAX 后停止分配，不回绕。

## Database ownership 与生命周期

可以存在多个 `core::Database` 对象，但 Storage 仍是无句柄 singleton。同一进程最多一个对象处于 open 或 cleanup-pending 状态。第二个 `open` 返回 Core `kExecute`，且不调用 Storage。

成功 close 才释放 ownership。Storage close 失败时 owner 进入 cleanup-pending，只允许重试 `close`；成功 retry 后才允许其他 Database open。reopen 总是从 Storage metadata 重建 catalog。

## 执行边界

Compiler 负责 SQL 到 typed Plan；Core 不重新解析 SQL，并执行 `CreateTablePlan`、`InsertPlan`、`QueryPlan`、`DeletePlan`。Core 只依赖 Storage 的 public requests/results，不能访问 HeapTable、BufferPool、RecordPage 或 PageFile 私有实现。

SELECT 在完整 Storage Record 上计算 predicate，再进行投影。DELETE 固定为：

```text
scan entire table
→ evaluate predicate
→ collect RID
→ close cursor successfully
→ delete batch
```

不得边扫描同一张表边删除；扫描、表达式或 close 失败时不发起 delete。INSERT 和 DELETE 的部分成功分别以 `InsertResult.rids.size()` 与 `DeleteResult.deleted_count` 作为已影响行数，不回滚。

## 暂不纳入范围

本阶段不实现 System Catalog、FSM、Index、WAL、Transaction、MVCC、NULL、隐式类型转换、函数、LIKE、算术或新的 SQL 语法。
