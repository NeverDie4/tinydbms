# tinydbms 技术决策

本文记录当前已实现代码的冻结决策。公共头文件和测试是最终可执行依据；本文不定义第二套接口。

## 工程基线

- 使用 C++20 的保守子集，不使用 ranges、coroutines 或 modules。
- 本仓库的编译与验证统一使用 g++。
- 使用 CMake 描述工程，Ninja 执行构建，CTest 运行测试。
- 初版使用自写断言，不引入第三方测试框架。
- 单进程；同一个 `Database` 实例的公开方法可被多个执行流并发调用，由 core 按调用级互斥串行执行（不承诺并行度与读并行）；storage 的公共 API 仍要求调用方串行调用。BufferPool 预取实验启用时会创建一个内部 worker 线程，默认关闭；一个可执行入口，三层静态库 `tinydbms_compiler`、`tinydbms_storage`、`tinydbms_core`。

## 公共契约

唯一正式入口是：

```text
include/tinydbms/common.hpp
include/tinydbms/compiler.hpp
include/tinydbms/core.hpp
include/tinydbms/storage.hpp
include/tinydbms/diagnostic.hpp
```

`src/include/tinydbms/*.h` 只转发到对应 `.hpp`，不再定义 `Type`、`Value`、Storage、Compiler 或 Core API。
`diagnostic.hpp` 由 `compiler.hpp` 与 `core.hpp` 显式包含；首轮不新增 `diagnostic.h` 转发层。

## 类型与物理格式

public type 为：

| SQL 类型 | C++ Value | V2 物理编码（非 NULL） |
|---|---|---|
| `INT` | `std::int32_t` | 4-byte signed little-endian |
| `BIGINT` | `std::int64_t` | 8-byte signed little-endian |
| `DOUBLE` | `double` | IEEE-754 binary64 位模式，8-byte little-endian |
| `BOOLEAN` | `bool` | 1 byte：0=false、1=true，其他值按 corrupt |
| `VARCHAR` | `std::string` | uint32 little-endian 字节长度，随后为 UTF-8 字节 |
| SQL NULL | `std::monostate` | V2 null bitmap 置位，不编码 payload |

SQL NULL 不是独立 `Type`；`ColumnMeta.nullable` 默认 false，即 NOT NULL。VARCHAR 必须是合法
UTF-8，长度不超过 1024 字节；单行逻辑载荷为所有非 NULL 值之和（INT 4、BIGINT 8、DOUBLE 8、
BOOLEAN 1、VARCHAR 按 UTF-8 字节数），不超过 4096 字节；DOUBLE 必须 finite。

Storage metadata 用 `INT32`/`INT64`/`DOUBLE`/`BOOLEAN`/`VARCHAR` 与
`NOT_NULL`/`NULLABLE` 标记描述 schema。历史 V1 metadata 仍可读，其中
`INT32`（含兼容 token `INT`）与 `VARCHAR` 映射为 NOT NULL 列；V1 的
`INT64`、`FLOAT`、`DOUBLE`、`BOOL` 仍不是支持类型，显式失败。完整格式见
[SQL v2 扩展契约](SQLv2扩展契约.md) §10。

## Storage 与 Catalog

`storage.meta` 是 V2 bootstrap：它只标识已初始化的格式，不能保存或恢复用户 schema。
持久化 schema 的权威是两个 Storage 管理的特殊 HeapTable：TableId 0 的
`tdb_sys_tables` 保存每张用户表的 ID、名称与列数，TableId 1 的 `tdb_sys_columns` 保存列定义。
正常 open 先验证 bootstrap 与这两个 PageFile，再扫描 catalog 表重建 `StorageState.tables`；Core
随后通过 `storage::list_tables` 重建运行时 Catalog。Core Catalog 仍是逻辑副本，不是第二份持久化 catalog。

TableId 0 与 1 为保留 system table ID，普通用户表必须从 2 开始。特殊表可作为只读表被
`SELECT`，但普通 `CREATE`、`INSERT`、`UPDATE` 和 `DELETE` 均不得修改（`update_rows` 对
system table 返回 `kInvalidRequest`）；Storage 内部写入 catalog 时，先写
`tdb_sys_columns`，最后写 `tdb_sys_tables` 的 table row 作为 commit marker，marker 写入必须 flush 成功后才发布内存表元数据。

Core 从已恢复表的最大 ID 加一分配；候选值在 64 位计数器上比较，`UINT32_MAX` 本身仍可分配，
只有候选值超过 `UINT32_MAX` 后停止分配，不回绕。

Storage 是同进程 singleton。正常数据操作只在 Storage 处于 open 时可用；同表存在未关闭 cursor 时阻止非空 INSERT/UPDATE/DELETE。Core 必须在 EOF 和所有失败路径关闭 cursor；DELETE 与 UPDATE 固定采用“扫描 → 收集命中行 → 关闭 cursor → 一次性批量提交”的顺序，不在 cursor 打开期间写入。

## Database ownership 与生命周期

可以存在多个 `core::Database` 对象，但同一进程最多一个对象处于 open 或 cleanup-pending 状态。第二个 `Database::open` 返回 Core `kExecute`，且不调用 Storage。

成功 close 才释放 ownership。`close_storage` 返回错误时，Storage 保持 Closing，Database 保持 cleanup-pending，只允许原 owner 重试 `close()`；清理成功前不允许其他 Database open。重试返回 `kInvalidRequest` 表示 Storage 已经结束生命周期，可以按清理完成处理。

Storage 抛异常或 Core 遇到无法确认副作用的模块异常时，Core 先 best-effort 调用 `close_storage`，清空 Catalog 并使当前会话失效。若清理调用返回错误或抛异常，实例保留 cleanup-pending 与重试状态。该路径不能回滚已经发生的 CREATE/INSERT/UPDATE/DELETE 部分副作用，后续 open 必须从 Storage System Catalog 恢复 Catalog。

Database 可移动、不可复制。移动赋值若遇到未完成的关闭清理，必须保留当前 Impl 和重试入口，不能因为转移所有权而丢失 Storage owner。

## 执行边界

Compiler 负责 SQL 到 typed Plan；Core 不重新解析 SQL，并执行 `CreateTablePlan`、`InsertPlan`、
`QueryPlan`、`UpdatePlan`、`DeletePlan`。`QueryPlan` 的算子树可包含
`SeqScanNode`、`FilterNode`、`ProjectNode`、`JoinNode`、`SortNode` 与 `AggregateNode`，
统一按 query-local `SlotId` 绑定列。Core 只依赖 Storage 的 public requests/results，不能访问
HeapTable、BufferPool、RecordPage 或 PageFile 私有实现。

`split_statements` 成功时返回 SplitStatement 列表，整段 SQL 超过 `kMaxSqlBytes` 时返回
`SplitStatementsResult` 中的 CompileError，不抛 `std::length_error`。分句失败只由 `kMaxSqlBytes`
或分句契约违反触发；未闭合字符串/块注释仍作为残缺语句交给 `compile()`。Core 对分句错误返回
`script_error{kCompile}`（无可信局部位置时用空插入点 `{1,1,0}-{1,1,0}`），此时 statements 为空，
不得编译或执行 Plan，也不得关闭 Storage 或使 Database 会话失效。

SELECT 在完整 Storage Record 上计算 predicate，再进行投影。DELETE 在 cursor 成功关闭后才调用批量删除。INSERT 和 DELETE 的部分成功分别以 `InsertResult.rids.size()` 与 `DeleteResult.deleted_count` 作为已影响行数，不回滚。

## 诊断与脚本恢复

- `diagnostic.hpp` 定义半开区间 `SourceRange`、单处替换 `FixIt` 与 `CompileStage`；端点携带
  line/column/`byte_offset`，行列 1-based、`byte_offset` 0-based、列与偏移按 UTF-8 字节；
  `\r\n` 计一个换行、独立的 `\r` 占一列、Tab 按一字节一列；
  端点不得落在 `\r\n` 之间，非法范围按 `kInternal` 致命中止。
- `CompileErrorKind` 已删除，统一使用 `CompileStage`；`CompileError` 携带 stage、范围、message、
  可选 suggestion 与单个 fix-it；`SplitStatement` 携带 `sql` 与脚本绝对 `SourceRange`。
- 每条语句最多一个主诊断和一个可选 fix-it；多错误来自脚本内多条语句的分别分析。
- Core `Error` 携带 `compile_stage`、脚本绝对 `source`、`suggestion` 与 `fix_it`，仍不携带
  `StorageErrorKind`；`ErrorKind` 增加 `kAnalysis`。
- `StatementResult` 九态（U5 起含 `kCancelled`）且只能经命名工厂构造；`kInternal` 只允许
  出现在 `script_error`，不允许作为语句级 outcome。语句数上限 `kMaxStatementsPerScript = 4096`。
- `script_error` 只承载分句失败、语句数超限与致命中止三类；普通语句错误进入 `statements`。
- `analyze` 策略使用脚本局部影子 Catalog（只模拟 CREATE TABLE），不调用 Storage、
  不消耗运行时 `next_table_id`；被拒绝的 CREATE 也不消耗候选 ID。
- CLI 新增 `--error-policy stop|analyze`（默认 stop）；脚本级致命错误使 REPL 停止读取并
  best-effort close，退出码 1。
- U3 计划模式在 `ExecuteScriptRequest` 增加 `ExecutionMode mode`（默认 `kExecute`）：
  `kPlanOnly` 只编译不执行，语句记新增状态 `kPlanOnly` 并携带 core 渲染的单列 `plan` 文本；
  渲染只读 Catalog 解析人名，解析不到退化为 `table#N`/`slot#N`/`column#N`；渲染契约见
  [Plan 整理输出设计](core-cli/Plan整理输出设计.md)。CLI 开关为 `--plan`。
- U2 JSON 输出在入口新增 `--format table|json`（默认 table），core 与 include/ 零修改；
  NDJSON schema 见 [JSON 输出设计](core-cli/CLI升级设计_JSON输出.md)，
  参数错误保持纯文本 + 退出码 2。

## CLI 边界

入口只负责参数解析、输入读取、结果展示和退出码，不拆句、不解析 SQL、不包含数据库业务逻辑。初版 REPL 按行提交，支持一行内多条完整语句；跨行 SQL 属于后续升级项。stdout 只保留真实执行结果（`OK <affected_rows>`/查询行）；诊断、suggestion、fix-it、`ANALYZED`、`SKIPPED`、`INDETERMINATE` 与 `script_error` 均写入 stderr。

默认构建使用不可用 Session 适配器，以便独立验证 CLI 和 core fake 行为。真实 compiler、core、storage 联调通过 `TINYDBMS_ENABLE_REAL_MODULES=ON` 启用。

## 暂不纳入范围

当前不实现 FSM、Index、WAL、Transaction、MVCC、函数、LIKE、算术表达式、跨进程文件锁、
V1 自动原地迁移、DROP/ALTER、外连接、子查询、`UNION`、`LIMIT`/`OFFSET`、窗口函数与
崩溃原子性。正常 close 后的重启可见不等同于崩溃恢复或逐操作 fsync 承诺。
