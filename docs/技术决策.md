# tinydbms 技术决策记录

状态说明：

- **已定**：已确认的技术基线，改动需要重新确认。
- **未决**：尚未决定；在决定前不按假设实现。
- **范围外/暂不纳入**：初版明确不做或不属于本文档范围，后续需要时单独决定并扩展。

## 已定

### 1. C++20（保守子集）

全项目使用 C++20。CMake 固定：

```cmake
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

不使用 ranges、coroutines、modules。不使用 GCC 专属扩展，以保证 MSVC 可编译。

### 2. 平台与编译器

- Linux 开发与构建使用 g++。
- Windows 开发与构建使用 MSVC。
- 同一份源码必须能被两边编译，任何一侧的编译器特性都不能成为前提。
- 本地编译器版本较高不作为使用更新语言特性的依据。

### 3. 构建工具

CMake 负责工程描述，Ninja 负责实际构建。构建、测试入口由 CMakePresets 固定。

### 4. 进程与模块形态

- 单进程，无 IPC、网络或消息总线。
- 三层静态库：`tinydbms_compiler`、`tinydbms_storage`、`tinydbms_core`。
- 一个可执行入口 `tinydbms`。

### 5. 测试

- CTest 作为测试运行入口。
- 现阶段自写断言，不引入第三方测试框架。
- GoogleTest 作为后期可选方案，引入前需要单独确认，并决定离线构建下的引入方式。

### 6. 模块职责与交互基线

core 拥有逻辑 Catalog；compiler 无状态，内部实现不规定；storage 拥有物理存储与物理元数据。
compiler 对外提供无状态 `split_statements`（返回带原文本起点的语句）与编译入口；core 持有语句并逐条编译执行。
编译错误先以相对语句的位置返回，由 core 换算为整段输入的绝对位置。
compiler 输出 LogicalPlan，引用已有表/列时使用 ID；CREATE TABLE 使用名字与列定义。
TableId 由 core 分配；ColumnId 等于建表列序。
core 对外暴露有状态 `Database` 对象（open/close/execute_script）；storage 初版保持无句柄单例。
公共契约头文件位于顶层 `include/tinydbms/`，按 common/compiler/storage/core 拆分；
共享类型放在 `tinydbms` 根命名空间，模块 API 放在 `tinydbms::compiler`、`tinydbms::storage`、`tinydbms::core`。

- Database 可移动、不可复制；close 返回 Error 后离开打开状态，析构做 noexcept 兜底关闭。
- moved-from Database 上的公开方法均返回 `ErrorKind::kExecute`，析构必须安全；
  core 对模块意外异常做边界捕获，不能让异常越过公开 API。
- TableId/ColumnId 初版同为 uint32_t 别名，接受靠命名与测试防混用，不引入强类型包装。
- Plan/Expr 不可默认构造空树、不可复制；二叉树与计划树节点必须带非空子树构造。
- core 静态库不直接绑定 compiler/storage target；真实实现与测试 fake 由可执行入口/测试的组合点决定。
- core 源文件按生命周期、脚本主循环、执行器职责拆分；app 与 core 保持边界，app 不承载数据库业务逻辑。
- 执行器测试不扩张公共 `core.hpp`：行为测试通过 fake compiler 预置 Plan，调用公开的
  `Database::execute_script` 覆盖执行路径；不提供额外的 Plan 注入入口。

完整交互基线见 [docs/模块交互契约.md](模块交互契约.md)，字段级契约见 [docs/消息契约详细设计.md](消息契约详细设计.md)。

### 7. 用户入口

一个可执行文件，默认交互式 REPL，支持 stdin 批处理；只负责读入 SQL、展示 core 返回的结果与错误，不包含业务逻辑。
REPL 初版按行提交；跨行 SQL 暂不支持，列为后期优先升级项。
REPL 以 EOF 退出（Unix 终端通常 Ctrl-D；Windows 控制台通常 Ctrl-Z 后回车），初版不提供 SQL 之外的元命令。
stdin 非交互时按整段批处理执行。入口支持可选 `--data-dir <DIR>`，缺省使用当前目录下的 `tinydbms-data/`。
`--data-dir` 最多出现一次且值不能为空；参数错误返回 2，SQL/运行时错误返回 1；REPL 遇错继续读入，
EOF 后按累计错误标记和 close 结果返回最终状态。

### 8. 存储生命周期与持久化承诺

- 入口通过 core 的 Database::open 打开数据库，Database::open 内部调用 storage 的 open_storage；
  正常退出通过 Database::close 调用 close_storage。
- storage 为无句柄单例：同一进程同一时间只能打开一个数据库；storage 句柄化属于后续扩展。
- storage 成功返回表示操作已更新内部状态，正常 close_storage 后重启可见。
- 正常 close_storage 的统一落盘属于初版；不承诺逐次 fsync、显式 flush API、进程崩溃或断电后的持久性。
- close_storage 一旦被调用即释放 storage 打开状态；返回错误只表示落盘/收尾未完整成功。
- storage 重复 open、未打开时调用业务 API、重复 close 返回 `kInvalidRequest`；空目录可以初始化，空字符串路径非法。
- storage 公共 API 通过 Result 表达普通失败；core 对意外异常做边界捕获，析构和移动赋值的 best-effort 清理保持 noexcept。
- 数据目录统一使用 UTF-8 字符串；Windows 入口负责把宽字符路径转换为 UTF-8。
- 初版不支持两个进程同时打开同一 data_dir，storage 不提供文件锁；跨进程并发属于后续扩展。
- 共享上限：VARCHAR 值必须为合法 UTF-8 且 ≤ 1024 字节；单行逻辑载荷 ≤ 4096 字节
  （INT 计 4 字节，VARCHAR 按 UTF-8 字节数），与 storage 物理编码格式无关；storage 最终校验并返回 `kValueTooLarge`。

## 未决

- SQL 编译器层与页式存储层的内部技术方案未定，本文档不预设。
- 第三方运行时依赖策略未定。当前骨架不引入第三方依赖只是现状，不是已定策略。

## 范围外与暂不纳入

- 数据/文件格式与物理布局由 storage 内部决定，不在本文档预设。
- 事务与并发不在初版范围内；SQL 初版范围以消息契约文档中的语句与类型清单为准。
- 崩溃恢复、显式 flush API 与逐操作 fsync 未纳入当前消息契约；正常 close_storage 统一落盘属于初版，后续如需逐操作持久化再扩展。
