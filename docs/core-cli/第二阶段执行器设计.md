# 第二阶段执行器设计（实现规格）

本文是第一阶段提交后的第二阶段实现规格。它与
[消息契约详细设计](../消息契约详细设计.md) 和
[模块交互契约](../模块交互契约.md) 一起作为本轮 core 执行器开发的依据；三者已经同步
本阶段新增的 Plan、表达式和 storage Result 约束。

本文中的“必须”是实现要求，不是可选优化。若实现发现公共契约仍不足以表达需求，应先修改
契约文档并登记公共文件变更，再修改代码。

## 1. 阶段目标与边界

第二阶段只实现 `tinydbms::core` 内部的以下能力：

- `InsertPlan`：校验并按 Catalog 列序展开 INSERT 行，调用 storage `insert`；
- `DeletePlan`：预校验谓词，扫描、求值、收集 `RecordId`，再调用 storage `delete_records`；
- `QueryPlan`：预校验单表算子树，扫描、过滤、投影并组装 `QueryResult`；
- core 内部表达式预校验与求值：`ColumnRef`、`Literal`、比较、`AND`、`OR`、`NOT`；
- 上述路径的异常、部分成功、游标关闭、非法 Plan 和非法 storage Result 回归测试。

本阶段不包含：

- compiler 的词法、语法、SQL 语义和 Plan 生成代码；
- storage 的文件、页、记录编码和持久化实现；
- CLI 参数、REPL、结果排版；
- 事务、并发、JOIN、聚合、排序、NULL 和算术表达式。

行为测试继续通过 fake compiler/storage 调用公开的 `Database::execute_script`，不在
`include/tinydbms/` 增加测试入口，也不让测试直接依赖 core 私有实现。

## 2. 实现组织与依赖边界

第二阶段延续按职责拆分，禁止把执行器和表达式求值重新合并到 `database.cpp`：

| 文件 | 职责 |
|---|---|
| `src/core/executor.cpp` | Plan 分发、Catalog/Plan 预校验、INSERT/DELETE/SELECT 执行和结果映射 |
| `src/core/expression.hpp` | core 私有的表达式类型、预校验和求值声明，不安装到公共 include |
| `src/core/expression.cpp` | 表达式静态类型检查、递归求值和内部求值错误 |
| `src/core/internal.hpp` | `Database::Impl` 以及多个 core 源文件共享的最小内部辅助声明 |
| `tests/fakes/storage_*` | 可配置表、记录、游标、结果错误、异常和调用顺序 |
| `tests/core_executor_test.cpp` | 通过公开 Database API 覆盖本规格的执行器行为 |

`src/core/CMakeLists.txt` 必须把新增的 core 源文件加入 `tinydbms_core`；fake 只能链接到
测试目标，不得进入产品 `tinydbms`。本阶段预期不修改 `include/tinydbms/`。如果确实需要
修改公共头文件，必须同步更新契约、检查所有调用方，并在
[公共文件修改记录](../公共文件修改记录-提交前删除.md) 登记原因、影响、验证和待通知成员；
该记录仍属于最终提交前清理项。core 的实现先编译为不携带 compiler/storage 链接依赖的
`tinydbms_core_objects`；`tinydbms_core` 只负责打包这些对象。产品 `tinydbms` 显式链接
`tinydbms_core`、真实 `tinydbms_compiler` 和真实 `tinydbms_storage`。行为测试直接组合
`tinydbms_core_objects` 与 fake compiler/storage，不链接真实模块，避免静态库链接顺序造成
fake/real 混用。

## 3. 执行器的两阶段校验

所有执行器都分成“无 storage 副作用的预校验”和“取得运行时行后的执行校验”两层。

### 3.1 预校验：调用 storage 前完成

预校验失败不得调用 `open_table`、`insert` 或 `delete_records`；对需要游标的路径，也不得
为了发现 Plan 错误而先打开游标。预校验至少包括：

1. `TableId` 在当前 Catalog 中存在且唯一；
2. Plan 行宽、ColumnId、列清单排列和 Query 算子树满足本规格；
3. 所有表达式的指针结构、ColumnId、静态类型和操作符组合合法；
4. Query 的结果列头已经可以根据 Catalog 和 Project 生成。

`Database::open` 从 `list_tables` 恢复 Catalog 时也执行同一组结构性元数据检查：表名和列名必须
符合 `[a-z][a-z0-9_]*` 且长度为 1..64，列清单非空、列名不重复，且每个 `ColumnMeta.type`
必须是当前公共契约支持的 `Type::kInt` 或 `Type::kVarchar`。
检查失败属于 `ErrorKind::kInternal`，core 关闭已经打开的 storage、清空半成品状态并拒绝进入
open 状态；CREATE TABLE 在调用 storage 前同样不得把不满足该条件的元数据写入 Catalog。

Plan 引用不存在的 `TableId`、越界/重复/缺失 ColumnId、空 child/root、非法表达式或其他
Plan 不变量违反，统一返回独立的 `ErrorKind::kInternal`，不产生 storage 副作用。

### 3.2 表结构与运行时 Row 校验

- Catalog 中的列序是唯一物理行序，`ColumnId` 满足 `0 <= id < columns.size()`；
- storage 返回的每条 Record 必须有完整行，满足
  `record.values.size() == table.columns.size()`；
- 每个 `Value` 的 variant 类型必须与对应 `ColumnMeta.type` 一致；
- INSERT 的每个输入值在重排后必须与目标列类型一致；
- core 不重复实现 UTF-8 和逻辑载荷上限校验，最终存储约束由 storage 负责；
- 运行时行宽或 Value 类型不匹配是 core 与 storage 的契约不一致，返回 `kInternal`，并按
  DELETE/SELECT 的清理规则结束当前操作。

### 3.3 错误映射与优先级

| 情况 | 对外结果 |
|---|---|
| Plan/Catalog/表达式/Result 不变量违反 | 独立 `Error{ kInternal, ... }` |
| storage Result 携带 `StorageError` | `kStorage`，保留 storage message |
| compiler/storage 公开调用意外抛异常 | `kInternal`；无法可靠知道副作用数量时不报告部分成功数 |
| INSERT/DELETE 已有可靠成功数量后收到 storage error | `CommandResult{affected_rows, error}` |
| 没有可靠副作用数量的写入失败 | 独立 `Error` |

同一执行路径中，较早发生的主错误优先；清理错误不得覆盖扫描、求值或写入主错误。独立
Error 或携带 error 的 CommandResult 都会被 `execute_script` 视为失败并停止后续语句。

storage 的正常实现必须把内部异常转换为 Result，不能让“已经分配 cursor 但尚未返回 cursor
ID”的异常越过公共 API。若异常仍越过边界，core 会把当前 Database 会话标记为失效，先
best-effort 调用 `close_storage`（该调用必须使所有 cursor 失效并结束 storage 生命周期），
再返回 `kInternal`；这不能回滚已经发生的 CREATE/INSERT/DELETE 部分副作用，下一次 open
必须重新从 storage 恢复 Catalog。若 open/close 的清理调用自身抛异常，core 保留一次清理重试状态，
重试完成前拒绝 open；重试返回 `kInvalidRequest` 视为 storage 已结束生命周期。异常路径返回后，
调用者必须先调用一次 `Database::close`，才能再次 open。core 的 catch 是最后一道边界保护，
不是对 storage 异常安全的替代。

### 3.4 内部对象所有权与生命周期

- `ValidatedQuery`、表达式类型结果和 `CursorGuard` 都是 core 私有的临时对象，不跨
  `execute_plan_impl` 保存；
- 预校验阶段得到的 `TableMeta` 和 Expr 指针只借用当前 Plan/Catalog，执行结束即失效；
- INSERT 的 physical rows 是独立拥有的数据，传给 storage 前完成全部检查；
- SELECT/DELETE 不把 Record 或 Row 指针存入 Catalog，也不把 cursor ID 暴露给调用者；
- 单线程顺序执行保证一次 Plan 执行期间 Catalog 不会被并发修改。

## 4. 表达式预校验与求值

### 4.1 静态类型

core 私有实现定义三种表达式类型：`INT`、`VARCHAR`、`BOOL`。其中 BOOL 只作为求值中间
结果存在，不进入公共 `Value`。

`validate_expr(expr, table_meta, expected_type)` 在打开游标前递归执行：

- `ColumnRef`：检查 ColumnId，并从 Catalog 取得列类型；
- `Literal`：从 `Value` variant 取得 INT 或 VARCHAR 类型；
- 比较：两侧必须是 Value 类型且类型相同；INT 支持 `= != < <= > >=`，VARCHAR 只支持
  `= !=`，结果类型为 BOOL；
- `AND/OR`：两侧必须是 BOOL，结果类型为 BOOL；
- `NOT`：operand 必须是 BOOL，结果类型为 BOOL；
- Binary 的 lhs/rhs、Unary 的 operand 为空时立即失败；
- Filter 和 DELETE 的顶层表达式必须为 BOOL。

预校验发现错误时返回 `kInternal`，不依赖表中是否存在记录，因此空表也不会掩盖非法 Plan。

为限制恶意或异常深度 Plan 对调用栈的压力，core 对表达式校验和求值统一设置最大递归深度
`256`；超出限制返回 `kInternal`，不打开 cursor。该限制只保护 core 的遍历过程，compiler
仍应避免构造无意义的深树。

### 4.2 运行时求值

求值器使用以下 core 私有形态：

```text
EvalValue = Value | bool
eval(Expr, Row) -> EvalValue 或 EvalError
```

求值前先完成整行宽度和 Value variant 校验。随后：

- `ColumnRef` 返回 Row 中对应位置的 Value；
- `Literal` 返回自身 Value；
- 比较只在预校验允许的类型组合上执行；
- `AND/OR` 先求出两侧结果，再应用逻辑运算；本阶段不采用短路求值，以便错误处理稳定；
- `NOT` 只接受 BOOL。

表达式无副作用，也不支持 NULL，因此两侧求值不会改变数据库状态。所有 EvalError 都映射
为 `kInternal`；不执行隐式类型转换、算术、函数或用户可观察副作用。

## 5. storage Result 防御规则

core 按以下顺序检查 storage 返回值；违反 Result 不变量时，不把不可信字段继续传给下一步。

### 5.1 OpenTableResult

| error | cursor | 处理 |
|---|---|---|
| 空 | 有值 | 成功取得游标，进入扫描 |
| 有值 | 空 | 正常 storage 错误，映射为 `kStorage`，不调用 close |
| 空 | 空 | storage Result 违反契约，返回 `kInternal` |
| 有值 | 有值 | storage Result 违反契约；返回 `kInternal`，但把 cursor 当作已取得并 best-effort close 一次 |

### 5.2 ScanNextResult

| error | record | 处理 |
|---|---|---|
| 空 | 有值 | 成功返回一条记录 |
| 空 | 空 | 自然结束；游标仍需 close |
| 有值 | 空 | 扫描 storage 错误，映射为 `kStorage`，record 不可使用 |
| 有值 | 有值 | Result 违反契约，返回 `kInternal`，record 不可使用 |

扫描错误、Result 违反、行校验错误或表达式错误都必须先保存主错误，再关闭已取得的游标。

### 5.3 CloseCursorResult 与异常

core 使用一次性 `CursorGuard`。调用 `close_cursor` **之前**设置 `close_attempted`，因此：

- close 成功或返回 storage error 都算已经完成一次 cursor 清理；close 抛异常也算已尝试，
  guard 析构不得再次调用同一个 close_cursor。若因此触发 Database 级会话清理，
  由 core 的 close_storage/retry 机制统一回收，不通过未知 cursor ID 重试；
- 主流程已有错误时，close 的错误/异常只记录为清理失败，不覆盖主错误；
- 主流程无错误时，close 返回 storage error 映射为 `kStorage`，抛异常映射为 `kInternal`；
- guard 析构必须 `noexcept`，仅在主流程未显式调用 close 且仍持有 cursor 时 best-effort 调用，
  并吞掉异常；
- `open_table` 没有取得 cursor 时不调用 close，除非返回值本身同时携带了 cursor，此时按
  5.1 的异常 Result 处理。

## 6. INSERT 执行设计

### 6.1 Plan 约束与列重排

`InsertPlan` 只能引用当前 Catalog 中的一张表。合法 `rows` 至少包含一行；空 `rows` 是
compiler/Plan 契约违反，core 返回 `kInternal`，不调用 storage。

`columns` 的合法形态只有两种：

1. 为空：每行已经按建表列序排列；
2. 非空：恰好包含每个 `ColumnId` 一次，顺序是 SQL 列清单顺序。

每行的值数量必须等于 `columns.size()`（`columns` 为空时等于表列数）。重复、缺失、越界
或行宽不一致均在预校验阶段失败。

core 为每行构造大小等于表列数的 `physical_row`：

```text
columns 为空：physical_row = input_row
columns 非空：physical_row[columns[i]] = input_row[i]
```

所有行检查和重排完成后才调用一次 `storage::insert`，避免前置错误造成部分写入。

### 6.2 InsertResult 映射

- storage 成功时必须满足 `rids.size() == rows.size()`，返回
  `CommandResult{rows.size(), nullopt}`；
- storage 携带错误时，`rids` 只包含错误前已成功插入的行：
  - `rids` 为空：返回独立 `kStorage` Error；
  - `rids` 非空：返回 `CommandResult{rids.size(), kStorage Error}`；
- `rids.size() > rows.size()` 或成功/失败结果违反不变量，返回 `kInternal`，并按 storage
  异常路径结束当前 Database 会话，因为实际写入数量已不再可信；
- storage 调用抛异常时，core 无法确认副作用数量，返回 `kInternal`，不猜测 affected_rows；
- INSERT 失败后，`execute_script` 不执行后续语句。

## 7. DELETE 执行设计

### 7.1 预校验、扫描与谓词

1. 通过 Catalog 校验 `table_id`，并预校验 predicate（无 predicate 表示恒真）；
2. 只有预校验成功后才调用 `open_table`；
3. 按 5.1 校验 OpenTableResult，取得 cursor 后建立 CursorGuard；
4. 循环调用 `scan_next`，按 5.2 分类；
5. 有 Record 时先校验完整 Row，再用完整物理行求值 predicate；命中则收集 RecordId；
6. 自然结束后调用一次 close；
7. 只有扫描、求值、Result 校验和 close 全部成功，才调用 `delete_records`。

无 predicate 时每条记录都命中。扫描失败时即使已经收集部分 RecordId，也不得删除这批 ID。
自然结束且没有命中行时仍调用 `delete_records`；空 rids 对有效 table_id 是合法零行删除。

### 7.2 DeleteResult 映射

- storage 成功时必须满足 `deleted_count == rids.size()`，返回
  `CommandResult{deleted_count, nullopt}`；
- storage 携带错误且 `deleted_count == 0`：返回独立 `kStorage` Error；
- storage 携带错误且 `deleted_count > 0`：返回携带 error 的 CommandResult；
- `deleted_count > rids.size()` 或其他 Result 不变量违反：返回 `kInternal`，并结束当前
  Database 会话，因为实际删除数量已不再可信；
- storage 调用抛异常：返回 `kInternal`，不伪造部分成功数量；
- close 失败或抛异常时不调用 `delete_records`。

## 8. SELECT 执行设计

### 8.1 合法算子树

为保证过滤始终作用于完整物理行，compiler 必须生成且 core 只接受以下四种 root 到叶子
的单链结构：

```text
SeqScan
Filter -> SeqScan
Project -> SeqScan
Project -> Filter -> SeqScan
```

约束为：

- `SeqScanNode` 恰好一个；
- `FilterNode`、`ProjectNode` 各最多一个；
- `ProjectNode` 必须位于 `FilterNode` 外层；
- 所有 root/child 指针非空；
- `ProjectNode.outputs` 至少一个 ColumnId；
- outputs 中 ColumnId 可以重复，但顺序原样保留；
- 越界 ColumnId、额外节点、其他拓扑或空 outputs 返回 `kInternal`，不调用 storage。

没有 ProjectNode 时采用全列投影。core 在预校验阶段取得唯一 SeqScan 的 table_id，按 Catalog
生成列名和类型；结果列头和每行的 Value 顺序与投影顺序一致。

### 8.2 执行顺序与错误

```text
校验算子树、Catalog、Filter 表达式和 Project outputs
  -> 生成 QueryResult.columns
  -> open_table / 校验 OpenTableResult
  -> scan_next 循环 / 校验 ScanNextResult
       校验完整 Record
       对完整 Row 求值 Filter
       命中后按 outputs 复制 Value 到结果 Row
  -> close_cursor
  -> 返回完整 QueryResult
```

任何预校验、扫描、行校验、表达式或 close 错误都会丢弃已收集行并返回独立 Error；不返回
部分 QueryResult。core 保留 storage 实际返回的扫描顺序，不承诺 SQL 层排序。

## 9. 测试矩阵与验收条件

### 9.1 INSERT

- 全列 INSERT 与指定列顺序重排；
- 空 rows、行宽、重复/缺失/越界 ColumnId、值类型错误均不调用 storage；
- storage 零行失败、部分成功失败、成功结果数量不一致和异常；
- storage 返回超过输入行数的 RecordId 数量；
- storage 在 CREATE/INSERT 返回前产生副作用后抛异常时，core 必须 close_storage、清空 Catalog
  并要求先 close 再重新 open；
- Catalog 不存在 table_id；
- 成功后下一条语句能看到已有 Catalog，错误后后续语句停止。

### 9.2 DELETE

- 无 WHERE、INT/VARCHAR 比较、AND/OR/NOT；
- 无 WHERE 的成功删除以及 VARCHAR 有序比较的拒绝；
- 非法谓词在空表上也必须在 open_table 前失败；
- 无命中时仍调用空 `delete_records`；
- open_table 四种 Result 组合、scan 的四种 Result 组合；
- open_table 已创建 cursor 但返回前抛异常时不得遗留 cursor，core 必须通过 close_storage 清理；
- scan 错误、行校验错误、表达式错误、close 错误/异常；
- 扫描失败时恰好尝试关闭一次且不删除；delete 部分成功和 Result 不变量违反。
- delete_records 产生部分删除后抛异常时结束当前 Database 会话，重新 open 后以 storage 实际状态为准；

### 9.3 SELECT

- 四种合法算子树、全列、指定列、重复投影列、Filter 后投影；
- 空 root、空 child、零个/多个 SeqScan、错误节点顺序、空/越界 outputs；
- FilterNode/ProjectNode 的 null child；
- 非法谓词在空表上也必须在 open_table 前失败；
- open/scan 的非法 Result 组合、扫描错误和 close 错误都不返回已收集行；
- open_table 产生 cursor 后抛异常时不调用未知 cursor ID 的 close_cursor，而通过 close_storage 清理；
- 结果列名、类型、列序和行值顺序与 Catalog/Project 一致。

### 9.4 全局验收

- `tinydbms.version`、`tinydbms.contracts_compile`、生命周期测试和执行器测试全部通过；
- `git diff --check` 无空白错误；
- 表达式深度超过 256 时在 open_table 前返回 `kInternal`，不因递归遍历栈溢出；
- 测试只通过 `tinydbms_core_objects` 与 fake 模块提供执行依赖，不把 fake 或真实模块混入同一
  core 行为测试目标，产品 `tinydbms` 显式链接真实模块；
- 本阶段不新增公共头文件改动；如有例外，先同步契约和公共文件修改记录。

## 10. 实施顺序
