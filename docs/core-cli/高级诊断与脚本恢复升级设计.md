> 状态：已落地。A 类决策已于 2026-09-12 关闭并采用推荐值，公共头文件、Core/CLI 实现与 fake 测试

## 1. 目标与边界

本轮 Core/CLI 升级提供以下能力：

- 保留 Compiler 的词法、语法、语义阶段和范围诊断；
- 将单条语句相对位置统一换算为脚本绝对位置；
- 脚本在首个编译或执行错误后关闭执行门；
- 可选继续编译后续边界可信语句，收集更多独立诊断；
- 用脚本内的影子 Catalog 支持“前一条分析态 CREATE、后一条引用”的语义分析；
- CLI 明确区分已执行、编译失败、执行失败、执行不确定、分析失败、仅分析和跳过；
- 保持首错后的 Storage 零调用和运行时 Catalog 零修改。

本轮不负责：

- Compiler 怎样恢复词法/语法错误、怎样计算候选建议；
- 在同一条语句内部返回多个诊断；
- 新 SQL 语法的执行器；
- Storage 新类型、NULL 或 UPDATE 的物理实现；
- 事务性回滚首错之前已经成功执行的语句；
- 在分句边界已经不可信时猜测后续语句。

## 2. 当前行为与目标行为

当前 `Database::execute_script` 按“分句 → 编译 → 执行”循环，遇到第一条错误后停止，结果只有按尝试顺序排列的 `outcomes`。目标行为增加显式策略：

| 场景 | `kStopOnFirstError` | `kAnalyzeRemaining` |
|---|---|---|
| 首错前 | 编译并执行 | 编译并执行 |
| 首个编译错误 | 记录并返回，其余 `kSkippedExecution` | 记录，关闭执行门，继续分析 |
| 首个执行错误 | 记录并返回，其余 `kSkippedExecution` | 记录，关闭执行门，继续分析 |
| 首错后的编译成功 | 逐条 `kSkippedExecution` | `kNoCatalogChange`/`kApplied` 为 `kAnalysisOnly`，`kRejected` 为 `kAnalysisError`；均不执行 |
| 首错后的编译失败 | 逐条 `kSkippedExecution` | `kCompileError`，继续下一条 |
| 首错后的 Storage 调用 | 不发生 | 不发生 |
| 致命中止（异常、内部不变量、影子建立失败） | 立即停止：可能已产生副作用的语句 `kExecutionIndeterminate`，否则 `kSkippedExecution`；其余 `kSkippedExecution` | 同左，不再继续分析 |

执行门在一次 `execute_script` 内只能从开变关，不能因为后续分析成功而重新打开。下一次 REPL 提交是新的脚本调用：只要 Database 会话仍有效，它有新的执行门。

已关闭的 A 类决策直接约束本文：A1 默认 `stop`、A4 分句致命失败保守停止、A5 影子 Catalog 仅模拟 CREATE、A6 首轮不默认打印摘要、A7 单脚本上限 4096、A8 单主诊断和单 fix-it。第一轮 CLI 对任何 `script_error` 都按 REPL 致命处理（见 §8.4）。

## 3. Core 脚本状态机

### 3.1 状态

Core 内部使用以下脚本局部状态，不进入公共头文件：

```cpp
enum class ShadowApplyResult {
    kNoCatalogChange,  // SELECT/INSERT/UPDATE/DELETE 等不改变 Catalog 的 Plan
    kApplied,          // CREATE TABLE 成功写入影子 Catalog
    kRejected          // CREATE TABLE 结构化失败（ID 耗尽、重复名称、非法元数据）
};

struct AnalysisState {
    Catalog catalog;
    std::uint64_t next_table_id;  // 与运行时同宽；超过 UINT32_MAX 后拒绝分配，严禁回绕
};

struct ScriptContext {
    bool execution_allowed{true};
    std::optional<AnalysisState> analysis;
};
```

`execution_allowed` 控制所有执行器和 Storage 调用；`analysis` 只在 analyze 策略且分句成功后分配。结构化错误只关闭执行门，analyze 仍可继续编译；任何致命错误都不再继续循环，直接把剩余语句记 `kSkippedExecution` 并结束，因此不需要额外的 analysis_available 标志。影子计数器与运行时 Catalog 的 `next_table_id` 同为 `std::uint64_t`，禁止窄化为 `TableId` 后再递增。

Core 内部还必须有 `side_effects_possible` 判定（可以复用 cleanup-pending/forced_close_pending 标志）：它表示当前语句是否已经调用过 Storage、或会话是否已进入 cleanup-pending。该标志只用于脚本层把 `kInternal` 区分为 `kExecutionIndeterminate` 或 `kSkippedExecution`，不进入公共头文件。

状态迁移：

0. split 成功后立即检查语句数：超过 `kMaxStatementsPerScript = 4096` 时 `statements` 为空，`script_error` 为 `kCompile`/`CompileStage::kLex`，直接返回，不编译、不执行、不调用 Storage；
1. 调用开始：执行门打开；analyze 策略先复制运行时 Catalog 与 `next_table_id`，复制失败按致命错误处理，全部语句记 `kSkippedExecution`；
2. 编译成功且执行成功：更新运行时 Catalog；如果是成功 DDL 且 `policy == analyze`，再以相同元数据同步影子副本（同步失败为致命错误，已完成语句保持 `kExecuted`）；
3. 编译返回结构化错误：记 `kCompileError`，执行门关闭；analyze 继续，stop 把剩余语句记 `kSkippedExecution` 后结束；
4. 执行返回结构化错误（含部分完成）：记 `kExecutionError`，执行门关闭；analyze 继续，stop 把剩余语句记 `kSkippedExecution` 后结束；
5. 门关闭后的编译成功：调用 `apply_supported_ddl`；`kNoCatalogChange` 和 `kApplied` 记 `kAnalysisOnly`，`kRejected` 记 `kAnalysisError`，异常按致命错误处理；
6. 门关闭后的编译错误：记 `kCompileError`，影子 Catalog 不变；
7. 致命中止（Compiler/Storage 抛异常、Core 不变量失败、影子建立或同步失败、分配失败）：`side_effects_possible == false` 时当前语句起全部 `kSkippedExecution`；`side_effects_possible == true` 时当前语句 `kExecutionIndeterminate`、其后 `kSkippedExecution`。两种情况都填充 `script_error` 后结束。

### 3.2 主循环伪代码

```text
validate request size
try: split = compiler.split_statements(text)
catch: script_error = kInternal({1,1,0}-{1,1,0}); return (statements 为空)

if split 返回错误:
    script_error = kCompile(绝对范围；契约违反时为 kInternal + {1,1,0}-{1,1,0})
    return (statements 为空)

if split.statements.size() > kMaxStatementsPerScript:
    script_error = kCompile(kLex, {1,1,0}-{1,1,0}, "script has too many statements")
    return (statements 为空)

execution_allowed = true
if policy == analyze:
    try: analysis = copy(runtime_catalog + runtime_next_table_id)
    catch: script_error = kInternal; 全部 statements = skipped; return

for i in 0..n-1:
    catalog = execution_allowed ? runtime_catalog : analysis.catalog
    try: compile_result = compiler.compile(statement.sql, catalog)
    catch: script_error = kInternal; statements[i..] = skipped; break

    if compile_result 是错误:
        statements[i] = kCompileError(绝对诊断)
        if policy == stop:
            statements[i+1..] = skipped; break
        execution_allowed = false
        continue

    if not execution_allowed:
        try: shadow_result = apply_supported_ddl(analysis, plan)
        catch: script_error = kInternal; statements[i..] = skipped; break
        if shadow_result == kRejected:
            statements[i] = kAnalysisError
        else:  # kNoCatalogChange 或 kApplied
            statements[i] = kAnalysisOnly
        continue

    try: execution = execute_plan(plan)
    catch: statements[i] = kExecutionIndeterminate
           script_error = kInternal; statements[i+1..] = skipped; break

    if execution 是 kInternal:
        if execution.side_effects_possible or cleanup-pending:
            statements[i] = kExecutionIndeterminate
        else:
            statements[i] = kSkippedExecution
        script_error = kInternal(执行器不变量失败)
        statements[i+1..] = skipped; break

    if execution 是结构化错误或部分失败:
        statements[i] = kExecutionError
        if policy == stop:
            statements[i+1..] = skipped; break
        execution_allowed = false
        continue

    statements[i] = kExecuted
    if 成功 DDL 且 policy == analyze:
        try: mirror confirmed metadata into analysis
        catch: script_error = kInternal; statements[i+1..] = skipped; break
```

Core 必须在调用任何执行器之前检查执行门。即使未来新增 Plan variant，默认分支也不能绕过该检查。

compile 抛异常时当前语句也记 skipped（执行阶段从未开始），原因由 `script_error` 描述；执行抛异常或返回 `kInternal` 时，只有 `side_effects_possible` 或 cleanup-pending 为真才记 `kExecutionIndeterminate`，否则当前语句起全部 skipped。执行器返回 `kInternal` 绝不能走 `kExecutionError` 分支。

`split_statements` 返回的 `CompileError::source` 已经是整段脚本绝对范围，Core 只做合法性校验、不再平移；`compile()` 返回的相对范围才交给 `absolutize_range`。没有可信局部位置的脚本级错误统一写 `{1,1,0}-{1,1,0}`。

### 3.3 错误分类

结构化错误——产生语句结果、关闭执行门；analyze 策略可以继续静态分析：

| 来源 | 语句状态 | 备注 |
|---|---|---|
| `compile()` 返回 CompileError | `kCompileError` | 不能执行 |
| ExecuteResult 为 Error（`kExecute`/`kStorage`） | `kExecutionError` | 未产生部分写入 |
| CommandResult 带 error（部分 INSERT/DELETE/UPDATE） | `kExecutionError` | `affected_rows` 保留错误前成功数量 |
| 分析态影子更新返回 `kRejected` | `kAnalysisError` | 仅 analyze 策略，不执行；`kNoCatalogChange`/`kApplied` 记 `kAnalysisOnly` |

致命错误——`script_error` 非空，立即停止，剩余语句记 `kSkippedExecution`：

| 来源 | 语句结果 |
|---|---|
| 分句失败、语句数超限或 split 抛异常 | statements 为空，只有 script_error |
| `compile()` 抛异常 | 当前语句起全部 skipped（执行阶段从未开始） |
| `compile()` 返回非法范围 | 当前语句起全部 skipped；`script_error = kInternal` |
| 执行抛异常 | 当前 `kExecutionIndeterminate`，其后 skipped（可能已产生物理副作用） |
| 执行器返回 `kInternal` 且 `side_effects_possible` 或 cleanup-pending | 当前 `kExecutionIndeterminate`，其后 skipped |
| 执行器返回 `kInternal` 且未调用 Storage | 当前语句起全部 skipped |
| 影子 Catalog 建立失败 | 全部已识别语句 skipped |
| 影子 Catalog 同步失败 | 已完成语句保持 `kExecuted`，其后 skipped |
| 结果聚合或分配失败 | 已构建结果保留，按异常保证处理 |

两个通道的边界固定：`kInternal` 只出现在 `script_error`，语句级 outcome 只允许 `kCompile`、`kExecute`、`kStorage`、`kAnalysis`。执行器返回 `kInternal` 时脚本层不得构造 `kExecutionError`；`side_effects_possible` 是 Core 内部标志，不进入公共头。查询结果为空、`affected_rows == 0`、分析态编译成功都不是错误。

## 4. 影子 Catalog

### 4.1 建立时机与数据来源

影子 Catalog 只在 `kAnalyzeRemaining` 下建立，并在执行第一条语句前复制：

- 最后一次确认成功后的运行时表元数据；
- 当前 `next_table_id`（`std::uint64_t`，复制后也不得窄化）；
- System Catalog V2 已暴露给 Compiler 的只读表定义。

它不从 Storage 重新 `list_tables`，不读取文件，也不共享可变容器。复制失败时返回 `kInternal` 脚本错误并且不执行任何语句。每次运行态 DDL 完整成功后，Core 再把同一份已确认元数据同步到影子副本；同步失败时，已完成语句仍记录为 `kExecuted`，同时设置 `script_error`、关闭执行门并停止本次脚本，不能继续执行并留下过期影子状态。

提前建立副本会增加一次有界 Catalog 复制，但能保证 Storage 在副作用后失败或 Core 进入 cleanup-pending 时，恢复分析仍有异常前的最后确认状态，不依赖失败现场重新分配内存或读取已经失效的会话对象。

### 4.2 第一轮只模拟 CREATE TABLE

第一轮只模拟成功编译的 CREATE TABLE（A5 已关闭）。分析态执行入口返回三态：

- `kNoCatalogChange`：INSERT、DELETE、SELECT、ORDER BY、JOIN 和 GROUP BY 等不改变 Catalog，无需模拟数据；
- `kApplied`：CREATE TABLE 成功写入影子 Catalog；
- `kRejected`：CREATE TABLE 结构化失败（ID 耗尽、重复表名、非法元数据）。

`kNoCatalogChange` 与 `kApplied` 都记 `kAnalysisOnly`；只有 `kRejected` 记 `kAnalysisError`。具体约束：

- 复用运行时 Catalog 的元数据校验和重复表名规则；
- 影子 Catalog 复制运行时 Catalog，包含 system tables；候选 ID 从 2 起，禁止分配 0/1 或已存在的 ID；
- 使用影子 `std::uint64_t next_table_id` 分配候选 ID：仅在候选值不超过 `UINT32_MAX` 时可用，比较与递增都在 64 位上完成；
- 成功插入影子表后递增影子计数器；失败不消耗 ID；
- 候选值超过 `UINT32_MAX`（ID 耗尽）产生该语句的 `kAnalysisError`，严禁回绕或窄化；后续语句仍可在未变更的影子 Catalog 上分析；
- 分析态 DDL 更新必须提供强异常保证：先完成校验和可能抛出的分配，再提交 Catalog 与 next_table_id；失败时两者都保持不变；
- 绝不调用 `storage::create_table`；
- 绝不修改运行时 Catalog 或运行时 `next_table_id`；
- 脚本结束后销毁影子状态。

未来 ALTER/DROP/视图等 DDL 必须逐项增加影子语义，不能默认把任意 Plan 当作 Catalog 安全操作。

### 4.3 执行失败后的不确定物理状态

Storage 若在产生部分副作用后失败，Core 无法承诺回滚。此时影子 Catalog 必须基于“最后一次确认成功”的运行时 Catalog，而不是猜测磁盘真实状态；后续结果明确是静态分析，不代表数据库可以按该状态执行。现有 cleanup-pending、会话失效和 best-effort close 规则继续生效。

## 5. 诊断位置换算

Compiler 对单条语句返回相对 `statement.sql` 的半开范围，Core 负责转换为整段脚本绝对范围：

- 偏移：`absolute.byte_offset = statement.source.begin.byte_offset + relative.byte_offset`；
- 行：相对第一行叠加语句起始行，其余行保留相对行偏移；
- 列：只有相对第一行需要叠加语句起始列，其余行直接使用相对列；
- 主诊断和 fix-it 必须使用同一换算函数；
- 换算前校验相对范围没有越过 `statement.sql`；非法范围转换为 `kInternal`，不能越界切片或产生错误 fix-it。
- 换行与列计数沿用公共契约：`\n` 分行、`\r\n` 计一个换行且 `\r` 不占列、Tab 按一字节一列计；换算不得另行定义换行口径；
- 换算后的端点必须落在合法字节边界且不得位于 `\r\n` 之间；违反时按致命错误处理并记 `kInternal`，不得输出错误 fix-it。

建议实现单一内部函数 `absolutize_range(statement_source, relative_range)`，并用多字节 UTF-8、跨行范围、空插入点和语句非第一列开头测试，避免主诊断与 fix-it 两套算法漂移。

- `split_statements()` 返回的 `CompileError::source` 已经是整段脚本绝对范围，Core 只校验合法性、不得再平移；只有 `compile()` 返回的相对 `source` 和 `fix_it.range` 走 `absolutize_range`；
- 没有可信局部位置的脚本级错误（分句失败、语句数超限、分句契约违反）统一使用空插入点 `{1,1,0}-{1,1,0}`。

## 6. 异常保证、资源与生命周期

### 6.1 异常保证

- Compiler 和 Storage 的正常实现不向 Core 抛异常；Core 在每次跨模块调用处捕获异常并转换。
- Core 公共方法（open/close/execute_script）不主动抛业务异常：跨模块违约异常、Core 内部逻辑异常和 `std::bad_alloc` 都按 §3.3 转成结构化结果。
- 部分结果优先：异常发生前已完成的语句结果必须保留并按原顺序返回；执行中被中断的语句记 `kExecutionIndeterminate`；其余已识别语句记 `kSkippedExecution`。
- 仅当连“部分结果 + 最小 script_error”都无法构造时，才允许 `std::bad_alloc` 越过公共 API。app 必须捕获它、按致命错误处理（退出码 1）并 best-effort close；该分支必须有 app 兜底测试。
- Database open/close 沿用既有 cleanup-pending 与析构兜底规则；moved-from 语义不变。
- 第一轮 REPL 对任何 `script_error` 都按致命处理：停止读取后续输入、best-effort close、退出码 1；该规则不需要新增 Database 状态查询 API。结构化错误（`kCompileError`/`kExecutionError`/`kAnalysisError`）仍可继续 REPL。

### 6.2 资源与限制

- Storage/执行器异常沿用现有 fail-closed 与 cleanup-pending 语义；执行门永久关闭。
- 已构造的 Plan、游标和临时行缓冲必须在每条语句边界使用 RAII 清理；进入 `kAnalysisOnly` 后 Plan 在影子 DDL 更新完成后立即销毁。
- `kAnalyzeRemaining` 不放宽 `kMaxSqlBytes`、表达式深度、行宽、结果集内存或单次脚本语句数限制。`kMaxStatementsPerScript = 4096`（A7 已关闭）在 split 成功后、任何编译或执行前检查；超限时 `statements` 为空、`script_error` 为 `kCompile`/`kLex`，且不发生任何 Storage 调用。
- 分析阶段不得创建 cursor、扫描记录、写表或调用 close/open Storage。
- 诊断建议来自 Compiler，不得被 Core 或 CLI 自动执行。

## 7. Core 文件组织建议

保持公共 API 在 `include/tinydbms/core.hpp`，实现细节继续位于 `src/core/`。建议按职责拆分，避免把脚本状态机继续堆入执行器：

- `database.cpp`：Database 生命周期和公开 API 兜底；
- `script.cpp`：分句、策略、执行门、逐语句聚合；
- `diagnostics.cpp/.hpp`：范围校验与绝对位置换算；
- `analysis_catalog.cpp/.hpp`：影子 Catalog 建立和受支持 DDL 模拟；
- `executor.cpp`：只执行已被脚本层允许的 Plan；
- `internal.hpp`：共享内部状态和小型不变量，不承载大段实现。

实际文件名可按同步后的目录调整，但职责必须可单测，且 `execute_plan_impl` 不能自行决定“错误后是否继续”。

## 8. CLI 升级

### 8.1 参数

新增：

```text
--error-policy stop|analyze
```

- `stop` 映射 `kStopOnFirstError`；
- `analyze` 映射 `kAnalyzeRemaining`；
- 默认 `stop`（A1 已关闭）；
- 缺值、未知值、重复出现均为参数错误，退出码 2；缺值判定与 `--data-dir` 一致：下一个 token 是另一个 `--` 选项或已经到末尾都算缺值；
- 不支持 `--error-policy=analyze` 形式，按未知参数处理；
- `--help` 说明 analyze 只继续静态分析，不会执行首错后的 SQL；
- REPL 和批处理都把同一策略放入每次 ExecuteScriptRequest。

### 8.2 输出通道与格式

stdout 只输出真实执行产生的 QueryResult 和 CommandResult。以下内容写入 stderr：

- 编译、执行、Storage、内部和 I/O 错误；
- suggestion 和 fix-it；
- `kAnalysisOnly`、`kSkippedExecution`、`kExecutionIndeterminate` 提示；
- 首轮不默认输出脚本恢复摘要（A6 已关闭）；后续如需摘要，另开 `--verbose` 扩展，不改变默认快照。

输出顺序固定为：按 `statements` 顺序展示；`script_error`（若存在）插在最后一条非 `kSkippedExecution` 语句之后、第一条 skipped 之前；没有语句结果时（分句失败）只展示 `script_error`。影子状态同步等晚发内部错误不能倒置，也不能丢弃前面已经执行成功的真实结果。

不能为 `kAnalysisOnly` 或 `kSkippedExecution` 输出 `OK 0`，否则脚本会把未执行语句误判成成功。建议稳定格式：

以下仅为各行格式示例，不是同一次执行的完整状态轨迹。

```text
# stderr
ERROR semantic 3:8-3:13 unknown column "naem"
SUGGESTION did you mean "name"?
FIX 3:8-3:12 name
# stdout
OK 2
# stderr
ANALYZED 4:1-4:20
ERROR storage 5:1-5:30 value too large
INDETERMINATE 6:1-6:30
ERROR internal 6:1-6:30 storage threw during execution
SKIPPED 7:1-7:12 aborted
```

约束：

- 语句级编译错误使用 `ERROR lex|syntax|semantic <diagnostic range> <message>`，不再只显示笼统的 `compile`；
- `kExecutionError` 的错误标签使用 `execute` 或 `storage`，范围取该语句的 `StatementResult::source()`；携带 error 的 `CommandResult` 先在 stdout 输出 `OK <affected_rows>`，再在 stderr 输出错误行，保持现有“先报告已完成部分”的行为；
- 影子状态更新失败使用 `ERROR analysis <diagnostic range> <message>`，不得显示为 execute；
- `kSkippedExecution` 输出 `SKIPPED <range> <policy|aborted>`：`script_error` 为空时为 `policy`，存在时为 `aborted`；
- `kExecutionIndeterminate` 输出 `INDETERMINATE <range>`，具体原因由随后的 `script_error` 行给出；
- `script_error` 使用 `ERROR <kind> <range> <message>`：分句失败或语句数超限时 kind=`compile`，致命中止时 kind=`internal`；
- 语句级 compile 标签只会是 lex/syntax/semantic；脚本级 compile 行只用于分句失败和语句数超限，两者作用域不同但格式一致；
- 范围采用 `begin_line:begin_column-end_line:end_column`；单点范围也保留完整格式，不压缩展示；
- 所有消息和 replacement 继续使用现有单行转义；
- CLI 不根据 message 推断 stage、位置、suggestion 或 fix-it；
- FIX 只是展示，不自动改写 stdin、脚本或文件；
- 以上所有诊断行都写 stderr，不进入 stdout；结果按 StatementResult 顺序输出。

### 8.3 退出码

退出码保持：

- 0：参数、输入、所有真实执行、分析和 close 均成功；
- 1：任一脚本级、编译、执行、Storage、内部、输入输出或 close 错误；
- 2：参数错误。

`kAnalyzeRemaining` 中后续语句分析成功不能把退出码从 1 恢复为 0。`kAnalysisOnly` 本身不新增错误，但它必然出现在已有首错之后，因此整个调用仍失败。

`script_error` 一律使退出码为 1；`SKIPPED`、`ANALYZED`、`INDETERMINATE` 行本身不改变退出码，因为致命中止必然伴随 `script_error`。

### 8.4 批处理与 REPL

批处理读取整段文本并调用一次 Core。analyze 模式可以报告后续独立语句问题，但不会执行它们。

REPL 仍按一次提交调用一次 Core：本次提交首错后的语句受策略控制；下一次输入建立新的脚本执行门。结构化错误（`kCompileError`/`kExecutionError`/`kAnalysisError`）后继续读取下一行；任何 `script_error`（分句失败、语句数超限、致命中止）都按 REPL 致命处理：停止读取后续输入，best-effort close，退出码 1。第一轮不新增 Database 状态查询 API，也不尝试区分 Compiler 违约与会话失效；将来若需要“Compiler 违约后继续”，再引入机器可读的 `session_usable` 字段。整个 REPL 会话只要出现过任一错误，最终退出码仍为 1，沿用现有累计错误规则。

## 9. 测试与验收

### 9.1 Core 单元/组合测试

至少覆盖：

- stop 策略与当前首错即停行为完全一致；
- analyze 策略在编译错、执行错、部分写失败后继续编译但 Storage 调用计数不再增加；
- 首错后的 SELECT/INSERT/UPDATE/DELETE Plan 被销毁而不执行；
- 分析态 CREATE 使后续语句可编译，但运行时 Catalog、next_table_id 和 Storage 均不变；
- 分析态 CREATE 失败不消耗候选 TableId；
- 分析态 `kNoCatalogChange`/`kApplied` 记 `kAnalysisOnly`，只有 `kRejected` 记 `kAnalysisError`；SELECT 等非 DDL 不得被误报为分析失败；
- System Catalog V2 的保留 ID 不会被影子 Catalog 分配；
- 多条 CompileError 的 statement_index、绝对范围和顺序正确；
- fix-it 与主诊断跨行、UTF-8 字节偏移换算正确；
- Compiler 返回越界范围时安全转换为 internal error；
- 分句失败只由 `kMaxSqlBytes` 或分句契约违反触发；未闭合字符串/注释仍作为语句交给 compile；脚本级失败只返回 `script_error`，使用 `{1,1,0}-{1,1,0}` 空插入点；
- 语句数超过 4096 时 `statements` 为空、`script_error` 为 `kCompile`/`kLex`，Storage 调用计数保持 0；
- Compiler 异常、Storage 异常以及影子 Catalog 建立/同步失败都不泄漏 Plan/cursor；
- moved-from、未 open、cleanup-pending 状态沿用原契约。
- stop 策略下首错后的剩余语句全部以连续 index 记 `kSkippedExecution`，行数与分句结果一致；
- compile 抛异常 → 当前起全部 skipped；执行抛异常 → 当前 `kExecutionIndeterminate`、其后 skipped，两者都带 `script_error`；
- 执行器返回 `kInternal`：未调用 Storage 时当前起 skipped；已调用 Storage 或进入 cleanup-pending 时当前 `kExecutionIndeterminate`、其后 skipped；两种路径都不得构造语句级 `kExecutionError{kInternal}`；
- 影子建立失败 → 全部 skipped + `script_error`；同步失败 → 已完成语句保持 `kExecuted`，其余 skipped；
- 分析态候选 ID 超过 `UINT32_MAX` 时记 `kAnalysisError`，计数器不回绕、不窄化；
- CRLF、Tab、EOF 插入点和跨行范围的换算与端点校验正确。

fake Compiler 只返回预置的 split/compile 结果，不实现第二个 SQL 解析器；fake Storage 必须记录每种 API 的调用次数。Core 测试继续用 object/test 组合隔离真实模块，避免 fake/real 符号混用。
