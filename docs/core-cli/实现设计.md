# core 与 CLI 实现设计

本文只描述 core 与 CLI 的实现设计，不规定 compiler/storage 的内部方案。
compiler 与 storage 的公共接口以 [docs/消息契约详细设计.md](../消息契约详细设计.md) 和
`include/tinydbms/` 下的头文件为准。

## 1. 目标与边界

- 本分支实现 core 的 `Database` 对象、逻辑 Catalog、执行器与表达式求值，以及可执行入口。
- compiler 的 `split_statements/compile` 与 storage 的全部消息函数由对应模块负责人实现；
  core/CLI 只调用其公开 API，不进入其内部。当前 compiler 与 storage 均已有可链接实现。
- core 测试使用测试专用 fake compiler/storage；产品可执行入口链接真实 compiler/storage。
- 本分支用 fake 模块驱动的测试验证 core 运行逻辑，并保留真实 compiler + fake storage 的窄联调；
  产品级黑盒验证使用真实 compiler/storage 组成的完整链路，不把 fake 放进产品代码。
- 初版单进程、单线程、顺序执行；storage 为无句柄单例。

### 源文件组织

- `src/app/` 只负责命令行参数、stdin 输入、结果展示和退出码；当前已拆为 arguments、input、
  output、runner、terminal 与 Session 适配器，公共契约之外的头文件不安装到 `include/`。
- `src/core/database.cpp` 负责 `Database` 生命周期、进程级占用标记和 Catalog 恢复。
- `src/core/script.cpp` 负责 `execute_script` 的拆句、逐条编译执行、stop/analyze 状态机、
  跳过填充与脚本级错误聚合。
- `src/core/diagnostics.{hpp,cpp}` 负责 SourceRange 校验与语句相对范围到脚本绝对范围的换算，
  只供 core 内部使用，不安装到 `include/`。
- `src/core/analysis_catalog.{hpp,cpp}` 负责 analyze 策略的脚本局部影子 Catalog（仅模拟 CREATE TABLE），
  不调用 Storage、不写磁盘。
- `src/core/executor.cpp` 负责 Plan 分发与执行；表达式求值等内部能力按职责继续拆分，
  不集中回 `database.cpp`。
- `src/core/internal.hpp` 只供 core 自身共享实现细节，不安装，也不进入公共 `include/`。
- `include/tinydbms/` 只保留跨模块公共契约；测试通过 fake compiler/storage 调用公开 API，
  不在公共头文件增加测试 friend 或测试入口。

## 2. Database 生命周期

core 对外只暴露 `tinydbms::core::Database`，内部状态放在 Pimpl 的 `Database::Impl` 中。

| 状态 | 进入方式 | 可用操作 |
|---|---|---|
| unopened | 默认构造后；open 失败且清理完成后；close 成功或 cleanup-pending 重试完成后 | open |
| open | Database::open 成功 | execute_script、close |
| cleanup-pending | close_storage 返回错误或抛异常后，core 已使会话失效并保留清理重试 | close；execute_script 返回 script_error{kExecute}，不调用 compiler/storage |
| moved-from | Database 被移动后 | 公开方法均返回 `ErrorKind::kExecute`；析构安全 |

生命周期约定：

- `Database::open` 失败时不进入 open 状态；若失败发生在 storage 已打开之后，
  core 先调用 `close_storage` 清理再返回 Error；清理错误不覆盖主错误。
  清理正常完成时释放已经获取的进程级占用标记；若 close_storage 返回错误或抛异常，
  则保留 cleanup-pending 直到后续重试或析构兜底结束。
- `Database::close` 返回 Result 错误后对象同样离开 open 状态，但进入 cleanup-pending，不能重新 open。
  BufferPool 关闭失败可使 storage 恢复 Open，文件/metadata 收尾失败则保持 Closing；两类错误都必须由
  原 owner 重试 `close()`。清理成功或重试返回 `kInvalidRequest` 后才释放占用标记。
- compiler/storage 公开调用意外抛异常时，core 先 best-effort 调用 `close_storage`，清空
  Catalog 并进入 cleanup-pending；该路径不能回滚已经产生的 CREATE/INSERT/DELETE 部分副作用。
  当前执行返回 `ErrorKind::kInternal`，后续必须先调用一次 `close` 消费清理状态，才能再次 open；
  再次 open 会从 storage 重新恢复 Catalog。
- 析构时若仍处于 open 状态，或上一次清理调用抛异常需要重试，core 以 noexcept 做 best-effort
  `close_storage`；关闭错误无法报告，析构不抛出。清理调用重试若返回 `kInvalidRequest`，按
  storage 已经结束生命周期处理。
- 同一进程同一时间只允许一个 Database 处于 open 或待清理重试状态；
  core 内部维护进程级占用标记。只有 close 完整成功或 cleanup-pending 重试完成后释放标记；
  析构兜底结束时也必须释放标记。待清理期间第二个 open 直接返回 Error，不调用 storage。
- 非法生命周期调用统一返回 `ErrorKind::kExecute`：
  open 时重复 open、unopened 时 close、moved-from 上调用公开方法都按该错误处理；
  unopened 或 cleanup-pending 时 execute_script 返回只含 `script_error{kExecute}` 的
  ExecuteScriptResult，statements 为空，且不调用 compiler/storage。
- Database 移动只转移 `Impl` 所有权；moved-from 的 `Impl` 为空，析构安全。
- 移动赋值若发生在目标仍 open 或有清理重试状态时，先 best-effort `close_storage` 再转移所有权；
  storage 单例占用标记随新 Impl 的状态更新。若清理调用返回错误或抛异常，目标保留待清理 Impl，
  不转移源对象，避免丢失重试句柄。
- compiler/storage 的普通失败通过 Result 返回；若其实现意外抛出异常，core 的公开方法不得让异常越过边界，
  普通调用转换为 `ErrorKind::kInternal`。若 open/close 的清理调用本身抛异常，实例保留 cleanup-pending
  与一次重试标记；析构和移动赋值的 best-effort 清理捕获异常并继续保证 noexcept。

## 3. Database::Impl 与 Catalog

```cpp
struct Database::Impl {
    std::vector<TableMeta> catalog;      // 逻辑 Catalog；顺序以 list_tables/建表顺序为准，core 不依赖排序
    std::uint64_t next_table_id = 0;     // 内部用 64 位避免先溢出再判断
    bool open = false;
    bool forced_close_pending = false;
    bool cleanup_retry_needed = false;
    // 当前 Plan 是否已经调用过 Storage；只用于把执行器 kInternal 区分为
    // kExecutionIndeterminate 或 kSkippedExecution，不进入公共头文件
    bool current_plan_storage_called = false;
};
```

Catalog 规则：

- `catalog` 是唯一的逻辑元数据来源；compiler 编译时通过 `CatalogView{catalog}` 借用。
- Catalog 不排序，表名/ID 查找使用线性查找；初版表数量少，不引入索引结构。
- open 成功后由 `list_tables` 重建 catalog，并令
  `next_table_id = max(table_id) + 1`（V2 空库已含 system TableId 0/1，首个用户 ID 为 2）；
  `uint64_t` 计算天然覆盖 `max == UINT32_MAX` 的情况。
- core 恢复 Catalog 时校验表名/列名符合 `[a-z][a-z0-9_]*` 且长度为 1..64、每张表至少有一列、
  列名不重复，且列类型只能是 `Type::kInt` 或 `Type::kVarchar`；storage 返回其他结构时按
  `ErrorKind::kInternal` 中止 open，先关闭 storage 并清空半成品状态。CREATE TABLE 也在调用
  storage 前执行同一结构校验；SQL 的大小写折叠由 compiler 完成，core/storage 对规范化后的
  小写名称做精确比较。
- 分配 TableId 时若 `next_table_id > UINT32_MAX`，CREATE TABLE 返回
  `ErrorKind::kExecute`，不回绕。
- CREATE TABLE 使用候选 ID：先读取 `next_table_id`，调用 storage 的 `create_table`；
  storage 失败时不更新 catalog，也不递增 `next_table_id`，候选 ID 可复用；
  storage 成功后才追加新 `TableMeta`，并将 `next_table_id` 更新为候选 ID + 1。

## 4. execute_script 主循环

```text
execute_script(request)
  -> 未 open、moved-from 或 cleanup-pending：statements 空 + script_error{kExecute}，不调用模块
  -> split_statements(request.text)
       分句失败 -> statements 空 + script_error{kCompile}，空插入点，不编译
  -> 校验每条 statement.source 与 sql 一致；语句数 > kMaxStatementsPerScript
       -> statements 空 + script_error{kCompile/kLex}，空插入点，不调用 Storage
  -> analyze 时先复制运行时 Catalog 与 64 位 next_table_id 建立影子 Catalog
  -> 对每条 SplitStatement（statement_index 从 0 连续）：
       compile(sql, CatalogView{执行门打开 ? 运行时 catalog : 影子 catalog})
       编译失败 -> kCompileError（脚本绝对范围）+ 关闭执行门
       编译成功且执行门打开 -> execute_plan_impl(plan)
           -> kExecuted；INSERT/DELETE 部分成功 -> kExecutionError
           -> 执行器返回 kInternal：按是否可能已产生副作用记 indeterminate/skipped + script_error
       编译成功但执行门已关闭 -> 影子 Catalog 模拟：
           kApplied / kNoCatalogChange -> kAnalysisOnly；kRejected -> kAnalysisError
       DDL 真实执行成功后更新运行时 Catalog；analyze 下再把影子副本同步到运行时 Catalog
  -> 返回 script_error 与 statements（分句成功后覆盖全部语句，index 连续）
```

规则：

- 不整段预编译；DDL 成功执行后立即更新 catalog，再处理下一条。
- 编译错误范围相对单条语句，由 core 结合 `SplitStatement.source` 换算成脚本绝对范围；
  fix-it 与主诊断共用同一套换算，任一侧非法都按 `kInternal` 致命中止。
- stop 策略在首错后立即把剩余语句全部记 `kSkippedExecution` 并返回；
  analyze 策略继续编译，但执行门永久关闭，后续语句不再执行、不再产生 Storage 调用。
- 致命中止（Compiler/Storage 违约、影子建立或同步失败、结果聚合失败）统一填
  `script_error{kInternal}` 并结束本次脚本；可能已产生副作用时当前语句记
  `kExecutionIndeterminate`，否则从当前语句起全部记 `kSkippedExecution`。
- 空文本或纯完整注释返回空 statements 且无 script_error。

## 5. 执行器组织

执行器按 Plan 的四种顶层类型分发：

| Plan | core 行为 |
|---|---|
| CreateTablePlan | 分配 TableId，调用 create_table；成功后追加 Catalog，返回 CommandResult |
| InsertPlan | 预校验列清单和行值，重排成建表列序全行，调用 insert；部分失败返回携带 error 的 CommandResult |
| DeletePlan | 预校验表和谓词后扫描收集命中 RecordId；扫描/求值/close 失败时不执行删除；部分失败同上 |
| QueryPlan | 预校验算子树/谓词/列头后 open_table + scan_next，经过 Filter/Project 后 close，返回 QueryResult |

SELECT 内部流程：

```text
预校验 QueryPlan/Expr/Catalog -> 生成结果列头 -> open_table -> 循环 scan_next
  storage Record -> core Row
  Filter：对 Row 求值 WHERE，不命中丢弃
  Project：按 outputs 选择列
close_cursor（调用前标记，异常也不重试）
成功 -> 组装 QueryResult
扫描错误 -> 丢弃已收集行，返回 Error
扫描正常但 close_cursor 失败 -> 丢弃已收集行，返回 close 错误
```

DELETE 内部流程：

```text
预校验 DeletePlan/Expr/Catalog -> open_table -> 循环 scan_next
  storage Record -> core Row
  Filter：对 Row 求值 WHERE，命中则收集 RecordId
扫描错误 -> 调用 close_cursor 清理，返回扫描错误（不执行删除）
扫描正常但 close_cursor 失败 -> 不执行删除，返回 close 错误
close_cursor 成功 -> delete_records(收集到的 RecordId)
delete_records 部分失败 -> CommandResult（deleted_count + error）
```

没有命中行时收集到的 RecordId 为空，仍调用 `delete_records` 并按成功的零行删除处理。

表达式求值：

- 求值器是 core 内部实现，不放公共头文件，不跨模块；
- 初版只处理 ColumnRef、Literal、比较、AND/OR/NOT；
- 在调用 storage 前先校验表达式结构、ColumnId 和静态类型；Filter/Delete 顶层必须为 BOOL，
  因此空表也不能掩盖非法表达式；
- 比较与逻辑运算的结果是内部 BOOL，不进入 `Value`；
- AND/OR 先求值两侧再运算，不采用短路；
- 表达式校验和求值的递归深度上限为 `256`；超过上限返回 `ErrorKind::kInternal`，不打开
  cursor。该限制保护 core 遍历调用栈，不改变合法浅层表达式的结果；
- 运行时发现 Plan 类型与行值不匹配时按 core 内部错误返回，不让未定义行为外溢；
- `FilterNode/ProjectNode.child` 与 `QueryPlan.root` 非空是 compiler 生成 Plan 的前置条件；
  执行器在解引用前校验，发现空节点返回 `ErrorKind::kInternal`，不调用 storage。
- 初版合法 `QueryPlan` 必须且只能包含一个 `SeqScanNode`；core 通过它取得查询表的 `TableId`，
  并据此解析输出列名。合法树只允许 `SeqScan`、`Filter -> SeqScan`、`Project -> SeqScan`、
  `Project -> Filter -> SeqScan`；零个或多个扫描节点、空 outputs 或其他拓扑均视为内部错误。

## 6. CLI 形态

### 参数

- `--help`、`--version`：打印后退出。
- `--data-dir <DIR>`：UTF-8 编码的数据库目录，最多出现一次；缺少参数或空字符串均为参数错误；
  未提供时补为 `./tinydbms-data`。
- `--error-policy stop|analyze`：脚本错误策略，最多出现一次；缺值、未知值或重复出现均为参数错误；
  未提供时补为 `stop`。
- 未知参数：打印错误与 help，退出码 2。
- `--help`、`--version` 与其他参数混用也视为参数错误，退出码 2。

### 输入模式

- stdin 是交互终端：REPL。按行提交，一行可含多条完整语句；跨行 SQL 初版不支持。
- stdin 非交互：读取整段文本，执行一次 execute_script。
- REPL 以 EOF 退出；Unix 通常 Ctrl-D，Windows 通常 Ctrl-Z 后回车。

### 生命周期与展示

- main 创建 app 私有 Session；真实 `CoreSession` 在参数解析成功后、open 调用时惰性创建
  `Database`，open 成功后才进入读入循环；退出前 close。
- open/close 失败打印错误并返回非零退出码。
- 逐条展示 statements：`kExecuted` 的 QueryResult 显示列名与行值、CommandResult 显示受影响行数；
  诊断、suggestion、fix-it、`ANALYZED`、`SKIPPED`、`INDETERMINATE` 与 `script_error` 全部写入
  stderr；`script_error` 插在首条 `kSkippedExecution` 之前，批处理与 REPL 使用同一展示器。
- 结果采用稳定的 TSV/`OK <affected_rows>` 格式，转义和错误行格式见
  [第三阶段 CLI 与入口设计](第三阶段CLI与入口设计.md)。

### 退出码与错误继续策略

- 退出码 `0` 表示整个入口流程成功；退出码 `1` 表示 open/close、SQL 编译/执行、storage 或输入输出错误；
  退出码 `2` 仅表示命令行参数错误。
- 非交互批处理：默认在首错后停止剩余语句；`analyze` 策略下 core 继续静态分析但不执行。
  入口展示已返回的结果，close 完成后返回 `1`。
- 交互 REPL：单行出现结构化错误（编译/执行/分析）时展示错误并继续读取下一行；
  出现任何 `script_error` 时按致命处理，停止读取后续输入并 best-effort close。入口记录错误标记，
  EOF 或停止后执行 close，期间发生过任何 SQL/运行时错误或 close 失败则返回 `1`。
- stdin 读取错误（非 EOF）返回 `1`；参数解析错误不创建或打开 Database。

### 跨平台路径

- Linux 直接使用 UTF-8 `std::string`。
- Windows 入口把宽字符参数转换成 UTF-8 后传给 core，storage 内部负责转回原生路径。

## 7. 错误映射

| 来源 | core Error |
|---|---|
| CompileError | ErrorKind::kCompile + CompileStage + 脚本绝对 SourceRange + 可选 suggestion/fix-it |
| 影子 Catalog 明确拒绝 | ErrorKind::kAnalysis + 脚本绝对 SourceRange |
| StorageError | ErrorKind::kStorage + storage 消息（不携带 StorageErrorKind 字段） |
| core 生命周期/ID 耗尽等执行失败 | ErrorKind::kExecute |
| 致命中止（模块违约、内部不变量、影子建立/同步失败） | script_error{ErrorKind::kInternal}，不构造语句级 kExecutionError{kInternal} |

core API 保留上述高层 ErrorKind，并在 `Error` 中携带 `CompileStage` 使词法/语法/语义保持机器可读；
仍不携带 `StorageErrorKind` 字段。转换时必须保留源错误的可读消息，调用方不得依赖消息文本判断
细分类别。若未来需要稳定区分 Storage 细分类别，应作为一次单独的公共契约扩展。

## 8. 测试策略

- 保留现有 `tinydbms.contracts_compile` 作为契约回归测试。
- 新增 fake compiler/storage，只放在 `tests/fakes/`，不进入产品代码。
- fake compiler 不做真实 SQL 解析：只提供极简 split_statements 与预置 CompileResult 队列；
  测试通过公开 `Database::execute_script` 驱动预构造 Plan，避免 fake 变成第二个 parser。
- fake compiler 支持 split/compile 异常注入、split 结果覆盖与 Catalog TableId 快照，
  用于覆盖致命中止与影子 Catalog 的候选 ID 断言；fake storage 必须记录每类 API 的调用次数。
- `tinydbms.core_script_policy` 覆盖 stop/analyze 状态机、影子 Catalog（拒绝、保留 ID、
  ID 耗尽不回绕、失败不消耗候选 ID）、致命中止、4096 语句上限、CRLF/UTF-8/跨行范围换算与
  fix-it 绝对换算。
- 影子 Catalog 建立/同步失败的 bad_alloc 路径没有可靠的注入接缝（不修改生产代码无法稳定触发），
  该路径保留代码审查证据，不作为自动化用例；其余清单项必须有自动化断言。
- 生产路径抽出内部 `Database::Impl::execute_plan_impl(compiler::Plan)`；
  该实现只由 `Database::execute_script` 调用，不向公共头文件暴露测试入口。
- core 行为测试直接组合 `tinydbms_core_objects` + fake 实现，不链接真实 compiler/storage；
  产品入口显式链接 `tinydbms_core`、真实 compiler 和真实 storage，测试与产品组合点相互隔离。
- CLI runner 测试通过 app 私有 `FakeSession` 注入结构化 core 结果；真实 compiler + fake storage
  的联调目标覆盖 `CoreSession`、core 脚本主循环和 CLI 展示。真实 storage 已可参与产品级黑盒联调。
- fake storage 维护测试进程内的单例状态，并提供 reset 供每个用例隔离。
- 每个用例使用临时 data_dir；测试结束清理。
- 先测 Database 生命周期，再测 execute_script 主循环与四种 Plan，最后测表达式求值。

## 9. 实施顺序

1. Database::Impl、内部 `execute_plan_impl` 与进程级占用标记；
2. 最小 fake storage（open/close/list_tables/reset）与生命周期测试；
3. open/close 的 Catalog 恢复与 TableId 分配；
4. 最小 fake compiler（split/compile）与 execute_script 主循环、错误换算；
5. 四个执行器与 INSERT/DELETE 部分失败路径；
6. Row 求值与 SELECT 管线；
