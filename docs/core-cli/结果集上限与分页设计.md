# CLI 升级设计：结果集上限可配置与分页边界

状态：**第一阶段已实现**（2026-09-15）。对应 [升级路线图](../升级路线图.md) 的 U4。
实现位置：`include/tinydbms/core.hpp`（请求字段）、`src/core/script.cpp`（请求校验与透传）、
`src/core/executor.cpp`（两个物化点）、`src/app/arguments.{hpp,cpp}`（`--max-rows`）、
`src/app/runner.cpp`（`ExecutionOptions` 统一透传）。

本文只覆盖第一阶段：**上限可配置 + 超限提示**。真分页与流式结果不在本轮，边界见第 6 节。

## 1. 背景与范围

目标：`kMaxQueryRows` 目前是编译期常量，用户无法按自己的场景调整；超限错误只说"超了"，
不告诉用户当前上限是多少、可以怎么处理。本项把上限变成请求级配置，并让超限错误可操作。

包含：

- `ExecuteScriptRequest` 增加 `max_query_rows`；
- 超限错误消息带当前上限数值，并给出 `suggestion`；
- CLI 增加 `--max-rows N`；
- 测试与验收。

不包含：

- 真分页（需要 SQL 层 LIMIT/OFFSET 或重放式游标，见第 6 节）；
- 流式结果（会改 `QueryResult` 的公共形状）；
- 导出功能（`--format json` 配合 shell 重定向已覆盖，不新增代码）；
- GUI 暴露该配置（GUI 走 core 模式可直接复用，但不在本轮范围）。

## 2. 现状基线

| 位置 | 现状 |
| --- | --- |
| `include/tinydbms/core.hpp` | `kMaxQueryRows = std::size_t{1} << 18`（262144），编译期常量 |
| `src/core/executor.cpp`（SeqScan 收集） | 超限返回 `kExecute`，消息固定 `query materialization exceeds the maximum row count`，不带数值 |
| `src/core/executor.cpp`（Join 收集） | 同上，消息为 `join materialization exceeds the maximum row count` |
| `src/core/script.cpp` | `execute_script` 只校验 moved-from 与未打开，两者都返回 script_error + `ErrorKind::kExecute` |
| `docs/SQLv2扩展契约.md` §7.3 | 已声明上限语义：按物化节点计数、超限不使会话失效、不产生 script_error |
| `src/app/arguments.cpp` | 参数缺值、空值、未知值、重复出现均按参数错误处理（退出码 2） |

现状语义在本轮保持不变：DELETE/UPDATE 只收集 RecordId，不受上限约束；上限按语句独立计数；
`--plan` 不进入执行器，因此不受上限约束。

上限按**物化节点**而不是最终结果计：`WHERE` 过滤发生在扫描节点物化之后，所以
`SELECT ... WHERE id = 2` 在大表上同样会因扫描行数超限而失败。这是第一阶段有意的语义
（它保护的是内存占用），已写入验收与真实链路测试；若将来做谓词下推或分页，需要重新评估。

## 3. 请求级配置

```cpp
struct ExecuteScriptRequest {
    std::string text;
    ScriptErrorPolicy error_policy{ScriptErrorPolicy::kStopOnFirstError};
    ExecutionMode mode{ExecutionMode::kExecute};
    // 单条语句在内存中物化的最大行数；必须 >= 1，默认值保持现行行为。
    std::size_t max_query_rows{kMaxQueryRows};
};
```

规则：

- 字段放在末尾，现有聚合初始化（`ExecuteScriptRequest{text}`、`{text, policy}`、
  `{text, policy, mode}`）继续编译，默认行为不变。
- `kMaxQueryRows` 常量保留，作为默认值来源与契约测试的锚点；运行期不再直接读取该常量，
  两个物化点改为读取请求字段。
- 不提供"无上限"取值：上限的职责是防止内存无界增长，去掉它等于放弃护栏。
- `max_query_rows == 0` 是调用方违约，不静默回退到默认值：core 返回 script_error +
  `ErrorKind::kExecute`，消息 `max_query_rows must be at least 1`，且不执行任何语句。
- 上限随请求传递，core 不保存会话级配置；同一 Database 的多次调用可以使用不同上限。
- 上限只影响物化行数检查，不改变 Plan 结构、结果内容与错误种类。

实现方式（不属于公共契约）：`Database::Impl::execute_plan_impl` 增加一个上限参数，由
`execute_script` 从请求透传；不使用会话字段保存请求级配置。

## 4. 超限行为与提示

- 错误种类保持 `ErrorKind::kExecute`（语句级）：不使会话失效、不产生 script_error，
  后续语句按错误策略处理。
- 消息带当前上限数值，替换现有的固定文案：
  - `query materialization exceeds the maximum row count (limit 262144)`
  - `join materialization exceeds the maximum row count (limit 262144)`
- 新增 `suggestion`：`raise max_query_rows or narrow the query`。
- 错误范围保持语句范围，与其他执行错误一致。
- CLI 展示沿用现有通道，不新增 schema：table 格式输出 `ERROR execute <range> <message>`
  与 `SUGGESTION ...` 行；JSON 格式输出 `message` 与 `suggestion` 字段。

分层约束：core 的 `suggestion` 只描述语义层动作（提高上限或收窄查询），不写 CLI 参数名；
`--max-rows` 与超限错误的对应关系写在帮助文本与本文档里，避免入口实现按 message 文本做
特殊匹配。

## 5. CLI 参数

新增 `--max-rows N`：

- 最多出现一次；缺值、空值、非十进制数字、带正负号、尾随字符、`0`、超出 `size_t`
  均按参数错误处理（退出码 2、纯文本提示），与现有参数错误规则一致。
- 解析使用 `std::from_chars`，只接受 `1 .. SIZE_MAX` 的十进制整数。
- 未提供时不改变默认值；`--help` 文本增加一行，说明默认值与用途。
- 与 `--plan` 组合时该参数不生效（计划模式不进入执行器），但不报错。

示例：

```text
$ tinydbms --data-dir ./db --max-rows 10
ERROR execute 1:1-1:49 query materialization exceeds the maximum row count (limit 10)
SUGGESTION raise max_query_rows or narrow the query
```

## 6. 与分页、导出的关系

- **导出**：`--format json` 的输出可以直接被 shell 重定向保存，本项不新增导出了命令或参数。
- **真分页**有两条路线，都需要单独设计，本轮不做：
  1. SQL 层 LIMIT/OFFSET：需要 compiler 新增语法与计划节点，语义清晰但要拉 compiler 联合设计；
  2. 重放式游标：core 保存扫描进度，但 storage 的 cursor 不跨语句存活，需要新的会话状态与失效规则，
     成本与风险都更高。
- 启动第二阶段前需要一次决策：选路线，以及是否要求分页结果的稳定顺序。本文只登记边界。

## 7. 测试设计

core：

- 默认值：不传新字段时行为与现状一致（现有执行与集成测试即回归）；
- 生效：上限设为 1 时，两行的 SeqScan 与 Join 都返回超限错误；
- 消息：`message` 含当前上限数值，`suggestion` 存在；
- 0 值：返回 script_error + `kExecute`，且不执行任何语句（Storage 调用计数为 0）；
- 不受限路径：DELETE/UPDATE 与计划模式在极小上限下仍正常工作；
- 独立计数：同一脚本中两条各占一半上限的查询都能成功。

CLI：

- `--max-rows` 的缺值、空值、非数字、`0`、溢出、重复六类参数错误；
- 透传：FakeSession 断言请求字段等于参数值，未提供时等于默认值；
- 展示：table 与 JSON 两种格式下的超限错误（含 suggestion 行与字段）；
- `--help` 文本包含新选项。

真实链路：小上限加真实 storage 的多行表，确认超限错误、退出码 1、会话仍可用（后续语句正常执行）、
数据文件未被修改。

## 8. 实施顺序与验收

1. `include/tinydbms/core.hpp` 增加字段；
2. `src/core/script.cpp` 校验 0 值并透传上限；
3. `src/core/executor.cpp` 两个物化点改用请求上限，消息带数值并补 `suggestion`；
4. `src/app/arguments.{hpp,cpp}` 增加 `--max-rows` 与 help 文本，`runner.cpp` 透传；
5. 补 core、CLI 与真实链路测试；
6. 同步文档：消息契约详细设计、SQLv2扩展契约 §7.3、第三阶段 CLI 与入口设计、README、升级路线图。

验收标准：

- 不提供 `--max-rows` 时默认行为与现状一致；唯一有意的输出变化是超限消息新增 `(limit 262144)`
  后缀与 `suggestion`（已核实现有测试没有断言旧文案）；
- 提供后上限真实生效，超限错误包含数值与 suggestion；
- 退出码、错误策略、会话可用性与现有语义一致；
- 真实链路验证数据未被修改。
