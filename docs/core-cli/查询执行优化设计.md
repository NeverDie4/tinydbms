# Core 执行器优化设计（收尾阶段）

状态：**第一阶段已实现**（2026-09-16）。
实现位置：`src/core/executor.cpp`（连接与聚合的执行路径）。
契约影响：无。`include/tinydbms/compiler.hpp`、`include/tinydbms/core.hpp`、
`include/tinydbms/storage.hpp` 与 `docs/消息契约详细设计.md` 均未改动。

## 1. 范围

本轮只做“不改变任何外部契约、不需要其他模块配合”的执行器优化：

| 编号 | 优化 | 归属 | 依赖 |
| --- | --- | --- | --- |
| A1 | 连接行合并去掉二次开销 | core 内部 | 无 |
| A2 | 等值连接哈希化 | core 内部 | 无 |
| A3 | 聚合分组哈希化 | core 内部 | 无 |

不在本轮范围（见 §5）：谓词下推、列裁剪、索引扫描、并行执行。

## 2. 现状基线

执行器把每个算子的输出物化成 `std::vector<expression::SlotRow>`，`SlotRow` 是
`std::vector<SlotValue{SlotId, Value}>`：

| 位置 | 现状 | 代价 |
| --- | --- | --- |
| `SeqScanNode` | 每行 `materialize_slot_row`（列映射 + 校验） | O(列数)/行，已 reserve |
| `FilterNode` | 逐行求值 `evaluate_predicate` | O(行数 × 表达式规模) |
| `JoinNode` | 双重循环：每对行 `merge_slot_rows` → 求值完整谓词 | 每对 O((n+m)²) 拷贝与查重 + 谓词求值 |
| `SortNode` | 预取排序键 + `std::sort` | O(n log n) |
| `AggregateNode` | 每行 `std::find_if` 线性找组 | O(行数 × 组数) |
| `ProjectNode` | 计划校验阶段解析成输出 slot 列表，执行时仅投影 | O(输出列数)/行 |

`merge_slot_rows` 的查重是主要浪费：它对每个右行 slot 调一次 `lookup_slot`，
而 `lookup_slot` 线性扫描已合并的行。两行 n 列、m 列时每次合并是 O((n+m)²)，
连接本身又是双重循环，合计 O(N×M×(n+m)²)。

## 3. A1 + A2：连接

### 3.1 行合并去二次开销

`validate_dataflow_node` 在计划校验阶段已经用 `merge_slot_rows` 检查过“左右输入
slot 集合不相交”，执行期不需要对每一对行重复查重：

1. 执行期先用 O(n+m) 的集合检查确认一次左右 slot 不相交（不满足时按既有语义返回
   `kInternal`，消息 `join inputs contain duplicate slot bindings`）；
2. 之后所有行合并退化成线性拼接（`reserve` + 两段 `insert`），`merge_slot_rows`
   只保留在校验路径。

### 3.2 等值连接哈希化

连接条件是任意 `Expr`，哈希化必须保证**语义不变**，因此采用“候选集 + 完整谓词复核”：

1. 只用连接条件中可以证明安全的等值合取项建键：从 `AND` 链上收集
   `ColumnRef = ColumnRef` 且一侧属于左输入、另一侧属于右输入的项；
2. 只有两侧 slot 的**值类别完全相同**（INT/BIGINT/DOUBLE/VARCHAR/BOOLEAN，且不是 NULL）
   才可作为键，依据是比较语义：
   - `INT = INT`、`BIGINT = BIGINT`、`VARCHAR = VARCHAR`、`BOOLEAN = BOOLEAN`
     的 `compare_*` 就是精确相等，键相等是谓词为真的必要条件；
   - `DOUBLE = DOUBLE` 用 `==`，键做 `-0.0 → 0.0` 归一（`0.0 == -0.0` 为真），
     NaN 不参与匹配（谓词同样为假）；
   - INT 与 DOUBLE/BIGINT 混用的等值比较会发生数值提升（例如
     `BIGINT 2^53+1 = DOUBLE 2^53` 为真），精确键会漏配，因此**整条等值项不参与建键**，
     退回嵌套循环。
3. 任意一侧键值为 NULL 的行不参与匹配：谓词在这种组合下是 UNKNOWN，与嵌套循环一致；
4. 命中候选后仍然对合并行求值完整连接条件，因此条件里的非等值项（`AND` 的其余合取项、
   `OR`、`NOT`、`IS NULL` 等）逐条生效；
5. 无法提取任何安全等值项（例如 `a.x < b.y`、混合类型等值）时退回原嵌套循环。
6. 键的值类别来自 `ValidatedQuery::slot_types`，它是**整棵计划**的 slot → 声明类型绑定
   （slot 由 SeqScan 与 Aggregate 引入，Filter/Sort/Join 只透传）。连接经常被
   Aggregate/Filter/Sort 包在中间，若只收集顶层输入行的 slot，内层连接键会查不到类型，
   哈希候选就静默退化成嵌套循环（结果正确、代价回到 O(N×M)），因此校验阶段必须累积
   遍历到的所有节点。

顺序保证：哈希表按右行下标升序追加，外层按左行顺序推进，输出顺序与嵌套循环一一对应
（`(左0,右0)`、`(左0,右1)`、…），不引入 SQL 层可见的顺序变化。

取消与上限：

- 取消检查点保留在左行循环与候选内层循环；
- `max_query_rows` 仍是“物化结果上限”，超限返回既有 `kExecute` 错误与 suggestion。

### 3.3 复杂度

设左 N 行、右 M 行、键 k 列：

- 旧：O(N×M) 次合并（每次 O((n+m)²)）+ O(N×M) 次谓词求值；
- 新：O(M) 建表 + O(N) 探测 + O(匹配对数) 次线性拼接 + O(匹配对数) 次谓词求值。

## 4. A3：聚合分组

分组键是 `std::vector<Value>`，语义是现有的 `grouping_value_equal`（变体下标 + 值相等，
NULL 与 NULL 同组，NaN 与 NaN 不同组）。改动：

- 保留 `std::vector<AggregateGroup> groups` 作为输出顺序来源（首次出现顺序，与改动前一致）；
- 新增 `std::unordered_map<std::vector<Value>, std::size_t, ValueKeyHash, ValueKeyEqual>`
  做键到组下标的索引；
- 哈希与相等必须与分组语义一致：按变体下标区分（`int32 1`、`int64 1`、`double 1.0`
  是三个键），`double` 做 `-0.0 → 0.0` 归一（`==` 认为两者相等），
  NaN 因相等判定为假而各自成组；
- 无分组键（全局聚合）时保持单组快路径。

复杂度：期望 O(行数 × 分组键数) 时间，替代 O(行数 × 组数)。

## 5. 未做的部分与阻塞

| 优化 | 结论 | 阻塞原因 |
| --- | --- | --- |
| 谓词下推（Filter 推到 Join/Scan 之下） | 未做 | 计划由 compiler 产出、core 只读；要下推得在 core 内重写 Plan 树（SlotId 稳定性、可下推判定、`OR`/NULL 语义），且收益与 A2 高度重叠——等值连接已经消掉主要代价 |
| 列裁剪 | 未做 | `SeqScanNode::columns` 已做列映射，但 `validate_scan_columns` 要求映射覆盖整表 schema，物理记录 `Record::values` 也是整行读；真正的裁剪需要 storage 提供按列读取 |
| 索引 / 范围扫描 | 未做 | `include/tinydbms/storage.hpp` 没有索引接口，core 无法表达“按 key 取行” |
| 向量化 / 批式求值 | 未做 | 需要重写 `expression` 求值接口，收益集中在大表扫描，超出收尾阶段范围 |
| 并行执行 | 未做 | 与 [进程内并发设计](进程内并发设计.md) 的单线程口径冲突：core 只承诺调用级互斥，不承诺并行度 |

上面三项阻塞项都需要 storage 或 compiler 配合，已登记到 [升级路线图](../升级路线图.md) 的 P 系列。

## 7. 实测记录

测量方式：同一台机器、同一天、g++ Release 构建、`TINYDBMS_ENABLE_REAL_MODULES=ON`。
基线是压缩包式的 `git archive HEAD`（本轮改动前的提交）另建目录编译出的可执行文件，
被测程序用同样的数据目录、同样的 SQL 反复运行 5–7 次取中位数；数字仅代表本机相对关系，
不是性能承诺。

### 7.1 等值连接（800 × 800 行，输出 800 行）

```sql
SELECT a.id, a.v, b.w FROM a INNER JOIN b ON a.id = b.id;
```

| 版本 | 中位数 | 最小值 |
| --- | --- | --- |
| 改动前（嵌套循环 + 逐对 merge_slot_rows） | 82.55 ms | 64.02 ms |
| 改动后（线性拼接 + 哈希候选） | 5.46 ms | 4.93 ms |

入口内部计时（`--time`，只含 `execute_script`）在同一工作负载上给出 5.16 ms，
与进程级中位数一致，说明差异来自执行器而不是启动开销。

### 7.2 分组聚合

```sql
SELECT k, COUNT(*) FROM g GROUP BY k;
```

| 工作负载 | 改动前 | 改动后 |
| --- | --- | --- |
| 3000 行 / 1556 组 | 12.01 ms | 8.71 ms |
| 5000 行 / 5000 组（两两不同） | 45.28 ms | 14.49 ms |

分组数越多，线性找组的代价越接近 O(行数 × 组数)，哈希索引的收益越明显；
分组数很少时收益有限，因为每行仍有键构造与聚合累加的固定成本。

### 7.3 回归

`build/debug`（占位模块）62/62、`build/mergecheck`（真实模块 + GUI）66/66、
ASan+UBSan（真实模块）65/65、TSan 62/62 全部通过；新增等价性用例见
`tests/core_executor_test.cpp` 的 `test_hash_join_and_group_paths_preserve_semantics`。

### 7.4 提交前审查发现的退化路径（已修复）

初版实现的 `slot_types` 只记录查询**顶层输入节点**的输出 slot。于是连接一旦被
Aggregate/Filter/Sort 包在中间（`SELECT COUNT(*) FROM a INNER JOIN b ON a.id = b.id`），
连接键在类型表里查不到，`key_plan.usable()` 为假，**静默退回嵌套循环**：结果正确，
优化形同失效。修复方式是让 `validate_dataflow_node` 沿途累积整棵计划的 slot 绑定。

同一台机器、同一份数据（两侧各 800 行、`--time` 单次调用、多次运行取中位数）：

| 查询形态 | 修复前 | 修复后 |
| --- | --- | --- |
| `SELECT a.id FROM a INNER JOIN b ON a.id = b.id` | 4.5–6.2 ms（本来就命中哈希路径） | 6.15 ms |
| `SELECT COUNT(*) FROM a INNER JOIN b ON a.id = b.id` | 42.6 ms | 6.23 ms |
| `SELECT SUM(a.id) FROM a INNER JOIN b ON a.id = b.id` | 33.5 ms | 6.09 ms |

修复后的规模关系（`COUNT(*)`，同一数据目录，两侧行数递增）：

| 两侧行数 | 修复前 | 修复后 |
| --- | --- | --- |
| 200 × 200 | 3.31 ms | 1.14 ms |
| 400 × 400 | 12.04 ms | 2.89 ms |
| 800 × 800 | 42.6 ms | 6.23 ms |

修复后每翻一倍约 ×2（线性增长），修复前每翻一倍约 ×3.5（接近二次），与"哈希候选已生效"
一致。回归覆盖：`test_hash_join_and_group_paths_preserve_semantics` 增加"聚合包在连接之上"
的 `COUNT(*)` 与 `GROUP BY` 用例；用例锁的是语义与计划组合，代价差异由本节数据佐证，
单元测试不对时间做断言。
