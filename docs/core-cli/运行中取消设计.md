# CLI 升级设计：运行中取消

状态：**第一阶段已实现**（2026-09-15）。对应 [升级路线图](../升级路线图.md) 的 U5。
实现位置：`include/tinydbms/core.hpp`（`CancelToken`、请求字段、`kCancelled`）、
`src/core/internal.hpp`（`PlanExecutionResult` 与内部取消信号）、`src/core/script.cpp`
（语句边界检查与状态填充）、`src/core/executor.cpp`（执行检查点）、
`src/app/main.cpp` 与 `src/app/runner.cpp`（SIGINT 与令牌 guard）、`src/app/output.{hpp,cpp}` 与
`src/app/json_output.cpp`（`CANCELLED` 与 status 对象）、`src/gui/session_state.cpp`（九态映射）。

## 1. 背景与范围

目标：长查询和长脚本可以被打断，入口能区分"正常完成""用户取消""执行不确定"。

包含：

- core 的请求级取消令牌与执行检查点；
- 新增 `StatementStatus::kCancelled` 与入口展示；
- CLI 的 SIGINT（Ctrl+C）优雅取消；
- 测试与验收。

不包含：

- 强制中断 storage 的单次调用（见第 6 节）；
- 事务回滚与"取消后恢复中间状态"；
- 进程内并发（U6）所需的执行流身份与同步点；
- 取消 GUI 正在进行的 `open`/`close`（只覆盖 `execute_script`）。

## 2. 现状基线

| 位置 | 现状 |
| --- | --- |
| `include/tinydbms/core.hpp` | 无取消概念；`ExecuteScriptRequest{text, error_policy, mode, max_query_rows}` |
| `src/core/executor.cpp`（`scan_records`） | SELECT/DELETE/UPDATE 共用的扫描循环，是唯一的统一行循环 |
| `src/core/executor.cpp`（Join / Sort / Aggregate） | 在内存中对已物化行做循环，不调用 storage |
| `src/core/executor.cpp`（INSERT） | 逐行调用 `storage::insert`，中途失败会返回"部分成功 + error" |
| `StatementStatus` | 八态；`kExecutionIndeterminate` 表示"可能已产生副作用"，语义上不等于取消 |
| `src/app/*` | 没有任何信号处理代码 |
| `src/gui/worker.hpp` | 工作线程执行 `Backend::execute_script`，接口同步阻塞，没有取消入口 |
| `include/tinydbms/common.hpp` | `kMaxSqlBytes = 1 MiB`，INSERT 的行数因此有天然上界 |

## 3. 取消令牌

```cpp
// include/tinydbms/core.hpp
class CancelToken {
public:
    CancelToken() : flag_{std::make_shared<std::atomic<bool>>(false)} {}

    // 线程安全；只做一次原子存储，不注册回调、不分配内存。
    // 信号处理器可用性依赖无锁实现：C++ 标准没有显式担保，因此用
    // is_always_lock_free 断言把前提固定在编译期。
    void request_cancel() const noexcept {
        flag_->store(true, std::memory_order_relaxed);
    }

    [[nodiscard]] bool cancel_requested() const noexcept {
        return flag_->load(std::memory_order_relaxed);
    }

private:
    std::shared_ptr<std::atomic<bool>> flag_;
};

static_assert(std::atomic<bool>::is_always_lock_free);
```

规则：

- 拷贝构造/赋值共享同一标志，调用方持有一份、请求里放一份即可跨线程/跨入口请求取消。
- 不使用 `std::stop_token`：它的 `request_stop()` 会调用已注册回调，不能保证在信号处理器中安全；
  本设计只需要"置位 + 轮询"，自定义令牌的语义更窄也更明确。
- 信号处理器只允许调用 `request_cancel()`（以及再次中断时的 `std::signal` / `std::raise`），
  不做展示、不写流、不分配内存；若平台不满足无锁断言，编译期直接失败，而不是留下运行时不确定性。
- 令牌默认可取消但从未被请求，因此不传令牌 = 行为与现状完全一致。
- 取消是**幂等的**：重复请求无副作用；请求后不会被清除，同一令牌不能复用于"重置后重跑"。

`ExecuteScriptRequest` 增加字段（放在末尾，默认值保持现有调用方零改动）：

```cpp
struct ExecuteScriptRequest {
    std::string text;
    ScriptErrorPolicy error_policy{ScriptErrorPolicy::kStopOnFirstError};
    ExecutionMode mode{ExecutionMode::kExecute};
    std::size_t max_query_rows{kMaxQueryRows};
    CancelToken cancel;   // 新增
};
```

## 4. 检查点与状态

### 4.1 检查点位置

| 位置 | 首版是否设检查点 | 取消时已产生的副作用 |
| --- | --- | --- |
| 语句开始前（每个语句的入口） | 是 | 无 |
| `scan_records` 每次迭代开始处 | 是 | 无（扫描只读） |
| Join 内层循环 | 是 | 无（内存中） |
| Sort / Aggregate 的行循环 | 是 | 无（内存中） |
| INSERT 的行循环 | **否** | —— |
| `delete_records` / `update_rows` 调用期间 | 否 | storage 单次调用不可中断 |

INSERT 不设检查点的原因：它逐行写 storage，取消会产生"部分行已写入 + 语句未完成"的复合结果，
而 `kCancelled` 首版不携带 outcome，调用方将无法知道实际写入行数。INSERT 的行数受
`kMaxSqlBytes`（1 MiB SQL 文本）约束，取消延迟有天然上界，因此首版接受该限制；
把 INSERT 纳入取消范围需要先设计"部分成功 + 取消"的结果形状，属于后续扩展。

### 4.2 语句状态

新增 `StatementStatus::kCancelled`（追加在枚举末尾，不改变已有取值），不携带 outcome，
与 `kAnalysisOnly`、`kSkippedExecution` 同类。

取消生效后：

- 正在执行的语句在检查点结束，记为 `kCancelled`；
- 之后尚未开始的语句直接记为 `kCancelled`，不再编译、不再执行；
- `script_error` 保持为空：取消是调用方的主动行为，不是错误，也不是"状态未知"；
- 完成的语句保留 `kExecuted` 结果，`statements` 仍覆盖分句后的全部语句，顺序与下标不变。

这与 `kExecutionIndeterminate` 的区别是明确的：后者表示"可能已产生副作用，需要重开数据库确认"，
而取消只发生在无副作用检查点，因此不需要重开。

### 4.3 与错误策略的关系

- `kStopOnFirstError` 与 `kAnalyzeRemaining` 都让位于取消：取消后不再编译剩余语句，
  不产生 `kSkippedExecution`（那是错误策略的语义）也不产生分析态。
- 取消与 `--plan` 组合时同样生效：计划模式不进入执行器，检查点退化为语句边界。
- 取消不改变 `execute_script` 的返回类型与既有字段。

## 5. 入口集成

### 5.1 CLI

**令牌生命周期**：每次 `execute_script` 调用使用独立的 `CancelToken`，令牌不跨调用存活。
批处理在 `read_batch` 完成后构造令牌；REPL 每读取一行构造一个新令牌。这样"空闲期按下的
Ctrl+C"不会把取消状态带进之后任何一次执行——否则一次误按会毒化整个 REPL 会话。

**信号处理器与活动令牌**：信号是进程级的，需要一个进程级的"当前活动令牌"指针：

```cpp
std::atomic<const CancelToken*> g_active_token{nullptr};  // 同样要求 is_always_lock_free
```

- 处理器只读取该指针；非空且尚未请求取消时调用 `request_cancel()`，不做其他工作。
- 其余情况（指针为空，或该令牌已经请求过取消）恢复默认处置并重新触发信号，进程立即终止。
  这一条规则同时覆盖三种场景：执行期间第二次 Ctrl+C、读取输入期间的 Ctrl+C、REPL 空闲期按 Ctrl+C。
- 指针由 RAII guard 维护：设置发生在 `execute_script` 调用之前，清除发生在令牌析构之前，
  避免处理器读到悬垂指针。

**行为与展示**：

- 首次 Ctrl+C：请求取消，当前语句在下一个检查点结束；批处理把剩余语句记为 `kCancelled`。
- 展示写 stderr（与 `SKIPPED`、`INDETERMINATE` 的流向一致）：table 格式输出 `CANCELLED <range>`；
  JSON 格式输出 `{"type":"status","statement_index":N,"status":"cancelled","range":"..."}`
  （与现有 status 对象同构，写 stderr 而不是 stdout）。
- 退出码：本次调用存在 `kCancelled` 语句时按失败处理（退出码 1）；REPL 在取消后继续读取下一行，
  最终退出码仍为 1。不引入 130 等新退出码，保持现有 0/1/2 契约。
- 参数错误与 `--help/--version` 不受影响（它们在执行前返回）。

### 5.2 GUI

GUI 的 `Backend::execute_script` 在 worker 线程同步阻塞，UI 线程持有同一个 `CancelToken`，
因此 `request_cancel()` 可以跨线程调用。取消后 core 正常返回，worker 把 `kCancelled` 语句
渲染为"已取消"状态即可，不需要新的线程机制。

本轮只登记该边界，不实现 GUI 的取消按钮；GUI 侧的展示映射已同步为九态
（见 [GUI 设计](../gui/GUI设计.md)）。

## 6. 与 storage 的边界

- storage 的公共调用（`scan_next`、`insert`、`update_rows`、`delete_records`、`close_cursor`）
  **不可中断**：取消在两处调用之间生效，不承诺"立即停止"。
- 取消延迟的上界是"一次 storage 调用 + 一次行循环迭代"；INSERT 例外，上界是整条语句。
- storage 不需要为 U5 提供新接口；cursor 的关闭仍由 core 的既有 `CursorGuard` 负责，
  取消路径必须与普通错误路径一样关闭 cursor（不得泄漏）。

## 7. 测试设计

core（fake storage 可注入取消）：

- 未请求取消时行为与现状一致（现有测试即回归）；
- 扫描中途取消：语句 `kCancelled`、后续语句 `kCancelled`、`script_error` 为空；
- Join 与 Sort/Aggregate 循环中途取消；
- 语句边界取消：第一句正常完成，第二句 `kCancelled`；
- 取消发生在 DELETE/UPDATE 的收集阶段：不产生 `delete_records`/`update_rows` 调用；
- 取消路径关闭 cursor（fake storage 断言 `close_cursor` 被调用）；
- 取消后同一 Database 的下一次 `execute_script` 仍可正常执行；
- 与 `--plan`、两种错误策略的组合行为。

CLI：

- 取消令牌在请求前已置位：输出 `CANCELLED`、退出码 1、REPL 继续读取下一行；
- REPL 每行使用独立令牌：第一行被取消后，第二行用新令牌正常执行并成功；
- table 与 JSON 两种格式的取消输出；
- 信号处理器本身不在单元测试中触发，测试通过直接请求令牌覆盖行为（信号注册用最小手工验证）。

真实链路：对大结果集脚本先请求取消，确认语句边界路径、退出码与数据未被修改。

## 9. 影响面与需要通知其他成员的事项

- `include/tinydbms/core.hpp`：新增 `CancelToken`、`ExecuteScriptRequest::cancel` 与
  `StatementStatus::kCancelled`。属于公共头变更：新增枚举项会让穷举 `StatementStatus` 的
  switch 编译报错，调用方需要补分支；新增字段有默认值，其余调用方无需改动。
- compiler：无请求。
- storage：无接口改动；取消不进入 storage 内部，只依赖"调用不可中断"这一既有事实。
- GUI：需要把 `kCancelled` 加入状态映射（九态）；取消按钮属于 GUI 侧独立工作项。
- 与 U6 的关系：本设计不需要执行流身份，只依赖线程安全令牌，因此可以先于 U6 落地；
  U6 的同步点设计可以复用同一套检查点位置。

## 10. 实现说明（不属于公共契约）

- 执行器内部的取消传播用私有信号类型 `internal::CancellationSignal` + 抛掷展开实现：
  检查点只调用 `internal::throw_if_cancelled(cancel_token)`，由 `execute_plan_impl`
  在 `catch (const CancellationSignal&)` 中转成 `PlanExecutionResult{cancelled = true}`。
  这样深层循环不需要逐层改造返回类型，cursor 由既有 `CursorGuard` 析构关闭；
  该类型不派生自 `std::exception`，不会被"存储/编译器异常"的兜底分支误判为致命中止。
- 第一阶段的实现把当前语句的令牌指针（`cancel_token`）放在 `Database::Impl` 上，每条语句
  入口重置、结束后复位；它不进入公共头文件。**U6（进程内并发）已把它改为每次调用的栈上
  上下文 `ExecutionContext`**，语义不变——见 [进程内并发设计](进程内并发设计.md) §11。
- 验收记录（2026-09-15）：fake 路径覆盖扫描中途、语句边界、Join、Sort、Aggregate、
  DELETE/UPDATE 收集阶段与计划模式取消；CLI 覆盖两种格式的 `CANCELLED`、退出码 1 与
  REPL 每行独立令牌；真实链路用预置令牌验证数据文件未变。SIGINT 三条路径在 `debug`
  真实模块构建上手工冒烟：执行期首次 Ctrl+C 在语句边界取消并退出码 1、空闲期 Ctrl+C
  按默认处置终止（退出码 130）、执行期第二次 Ctrl+C 立即终止（退出码 130）。
