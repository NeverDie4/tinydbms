# Core/入口升级设计：进程内并发

状态：**第一阶段已实现并验收**（2026-09-15）。对应 [升级路线图](../升级路线图.md) 的 U6。
实现记录见 §11；A/B 类决策已按推荐值关闭（§9）。

> 2026-09-15 复核：storage 的 PR #6（`4e66b97`）已合入 main，下面的 §2、§5、§6、
> §8 按合入后的代码事实更新（storage 内部新增了锁与状态机串行化，并带一个默认关闭的
> 预取 worker 线程）。结论 A1/A2 不变：core 侧的串行化仍然是必要条件。

## 1. 背景与范围

**目标**：同一个 tinydbms 进程（一个可执行文件的一次运行）里有多个执行流——线程或协程——
同时访问同一份内存状态。

**包含**：

- 共享 `Database` 实例的并发访问规则：互斥范围、等待策略、与取消的交互；
- 执行流身份：把 U5 起写在 `Database::Impl` 上的**每语句临时状态**归位，避免多个执行流互相覆盖；
- 生命周期并发：`open`/`close` 与在途执行的关系、cleanup-pending 期间的新请求；
- 与 storage 的并发边界（对外请求，不要求 storage 新增接口）；
- 测试与验收：串行化证据、取消隔离、ThreadSanitizer 构建。

**不包含**：

- 跨进程并发、文件锁、多实例并行——路线图 §3 已列为独立阶段；
- 事务、MVCC、原子多语句提交；
- 读写并行（首版只承诺"安全串行化"，见 A2）；
- 协程调度器（技术决策的工程基线已排除 coroutines，见 A6）；
- 入口层的并发交互（GUI 多标签、多连接、后台任务面板）。

## 2. 现状基线

| 位置 | 现状 |
| --- | --- |
| `src/core/internal.hpp`（`Database::Impl`） | 单份可变状态：`catalog`、`next_table_id`、`open`、`forced_close_pending`、`cleanup_retry_needed`、`current_plan_storage_called`、`cancel_token`。所有调用共享这些字段，没有任何同步 |
| `include/tinydbms/core.hpp` | `Database` 是 move-only 的 Pimpl 值对象，没有线程语义声明；`execute_script` 以"整段脚本一次调用"为单位 |
| `include/tinydbms/storage.hpp` | 无句柄单例 API：`open_storage`/`close_storage` 是进程级操作，`CursorId` 由 storage 全局分配器发放；没有并发承诺 |
| `src/storage/page_file.cpp`、`file_manager.cpp`、`buffer_pool.cpp` | PR #6（`3f32a57`）起，`PageFile` 有 per-file `std::mutex`；`FileManager` 有 `mutex_` 加 `state_changed_` 条件变量，串行化表的打开/关闭状态转换；`BufferPool` 有 `metadata_mutex_`、`prefetch_mutex_`、`worker_control_mutex_`。这些锁保护的是**内部层级**，不等于调用方可以并发调用公共 API |
| `src/storage/storage.cpp`、`cursor_state.*` | 公共 API 层仍是文件作用域的 `StorageState state;`（生命周期、catalog、buffer pool、cursor 注册表），与无锁的 cursor 分配——按检索确认**同步原语数量为 0**。并发调用公开 API 依旧会数据竞争 |
| `src/storage/buffer_pool.{h,cpp}`（预取实验） | `BufferPool` 持有一个 `std::thread` 预取 worker（RUNNING/STOPPING/STOPPED、advisory 提交、`LoadOrigin` 区分 Demand 与 Prefetch）。默认 `prefetch_enabled=false`，只有内部 `BufferPool::create(..., true)`（benchmark 与测试）才创建线程；实验结论是本机 elapsed 退化，默认保持关闭，见 [pref1 报告](../storage/pref1-report.md) |
| `src/gui/main_window.cpp` | GUI 已有工作线程：`Worker` 被 `moveToThread`，`Database` 归工作线程所有，UI 线程只发信号、不触碰 Database。当前的实际形态是"一条执行流 + 一个不接触 core 的 UI 线程" |
| `include/tinydbms/core.hpp`（U5） | `CancelToken` 本身线程安全（原子标志 + 无锁断言），但 `Impl::cancel_token` 是单成员：并发下两个执行流会互相覆盖令牌 |
| `src/core/database.cpp`（进程级槽位） | "同一进程同一时间只能打开一个数据库"由 `g_database_open` 这个 `std::atomic<bool>` 用 CAS 获取、release 释放实现，跨实例的抢占已经是原子的；第二个实例的 `open` 稳定返回 "another database is already open in this process" |
| `docs/消息契约详细设计.md` | "初版单进程：调用方按顺序、单执行流调用 core 的 `Database`（core 内部没有同步原语），storage 的公共 API 同样要求串行调用……进程内并发的控制逻辑归 core 执行层"；同一进程同一时间只能打开一个数据库 |
| `docs/模块交互契约.md` | "本阶段约定调用方按顺序、单执行流调用：core 内部没有同步原语，storage 的公共 API 同样要求串行调用" |
| `docs/技术决策.md` | 工程基线为"单进程；正常 SQL 操作按调用方顺序执行。BufferPool 预取实验启用时会创建一个内部 worker 线程，默认关闭"，并使用 C++20 的保守子集（不使用 ranges、coroutines 或 modules） |

由此得到两条必须先接受的约束：

1. **"每个执行流一个 `Database` 实例"在当前架构下不可实现。** storage 无句柄、`open_storage`
   是进程级单例操作，第二个 `Database::open` 会按现行契约直接返回错误；每流一个实例等价于
   多实例并行，而路线图已把它列为需要 WAL 与句柄化的独立阶段。
2. **并发安全的第一责任方仍是 core。** storage 在 PR #6 之后给 page/file/buffer 层加了内部锁，
   但**公共 API 层与 cursor 注册表至今没有任何同步原语**：并发调用公开 API 依旧会数据竞争。
   core 必须自己保证同一时刻只有一个执行流进入 storage；storage 的内部锁属于它自己的实现细节，
   不能被读成"调用方可以并发调用"的许可。

## 3. 并发模型

### 3.1 共享方式（A1）

多个执行流共享同一个 `Database` 实例，由 core 内部串行化；不新增 `Session`/`Connection`
之类的句柄类型。

理由：

- 与 storage 的单实例现实一致（§2 约束 1）；
- 与 GUI 现有结构一致：一个 `Backend` 归工作线程所有，请求排队；
- 保持公共 API 形状不变，`Database` 的构造与移动语义维持现有契约。

### 3.2 承诺级别与忙时策略（A2、A4）

首版承诺 **"安全但串行化"**：

- 同一时刻只有一个执行流处于执行临界区，其他执行流阻塞等待；
- 不承诺并行度，不承诺读并行，也不承诺多语句并行；
- 并发调用不产生数据竞争、不交错修改 catalog、不互相污染结果与状态。

读并行需要 catalog 快照与 storage 只读并发两件事，成本与风险都不低，而当前没有任何入口
需要它；把它登记为后续候选，不作为首版承诺。

忙时策略同样从简：**统一阻塞等待，不新增"忙则失败"策略**，也不引入 `kBusy` 之类的错误种类。
需要"执行中就拒绝新请求"的入口可以自己在入口层维护队列，`core` 不必把这个维度扩散到
错误模型与展示层。

### 3.3 临界区范围（B1）

以 `Database` 为单位的**调用级互斥**：一次 `open`、`close` 或 `execute_script` 从进入公开方法
到返回全程持锁。

不做语句级交错的原因：`execute_script` 的脚本级状态（错误策略、执行门、影子 Catalog、
`statements` 顺序）都属于一次调用，把锁下沉到语句会让两个脚本的语句交替执行，直接破坏
stop/analyze 语义与结果顺序。

### 3.4 等待与取消（A3）

- 预置令牌（进入前已请求取消）的请求仍按 U5 语义返回：分句后全部语句记 `kCancelled`，
  不编译、不执行、不触碰 storage。它仍要排队取得执行权，因为"数据库是否打开"的状态本身在锁内。
- 首版**不实现"等待期间取消"**：等待者只有在取得执行权后才能命中检查点。已知影响是取消的
  响应延迟上界从"一次 storage 调用 + 一次行循环迭代"扩大为"前一个执行流剩余的执行时间"。
- 入口层可以规避这一延迟：CLI 与 GUI 的排队都发生在入口侧，"不投递下一个请求"本身就是取消排队。

若评审认为等待期间取消是必要能力，实现路径已明确：把令牌每 50 ms 轮询一次并用
`condition_variable::wait_for` 等待，命中时走一条"锁外快速路径"（只做 moved-from 与 open 校验，
再分句并全部记 `kCancelled`）。该路径会让 `open` 需要一个供锁外读取的原子镜像，属于后续扩展，
本文只登记，不列入首版范围。

### 3.5 生命周期与并发（A5）

| 并发组合 | 规则 |
| --- | --- |
| `execute_script` ∥ `execute_script` | core 串行化：后到者等待，两者结果互不污染 |
| `close` ∥ `execute_script` | 互斥：`close` 等待在途执行结束后进入，不与执行交错 |
| `open` ∥ `execute_script` | 互斥：未打开时会得到与顺序执行一致的"database is not open"错误 |
| `open` ∥ `close` | 互斥：先取得执行权的一方先生效，后到者按当时的生命周期状态返回结果——未打开时 `close` 返回"database is not open"，`open` 成功后 `close` 正常关闭 |
| 不同 `Database` 实例 ∥ `open`/`execute_script` | 进程级槽位（`g_database_open` 的 CAS）保证只有一个实例处于 open 或 cleanup-pending；另一个实例的 `open` 返回"another database is already open in this process"。这属于**已存在**的原子保护，U6 不改动它，也不把它扩展成"多实例并行" |
| cleanup-pending / forced-close ∥ 新请求 | 语义不变：按现行契约返回错误或要求重试 `close`，不新增强制中断 |
| 移动、析构 ∥ 任意调用 | **调用方责任**：对象生命周期与并发访问必须互斥，与 C++ 标准库对象一致，core 不做额外保护 |

不提供"强制中断在途 storage 调用"的能力——运行中取消设计已声明 storage 的单次调用不可中断，
并发不会改变这条边界。

这张矩阵合起来给出 U6 的核心论证：**进程级槽位保证任何时刻只有一个 `Database` 实例可能调用
storage，每实例的调用级互斥保证该实例内部不并行**。因此 storage 的全局状态在场面上始终只有
一个执行流在驱动，"调用方单线程"这条隐含假设在本设计下可以改成可验证的显式规则。

需要单独说明 storage 自带的**内部预取 worker 线程**：它只访问页缓存与文件层，不触碰
`StorageState`、catalog 或 cursor 注册表，也不属于"调用方执行流"。core 既不依赖它的存在，
也不为它的行为提供保证；在默认配置（`prefetch_enabled=false`）下它根本不会被创建。

### 3.6 执行流身份与临时状态（B3）

`Impl` 只保留**共享状态**：`catalog`、`next_table_id`、`open`、`forced_close_pending`、
`cleanup_retry_needed`，以及保护它们的互斥量。

落到执行流本地的状态改为参数或栈上上下文对象：

- `cancel_token` 由成员改为沿调用链传递（`execute_plan_impl` 已经是参数形式，执行器内部
  不应再从成员读取）；
- `current_plan_storage_called` 改为本次语句的局部上下文，其"当前语句是否可能已产生副作用"
  的语义只对正在执行的调用有意义。

`current_plan_storage_called` 的**回传路径必须写清**：`script.cpp` 并不是只读该标记，
它在 `execute_plan_impl` 返回之后才用它。执行器把"本次 Plan 是否调用过 Storage"写进内部的
`PlanExecutionResult`（新增 `storage_called` 字段），`script.cpp` 用自己的局部变量承接，
再交给 `side_effects_possible()`。**不能只做删除**：`open_table` 返回"成功但无 cursor"、
`insert` 返回的 rid 数量超出请求行数这类路径，返回 `kInternal` 之前确实已经调用过 Storage，
但并没有走 `abort_after_storage_exception()`，这个标记是 `kExecutionIndeterminate` 与
`kSkippedExecution` 之间唯一的判据。

这一步是并发安全的必要条件：即使加了锁，把"当前执行流"的临时状态放在共享对象上也会在
入口层出现重入调用（例如未来 GUI 在 worker 内部触发第二次调用）时互相覆盖。

### 3.7 协程（A6）

首版不支持协程，理由是两条硬约束：

- `docs/技术决策.md` 的工程基线明确使用 C++20 保守子集，不使用 coroutines；
- storage 是同步阻塞 I/O，协作式让出无法避免阻塞事件循环，除非先做异步 storage 接口。

若将来确实需要更高并发度，先做"线程池 + 本文的串行化"，再单独评估异步 storage。

## 4. 契约与公共头影响

- `include/tinydbms/core.hpp`：**不新增符号**，只补充文档级线程语义——同一实例的公开方法
  （`open`、`close`、`execute_script`）可被多个执行流并发调用，core 内部串行化；对象移动与
  析构仍需调用方保证互斥。
- `include/tinydbms/storage.hpp`：**不新增接口**。需要把"core 串行化后，storage 收到的调用
  仍是串行的"写进契约，并明确 cursor 归属（见 §5）。
- 需要同步的文档：`docs/消息契约详细设计.md`（单线程表述）、`docs/模块交互契约.md`
  （本阶段单线程顺序执行）、`docs/技术决策.md`（工程基线与暂不纳入范围）、
  `docs/gui/GUI设计.md`（工作线程假设）。

## 5. 与 storage 的边界（对外请求）

core 串行化后，storage 不需要新增接口。PR #6 之后 storage 内部已有锁，所以这里要的
**不是"再补一把锁"，而是把边界写清楚**。需要 storage 成员确认并把以下六点写进
[storage 契约](../storage/storage-contract.md)：

1. **并发边界**：公共 API（`open_storage` 到 `update_rows`）是否要求调用方串行化。按代码事实，
   公共 API 层与 cursor 注册表目前没有同步原语，这条要求只存在于"core 单线程"的隐含假设里；
   内部锁保护的是 page/file/buffer 层，不能据此推断"公共 API 可以并发调用"。
2. **cursor 归属**：`CursorId` 由 storage 全局分配器发放，需要声明它是否跨执行流可见、
   以及在 `close_cursor` 之后是否可能被复用。
3. **`close_storage` 与在途调用**：`3f32a57` 新增了打开/关闭状态机与 `state_changed_` 条件变量，
   需要说明 `close_storage` 与在途 `scan_next`/写调用的关系，以及 core 现有的 cleanup-pending
   语义（"storage 可能已经完成、也可能没有"，见消息契约）是否仍然成立。
4. **预取 worker 的线程语义**：谁创建与停止它、它的可见性边界（明确哪些状态它绝不触碰），
   以及未启用时确实不创建线程。
5. **fail-fast 与错误返回的分界**：PR #6 之后 storage 在内部不变量失败时大量使用
   `std::terminate()`（`file_manager.cpp` 2 处、`buffer_pool.cpp` 11 处，例如关闭等待后
   `open_files_` 条目消失、或违反"非重入单线程"不变量）。这会让进程直接终止，**绕过 core 的
   cleanup-pending 恢复路径**：core 现有的"storage 抛异常 → 记 `kExecutionIndeterminate`、
   要求重开"契约以"异常可捕获"为前提。需要 storage 明确哪些失败走 fail-fast、哪些通过错误码或
   异常返回，避免 core 的恢复语义被静默绕过；这是本次合并复核新发现的一项，与并发无关，
   但对 U6 的执行流串行化证明同样重要（它把"违反串行化"的后果从"出错"变成"崩溃"）。
6. **未来扩展的接口面**：如果 storage 要把内部锁扩展成支持并发调用（句柄化、写锁），
   需要单独设计并提前通知 core，因为 core 的串行化假设会随之改变。

## 6. 测试设计

core（fake storage 可注入交错窗口）：

- 两个线程并发 `execute_script`：fake 在 storage 调用处阻塞，制造第二个执行的等待窗口，
  断言 storage 调用序列**严格不交错**（fake 记录进入/退出序列），且两个结果都正确；
- 取消隔离：A 执行中请求 A 的令牌，B 的令牌不受影响，B 的语句状态不受 A 的取消影响；
- 并发 `close` 与 `execute_script`：执行结果完整返回，`close` 不产生清理错误；
- 并发 `open` 与 `execute_script`：未打开时的错误与顺序执行一致；
- 预置令牌的请求在并发下仍返回全部 `kCancelled`，且不产生 storage 调用；
- 回归：单线程路径的现有用例全部保持通过，输出零变化。

实现后的取证方式（对应 `tests/core_concurrency_test.cpp` 与 `tests/fakes/storage_fake.cpp`）：

- fake 的每个公共入口都经一层 `CallScope`，用原子计数记录"同时处于 storage 内部的调用方
  数量峰值"，并提供 `fake::max_concurrent_calls()` 与 `fake::overlap_detected()`；
- `fake::set_on_storage_call` 是新的通用阻塞钩子（参数是入口名），测试用它把调用方停在
  storage 内部，再由主线程启动第二个执行流、等待 150 ms、放行；core 串行化正确时峰值恒为 1；
- 另有顺序证据：`fake::state().call_order` 断言两条脚本的调用序列**首尾相接且不交错**，
  `close` 场景断言 `close_cursor` 一定早于 `close_storage`；
- **反向验证（用例有效性）**：把 `open`/`close`/`execute_script` 的 `lock_guard` 摘掉后重编
  同一用例，进程直接以 `double free or corruption` 崩溃——说明这些断言确实能观测到串行化缺失，
  而不是"永远为真"。

构建与工具：

- 新增 ThreadSanitizer 构建目标：`CMakePresets.json` 的 `tsan` 预设（`-fsanitize=thread
  -fno-omit-frame-pointer`，输出到 `build/tsan`），与手工配置的 `build/sanitize-*` 并列，
  在其上运行 core、CLI 与 fake 测试。**本机可用性已实测**：g++ 16.2.1 链接通过、运行探针正常，
  对故意构造的数据竞争能正确报 `WARNING: ThreadSanitizer: data race`。storage 的
  [pref1 报告](../storage/pref1-report.md) 记录过 `cannot find -ltsan`，与本机实测不一致
  （多半来自另一套工具链），实施时以本机实测为准；备用方案是本机已安装的 valgrind
  （Helgrind/DRD），但它对假阳性更敏感，只作为补充。
- 严格警告构建继续通过（并发代码容易引入类型与转换警告）。

一处 TSan 相关的既有边界：`tests/core_executor_test.cpp` 的"病理 Plan 深度"用例会用
4096 层 Filter 串联构造 Plan。`PlanNode` 的析构本身是递归的，**单独析构这样一棵树**
在 TSan 下就会栈溢出（最小探针复现，与 core 无关；见 §11），因此该用例在
`__SANITIZE_THREAD__` 下取 1024 层（仍是 `kMaxPlanDepth = 256` 的 4 倍），普通构建保持 4096。
真正的结论是"递归 `unique_ptr` 表示的 Plan 在深树上有析构栈风险"，属于公共头文件的表示形式，
留给 compiler 侧评估。

真实链路：

- 真实 compiler + storage 上并发执行两条读语句与一条写语句，确认结果正确、数据文件一致；
- 真实链路上并发 `close` 与执行，确认无清理错误。

## 8. 影响面与需要通知其他成员的事项

- **storage**：§5 的六点需要确认并回填契约。本轮不要求 storage 改代码，也不需要它再加锁——
  PR #6 已经给 page/file/buffer 层加了锁与状态机串行化；缺的是"公共 API 层要求调用方串行"
  这条明确声明，以及预取 worker 的线程语义。需要特别指出：公共 API 层与 cursor 注册表
  **至今没有任何同步原语**，core 的串行化是这块安全性的唯一来源。
  另外 §5 第 5 点是本次合并复核新发现的、与并发无关的一项：storage 用 `std::terminate()`
  处理内部不变量失败，会绕过 core 的 cleanup-pending 契约，需要 storage 说明 fail-fast 边界。
- **compiler**：无请求。core 串行化后 compiler 仍按单执行流被调用；按源码检索，compiler 的
  公共调用没有文件作用域可变状态，因此后续若要放开"锁外分句"也不需要 compiler 配合，
  但该前提需要在实施时由 compiler 成员复核一次。
- **GUI**：本设计只提供 core 能力。多标签、并行任务面板与"同时运行两条脚本"的交互属于入口层
  工作项，需要 GUI 侧单独提需求。
- **全体成员**：`include/tinydbms/core.hpp` 只有文档级线程语义补充，不新增符号；
  `include/tinydbms/storage.hpp` 无改动。

## 9. 决策（推荐列已于 2026-09-15 按原样关闭）

A 类（改接口形状或对外承诺；已全部采用推荐值）：

| 编号 | 决策 | 推荐 | 理由 |
| --- | --- | --- | --- |
| A1 | 共享方式：共享实例 + core 串行化，还是每执行流一个实例 | **共享实例 + core 串行化** | 每流一个实例被 storage 单例挡住，等价于多实例并行；GUI 现状也是共享实例排队 |
| A2 | 承诺级别：安全串行化，还是读写并行 | **安全串行化** | 读并行需要 catalog 快照与 storage 只读并发，当前没有入口需要 |
| A3 | 等待期间是否可取消 | **首版不实现**，登记为后续扩展 | 入口层的排队已经能表达"取消排队"；锁外快速路径会引入 `open` 原子镜像等额外状态 |
| A4 | 忙时策略：新增"忙则失败"，还是统一阻塞等待 | **统一阻塞等待**，不新增 `kBusy` 与请求字段 | 一次性并发度需求未出现；新增策略维度会扩散到所有入口与错误展示 |
| A5 | `close` 与在途执行：互斥等待，还是强制中断 | **互斥等待** | storage 单次调用不可中断已经写进 U5 契约 |
| A6 | 是否引入协程 | **不引入** | 工程基线排除 coroutines；storage 同步阻塞，让出无收益 |

B 类（实现细节；已按推荐值实现，实施中的细化记在 §11）：

| 编号 | 决策 | 推荐 |
| --- | --- | --- |
| B1 | 互斥粒度 | 调用级：`open`/`close`/`execute_script` 全程持锁 |
| B2 | 同步原语 | `std::mutex` + `std::lock_guard`/`std::unique_lock`；不使用递归锁与自旋。互斥量放在 `Impl`（Pimpl 指向的对象）里：`Database` 是 move-only 值对象，`Database(Database&&) noexcept = default` 会因为 `std::mutex` 不可移动而被隐式删除 |
| B3 | 临时状态归位 | `cancel_token`、`current_plan_storage_called` 移出 `Impl`，改为参数或栈上上下文 |
| B4 | 移动与析构 | 仍属调用方责任，不承诺与并发调用共存 |
| B5 | 测试基建 | 新增 ThreadSanitizer 构建目标 + fake 阻塞钩子 |
| B6 | 加锁位置 | 只加在 `Database` 的公开方法上，不下沉到内部 helper |

## 10. 启动条件

U6 不因为"设计已就绪"就启动。进入实现前需要出现至少一条真实需求：

- GUI 出现多标签、并行任务面板或"执行中继续提交"的交互；
- CLI 需要"一边执行一边接收新命令"；
- 其他成员需要在一个进程里安全共享同一个 `Database`。

在那之前，本设计的价值是固定共享方式、临界区范围与 storage 边界，避免后续以不兼容的方式
补并发。

**2026-09-15 决定：提前实施。** 触发理由是项目负责人明确要求本次进入实现，且当前处于允许
破坏性变更的窗口内，后续入口演进（GUI 多标签、脚本并行提交）会依赖这条边界，先固定实现比
以后再补更便宜。上述三条真实需求在实施时都还没有落地，所以本节记录的事实是"决策提前实施"，
不是"需求已经出现"；验收要求也相应放宽为"单线程路径行为零变化 + 并发用例给出串行化证据"，
而不是端到端入口需求验证。

实施中的三点细化（都对得上 §3.6 与 §6 的口径）：

1. **`storage_called` 必须回传**，不能只把成员删掉：`script.cpp` 在 `execute_plan_impl`
   返回之后才用它，而且 `open_table` 返回"成功但无 cursor"、`insert` 返回过多 rid 这类路径
   并不走 `abort_after_storage_exception()`，返回值是区分 `kExecutionIndeterminate` 与
   `kSkippedExecution` 的唯一判据。`tests/core_executor_test.cpp` 的
   `test_open_and_scan_result_invariants_close_cursor_once` 覆盖这条语义。
2. **冻结的调用级互斥不影响 `g_database_open` 槽位**：进程级 CAS 与实例内互斥量两级保护
   互不替代，第二个实例的 `open` 仍返回 "another database is already open in this process"。
3. **反向验证**：摘掉三处 `lock_guard` 后重编同一并发用例会直接 `double free` 崩溃，
   说明用例不是恒真断言（细节见 §6）。

已知边界（不在本阶段范围）：

- 等待期间取消（A3）未实现，取消响应延迟上界仍是"前一个执行流剩余的执行时间"；
- 读并行（A2）、多实例并行、协程（A6）未实现；
- storage 侧 §5 的六点仍需其成员确认并回填 [storage 契约](../storage/storage-contract.md)；
- `PlanNode` 递归析构在深树上的栈开销属于公共头文件表示形式，留给 compiler 侧评估。
