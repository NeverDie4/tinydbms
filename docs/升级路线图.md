# tinydbms 升级路线图

本文汇总 core、cli 与公共契约职责范围内的升级候选。compiler 与 storage 的实现不在本文范围，
但每项都会标出"对外请求"，用于通知对应模块成员。

状态取值：**候选**（只登记） / **设计中**（已写设计稿） / **已实现**。

推荐次序：**U2 → U3 → U4 → U5 → U6**（U1 已舍弃，编号保留不复用）。U2 只动入口；
U3、U4 开始碰 core 返回结构与配置；U5 只需要线程安全取消令牌与检查点；U6 需要执行流身份，
必须与 storage 联合设计。

编号保留原值是有意的：U1 的舍弃记录见下方 §2 与
[JSON 输出设计](core-cli/CLI升级设计_JSON输出.md) 附录 A，避免后续重复提案。

## 2. 逐项要点

### U1 跨行 SQL（REPL 多行输入）

**状态：已舍弃（2026-09-15 决定）**。

- **舍弃原因**：跨行判定的关键信息（输入结束时是否停在未闭合字符串/块注释）只存在于 compiler
  内部变量里，现有接口既不报错也不暴露该状态；不依赖 compiler 就只能读错误 message 或按末尾分号
  猜，两者都被实测证伪。
- **实测证据**：`SELECT 'a;` 以分号结尾却是未闭合字符串；`SELECT 1; -- note` 的注释落在语句范围之外；
  `SELECT * FROM (` 只得到普通语法错误。完整探针表见
  [JSON 输出设计](core-cli/CLI升级设计_JSON输出.md) 附录 A。
- **结论**：为一个入口体验提升去改公共头并拉上 compiler 的 parser 分类，收益不抵成本；
  契约中原有的"跨行 SQL 为后期优先升级项"表述可以保留为未实现能力，不需要删除。

### U2 JSON 输出

- **目标**：`--format json` 输出机器可读结果，供脚本、测试与 GUI 复用；默认 table 格式不变。
- **现状**：`src/app/output.cpp` 固定制表符文本 + 单行转义；诊断写 stderr。
- **关键决策**：NDJSON（每行一个 JSON 对象）；stdout 只放结果对象、stderr 只放诊断对象；
  字段名与类型固定成可测试契约；BIGINT、DOUBLE、NULL、非 UTF-8 字节的映射需要写死。
- **对外请求**：无。纯入口改造，core 返回结构不变。
- **验收**：每个结果类型与每个诊断类型的 golden 文本、转义边界、退出码不变、批处理与 REPL 一致。

### U3 Plan 整理输出（原 EXPLAIN）

- **目标**：用户能看到一条语句被编译成的执行计划，用于教学、演示与排错。
- **路线已定**：compiler 视为固定——不改公共头、不扩 SQL 方言，因此**不做 SQL `EXPLAIN` 语句**。
  改为入口开关（`--plan`）+ core 侧"计划模式"：core 用现有 `compiler::compile` 得到 Plan，
  按公共头里的 Plan 类型渲染成文本，包装成单列 VARCHAR 的 `QueryResult` 返回，复用现有结果链路。
- **计划文本的归属**：由 core 私有渲染器产出，是本项目自有的展示契约，与 compiler 内部的
  `format_plan`（仅被 compiler 自身测试使用）无关；不改 compiler 意味着两份格式可能不同，这是接受的结果。
- **详细设计**：[Plan 整理输出设计](core-cli/Plan整理输出设计.md)。
- **风险**：Plan 中只有 SlotId、TableId 等编号，渲染需要 core 结合 catalog 解析出列名，解析失败时要退化，
  这部分规则必须写死，否则输出不稳定。

### U4 结果集上限可配置 + 分页/导出

- **目标**：把 `kMaxQueryRows`（现为 `include/tinydbms/core.hpp` 的编译期常量）变成可配置项，
  并让大结果集有可控出路。
- **分阶段**：第一阶段只做"上限可配置 + 超限错误带明确提示"；导出交给 CLI 的 table/JSON 两种格式；
  真正的分页需要重放式游标或 SQL 层 LIMIT/OFFSET，属于第二阶段。
- **关键决策（已定稿，2026-09-15）**：配置放在 `ExecuteScriptRequest`（请求级，默认值保证零改动）；
  取值范围 `>= 1`，不提供"无上限"；超限保持语句级 `kExecute`，消息带上限数值并附 `suggestion`。
- **详细设计**：[结果集上限与分页设计](core-cli/结果集上限与分页设计.md)。
- **对外请求**：compiler 若要支持 LIMIT/OFFSET，需要新增语法与计划节点。

### U5 运行中取消

- **目标**：长查询可以被打断，入口能区分"正常完成""用户取消""执行不确定"。
- **关键决策（已定稿，2026-09-15）**：请求内 `CancelToken`（线程安全、无回调、可在信号处理器中
  置位）；检查点为语句边界、`scan_records`、Join 与 Sort/Aggregate 行循环；新增
  `StatementStatus::kCancelled` 且不携带 outcome；INSERT 行循环首版不设检查点。
- **详细设计**：[运行中取消设计](core-cli/运行中取消设计.md)。
- **依赖**：只需要线程安全令牌，不依赖执行流身份，因此可以先于 U6 落地；U6 复用同一套检查点。

### U6 进程内并发

- **目标**：同一个 tinydbms 进程（一个可执行文件的一次运行）里有多个执行流——线程或协程——
  同时访问同一份内存状态。
- **现状（实现前）**：`docs/消息契约详细设计.md` 与 `docs/模块交互契约.md` 当时的口径是
  "调用方按顺序、单执行流调用；core 内部没有同步原语，storage 的公共 API 同样要求串行调用"；
  GUI 设计依赖"一个工作线程、UI 线程不触碰 Database"。PR #6 之后 storage 内部已有锁
  （`PageFile`/`FileManager`/`BufferPool`）与默认关闭的预取 worker 线程，但**公共 API 层与
  cursor 注册表仍无同步原语**——并发安全此前完全依赖"调用方串行"这一约定（现在由 core 的
  调用级互斥提供）。
- **关键决策（已按推荐值关闭）**：共享方式（共享实例加同步，不采用每执行流一个
  `Database` 实例）；core 里每语句临时状态与取消令牌的归属；storage 单实例的写冲突与
  `close_storage` 在途操作语义；承诺"安全但串行化"，不引入协程。
- **详细设计**：[进程内并发设计](core-cli/进程内并发设计.md)。
- **对外请求**：storage 需要正式定义多执行流下的原子性边界与 cursor 归属。
- **风险**：涉及 core 全部状态机、错误恢复语义与测试矩阵；本阶段按"安全串行化"落地，读并行、
  等待期间取消与多实例并行都留在后续（见设计稿 §3.4、§10）。

## 3. 暂缓或不做

| 项 | 理由 |
| --- | --- |
| 事务、多实例并行、跨进程并发 | 需要 WAL、storage 句柄化与恢复策略，属于独立阶段 |
| 索引扫描、代价模型、谓词下推 | 由 compiler 与 storage 主导，core 只被动适配 |
| 外部排序、流式结果 | 要改 `QueryResult` 公共形状与物化模型，收益不足以抵消改动面 |
| 崩溃恢复与 fsync 策略 | storage 的恢复语义需要单独设计，不与入口升级混做 |

## 5. 需要通知其他模块的事项

- **compiler**：U2/U3 不需要配合——U3 是 core 侧渲染，且没有改动 `src/compiler/` 与
  `include/tinydbms/compiler.hpp`。U4 的上限配置不涉及语法；只有将来要做 LIMIT/OFFSET
  或 SQL 层 `EXPLAIN` 时才需要联系。
- **storage**：U2/U3/U5 不需要配合——计划模式不调用 Storage，取消只在 storage 调用之间生效、
  不进入其内部。U4 不需要新接口；U6 需要确认单实例语义、在途操作与多执行流的原子性边界。
- **storage（收尾阶段新增请求）**：P3 需要 `include/tinydbms/storage.hpp` 增加
  `StorageStatsRequest` / `StorageStats` / `StorageStatsResult` 与 `storage_stats()`，
  语义四条（累计与清零、未打开返回 kInvalidRequest、口径只含 buffer pool、只读且不抛异常）
  见 [展示格式与性能观测设计](core-cli/CLI展示格式与性能观测设计.md) §5.3；
  同时 `codex/log`（PR #7，`73cbf5a`）已实测可合入当前 main（65/65 测试通过），
  但需处理事件日志的 4 项口径与健壮性问题、并把 `TINYDBMS_BUFFER_EVENT_LOG` 与
  `[BUFFER][…]` 格式回填 [storage 契约](storage/storage-contract.md)，
  清单见 [展示格式与性能观测设计](core-cli/CLI展示格式与性能观测设计.md) §5.5。
  **在这些确认之前 core/cli 不改 storage 头。**
- **所有成员（本轮实际发出的通知）**：U3 已修改 `include/tinydbms/core.hpp`，新增
  `ExecutionMode`、`StatementStatus::kPlanOnly`、`StatementResult::plan_only` 与
  `ExecuteScriptRequest::mode`（默认 `kExecute`，现有调用方零改动）。因为新增了状态枚举，
  任何穷举 `StatementStatus` 的 switch 都需要补分支，编译期 `-Wswitch` 会提示。
  U2 不涉及公共头。

- U1 已于 2026-09-15 舍弃，记录保留在本文 §2 与 JSON 输出设计附录 A。

  入口新增 `--format table|json` 与 `--plan`；core 新增 `ExecutionMode::kPlanOnly`、
  `StatementStatus::kPlanOnly` 与私有计划渲染器；`include/tinydbms/core.hpp` 有变更，已登记。
  compiler 与 storage 的实现文件均未改动。
- U4（结果集上限）第一阶段已于 2026-09-15 实现并验收：`ExecuteScriptRequest::max_query_rows`
  （默认 `kMaxQueryRows`，`0` 在分句前拒绝）、超限消息带 `(limit N)` 与 suggestion、入口新增

## 8. 收尾阶段（P 系列）要点

### P1 CLI 展示格式

- **目标**：终端里默认给人看的输出不再是裸 TSV。
- **关键决策**：新增 `--format pretty`；未显式指定 `--format` 时按 stdout 是否终端选择
  （终端 pretty、非终端 table），TSV 与 NDJSON 的字节级契约不变。
- **详细设计**：[展示格式与性能观测设计](core-cli/CLI展示格式与性能观测设计.md) §3。
- **对外请求**：无。

### P2 调用级耗时

- **目标**：看到每次执行的墙钟耗时。
- **关键决策**：`--time` 写 stderr（`TIME script …` / `TIME line N …`），
  stdout 字节流不变；只测 `execute_script`，不含 open/close 与渲染。
- **详细设计**：[展示格式与性能观测设计](core-cli/CLI展示格式与性能观测设计.md) §4。
- **对外请求**：无。

### P3 buffer pool 统计（缺页率）

- **目标**：显示页缓存命中与缺失情况。
- **阻塞**：`BufferPoolStats` 只在 `src/storage/buffer_pool.h`，公共契约无出口，
  core 取不到值，CLI/GUI 也无法显示。
- **已发出的请求**：storage 增加 `storage_stats()` 与结果类型（§5 通知项），
  落地后按 `--stats` 展示。
- **详细设计**：[展示格式与性能观测设计](core-cli/CLI展示格式与性能观测设计.md) §5。

### P4 执行器连接与聚合优化

- **目标**：去掉连接的二次行合并开销，把连接与聚合的复杂度从乘积降到线性。
- **关键决策**：连接用“安全等值键建哈希候选 + 完整谓词复核”，只在两侧值类别完全相同时建键；
  聚合保持首次出现顺序，只把线性找组换成哈希索引。契约零变更。
- **详细设计**：[查询执行优化设计](core-cli/查询执行优化设计.md)。
- **对外请求**：无；谓词下推/列裁剪/索引扫描三项需要 storage 或 compiler 配合，已登记为后续。
