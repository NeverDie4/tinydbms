## 1. 通知原则

- `include/tinydbms/` 是所有模块共享的正式接口；任何字段、variant、枚举、构造函数或错误语义变化都必须在修改前通知直接消费者。
- A 类决策已关闭，公共头文件尚未修改；收到 Compiler/Storage 确认前，不要求其他成员立刻适配代码。
- 通知应说明“类型形状、语义不变量、迁移窗口、测试要求”，不能只发一个头文件 diff。
- Compiler 内部实现不由 Core/CLI 成员指定；通知只陈述 Core 需要的输入/输出契约。
- 诊断/恢复线与 SQL v2 能力线分开发送和评审，避免把无 Storage 改动的首轮升级与磁盘格式升级混在一起。

### 2.5 Compiler 增量补充（2026-09-14）：PR #4 收敛口径

PR #4 的 `481d31b`（`refactor(diagnostics): unify compiler source range contract`）已经把
`CompileErrorKind` 换成 `CompileStage`、把单点位置换成半开 `SourceRange`，但形状与本组分支存在
三处差异。B13–B15 采用推荐值后，**形状收敛全部由本组承担**，Compiler 侧只需保证字段语义正确。

#### 2.5.1 B13–B15 结论（对 Compiler 的可见影响）

- [x] B13 `SourceRange` 形状：统一采用 PR #4 的 `SourceLocation{line, column, byte_offset}` +
  `SourceRange{begin, end}`。`byte_offset` 归属端点，0-based、按 UTF-8 字节；本组删除
  `SourceRange.begin_offset/end_offset`。**Compiler 侧无形状改动。**
- [x] B14 `core::Error`：保留 `std::optional<SourceRange> source`（脚本绝对范围）与
  `ErrorKind::kAnalysis`；不采用 PR #4 的 `std::optional<SourceLocation> location`（单点）与
  四值 `ErrorKind`。语句相对 → 脚本绝对的换算仍由 Core 完成，Compiler 不产出 `core::Error`。
- [x] B15 `StatementStatus` 与脚本策略：保留七态（`kExecuted`、`kCompileError`、
  `kExecutionError`、`kExecutionIndeterminate`、`kAnalysisError`、`kAnalysisOnly`、
  `kSkippedExecution`）与 `--error-policy stop|analyze`；不采用 PR #4 的四态版本。脚本聚合、
  执行门、恢复状态全部由 Core 负责，Compiler 不实现。

#### 2.5.2 Compiler 在下次更新需要确认或修复

- [ ] `byte_offset` 精确性（B13 的唯一硬要求）：`split_statements()` 与 `compile()` 的每个端点
  都必须给出所属文本内的字节偏移；EOF 插入点取文本长度；`\r\n` 的端点不得落在两个字节之间；
  Tab 按 1 字节推进。Core 依赖它做语句相对 → 脚本绝对换算与 fix-it 定位。
- [ ] 无状态假设：analyze 模式下 Core 会对**未执行**语句继续调用 `compile()`，且 `CatalogView`
  来自影子 Catalog（其中的 TableId 可能是尚未落盘的候选 ID）。`compile()` 的结果只能依赖
  `(sql, catalog)` 入参，不得缓存跨调用状态、不得读取磁盘、不得假设 TableId 已持久化或连续。
- [ ] 表达式上限不变量：PR #4 的 `kMaxExpressionComplexity = 256` 位于
  `src/compiler/parser.cpp`（私有），边界测试硬编码 253/254（NOT）与 64/65（AND）；Core 另有
  `kMaxExpressionDepth = 256`（`src/core/expression.hpp`，超限报 `expression depth exceeds core limit`）。
  请保证“任何编译成功的 Plan 都不会触发 Core 的深度兜底”，并考虑把常量放到双方可见处或写入
  契约，测试边界从常量推导而不是硬编码。
- [ ] 诊断质量（非阻断，与 B 决策无关）：以下输入的错误指向与措辞需要更明确，建议给出
  “不支持”诊断并指向真实 token（实测于 PR #4 `build/real`，2026-09-14）：
  - `SELECT id AS x FROM s;` → `ERROR compile 2:11 expected FROM after SELECT list`
  - `SELECT id FROM s AS x;` → `ERROR compile 2:18 expected ';' after SELECT statement`
  - `INSERT INTO t VALUES (1e400);` → `ERROR compile 2:24 expected ')' after VALUES row`
- [x] 已确认无需改动：`SplitStatement{sql, source}`、
  `CompileError{stage, source, message, suggestion, fix_it}`、
  `CompileStage{kLex, kSyntax, kSemantic}`、`QueryPlan.outputs`（结果列名/类型/nullable 的权威
  来源，取代旧的“从算子树反查唯一查询表”方案）、`ColumnRef{SlotId}` 与 SlotId 分配规则
  （见 PR #4 `docs/SQLv2扩展契约.md` §6）都与本组契约一致。
- [x] Plan 形状沿用 PR #4：Core 接受 `SlotId` / `QueryOutput` 以及 UPDATE、INNER JOIN、GROUP BY
  节点，并由本组负责执行器、CLI 输出与结果模型的适配；Compiler 不需要为合并改 Plan 形状。

### 4.2 B 类：进入 SQL v2 类型/Storage 实现前决定（全部关闭）

2026-09-12 确认：以下决策均采用推荐值，已写回[SQL v2 公共契约升级设计](../sql-v2/公共契约升级设计.md) §4。

9. **ColumnMeta 的兼容默认值**
   - 推荐：既有列和未显式声明的列默认 NOT NULL（`nullable=false`）。
   - 结论：默认 NOT NULL（`nullable=false`）。

10. **DOUBLE 有效域**
    - 推荐：只允许有限 IEEE-754 值，拒绝 NaN/Inf，避免比较、排序和持久化产生跨平台歧义。
    - 结论：仅有限值，NaN/Inf 在公共契约层非法。

11. **磁盘格式迁移策略**
    - 方案：新版本拒绝旧库、提供离线迁移工具，或实现读旧写新。
    - 推荐：由 Storage 组先给出成本评估；在决定前不得落地 NullValue/新 Type 到持久化格式。
    - 结论：采用该评估流程；具体策略待 Storage 成本评估后决定，评估前不得落地持久化格式变更。

12. **SQL v2 垂直功能顺序**
    - 推荐：诊断/恢复 → ORDER BY → 类型逐项 → NULL → UPDATE → INNER JOIN → GROUP BY/聚合。
    - 说明：ORDER BY 可先由 Core 内存执行；类型/NULL/UPDATE 需要更早协同 Storage。
    - 结论：接受推荐顺序。
