# tinydbms 初始化开发链路

## 目标

这一阶段不是实现完整数据库，而是把后续开发所依赖的模块边界和启动顺序固定下来。实现以当前仓库的三份契约文档为准，代码只加入最小可运行骨架。

## 启动链路

```text
main
  -> core::open_database
      -> storage::open_storage
      -> storage::list_tables
      -> core 保存内存 Catalog
  -> REPL 读取脚本
      -> core::execute_script
          -> compiler::split_statements
          -> compiler::compile
  -> core::close_database
      -> storage::close_storage
          -> 写入 storage.meta
```

`main` 只负责进程级参数、输入输出和退出码；Catalog 的逻辑所有权在 `core`；磁盘目录和物理元数据由 `storage` 管理；`compiler` 不保存数据库状态。

## 当前已经初始化的接口

- `src/include/tinydbms/types.h`：ID、`Value`、列/表元数据、错误和源位置。
- `src/include/tinydbms/compiler.h`：语句切分、表达式和计划数据结构的公共形状。
- `src/include/tinydbms/storage.h`：生命周期、Catalog、扫描、插入和删除的存储边界。
- `src/include/tinydbms/core.h`：数据库生命周期和脚本执行结果。

这些头文件先把跨模块消息固定下来，后续实现可以在不改变调用方向的前提下替换内部算法。

## 当前阶段的边界

`compiler::compile` 会明确返回“编译器尚未实现”的错误；storage 的扫描、插入和删除接口也会明确返回“尚未初始化”的错误。这样做是有意的：接口已存在，但没有用假执行结果掩盖缺失的 Parser、Executor、Page 和 Buffer Pool。

当前唯一落盘内容是 `storage.meta`，用于验证打开、关闭、重新打开和 Catalog 恢复的生命周期。它不是最终的表数据格式，也不是对页式存储的替代。

## 后续实现顺序

1. 在 `compiler::compile` 中实现 Lexer、Parser 和 `CatalogView` 语义检查。
2. 在 `core` 中执行 `CreateTablePlan`，分配 `TableId`，同步 Catalog 和 storage。
3. 在 storage 中实现 Table 文件、Page、Record 序列化和扫描游标。
4. 把 `InsertPlan` 接到 Record 写入路径。
5. 把 `SeqScanNode`、`FilterNode`、`ProjectNode` 接到 core 执行器，并在 core 中求值表达式。
6. 最后再加入 Buffer Pool、空闲空间、索引、事务和恢复机制。

每一步都应该先补充跨模块测试，再扩大下一层的实现范围；避免在 Parser、Executor 和物理存储同时不稳定时调试整条链路。
