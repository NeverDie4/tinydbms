# tinydbms 消息契约详细设计

本文是字段级消息契约的主体设计，包含初版生命周期与边界约束；公共头文件已按本文落地到 `include/tinydbms/`。后续字段调整需要重新确认，并同步修改文档与头文件。

崩溃恢复、显式 flush API 与逐操作 fsync 不在本文范围；正常 close_storage 时的统一落盘属于初版范围。
未来日志条目统一命名为 `LogEntry`，不与行记录 `Record` 混淆。
初版单进程：同一个 `Database` 实例的公开方法（`open`、`close`、`execute_script`）**可以被多个执行流并发调用**，由 core 按调用级互斥串行化——一次调用从进入到返回全程持锁，不承诺并行度，也不承诺读并行。对象移动与析构仍需调用方保证与调用互斥。storage 的公共 API 仍然要求串行调用，这条前提由 core 保证：storage 内部已有 page/file/buffer 级锁与 FileManager 状态机，但**公共 API 层与 cursor 注册表没有同步原语**；BufferPool 的顺序预取实验启用时会创建内部 worker 线程（默认关闭，见 [storage/pref1-report.md](storage/pref1-report.md)）。不实现事务与 MVCC；进程内并发的控制逻辑归 core 执行层，storage 只补充必要的原子性边界。

下文代码块表达逻辑形态与字段，按主题分组展示；不保证按出现顺序可直接编译，实现头文件时自行处理前置声明与定义顺序。

## 1. 基础类型与元数据

### ID

```cpp
using TableId = std::uint32_t;   // 由 core 的 Catalog 分配
using ColumnId = std::uint32_t;  // 等于建表列序 0..n-1，不单独分配
```

TableId 是完整 `uint32_t` 类型，但 Storage 保留 0 为 `tdb_sys_tables`、1 为
`tdb_sys_columns`；普通用户表不得使用这些 ID 或名称，空库的第一个用户 TableId 为 2。
TableId 按“已存在最大值 + 1”继续分配且不回绕；候选值在 64 位计数器上比较，
`UINT32_MAX` 本身是最后一个合法候选 ID。只有候选值超过 `UINT32_MAX`（即已分配 `UINT32_MAX`
之后）时，后续 CREATE TABLE 才由 core 返回 Error，不允许回绕到已有 ID。

### Type 与 Value

```cpp
inline constexpr std::uint32_t kMaxVarcharBytes = 1024;      // 单个 VARCHAR 值的 UTF-8 字节上限
inline constexpr std::uint32_t kMaxRowLogicalBytes = 4096;   // 单行逻辑载荷字节上限

enum class Type {
    kInt = 0,      // INT，32 位
    kBigInt = 2,   // BIGINT，64 位
    kDouble = 3,   // DOUBLE
    kBoolean = 4,  // BOOLEAN
    kVarchar = 1   // VARCHAR；保留 SQL v1 枚举值
};

struct Value {
    // std::monostate 是 SQL NULL 的唯一表示，不是独立 Type
    std::variant<std::monostate, std::int32_t, std::int64_t, double, bool, std::string> data;
};
```

Value 只表示可存储值，是共享类型。比较/逻辑运算的中间结果由 core 执行器内部处理，不进入存储。
类型集合、NULL、数值字面量与列 `nullable` 的完整语义以 [SQL v2 扩展契约](SQLv2扩展契约.md) 为准，
本节其余规则继续有效。
整数文字采用十进制 `[0-9]+` 形式，SQL v2 第一阶段不接受负数、十六进制或独立的前导 `+`；
`0..2147483647` 推断为 INT，`2147483648..9223372036854775807` 推断为 BIGINT，
超出 INT64 属于 `CompileStage::kLex`。DOUBLE 的严格形式为 `digits '.' digits`，
转换结果必须是 finite，否则返回 `CompileStage::kLex`；赋值给具体列类型时的范围检查属于 `CompileStage::kSemantic`。
VARCHAR 值必须是合法 UTF-8，长度按 UTF-8 字节数（即 `std::string::size()`）计算；compiler 在解析字符串字面量时校验。
单行逻辑载荷 = 各列逻辑长度之和：INT 计 4 字节、BIGINT 计 8、DOUBLE 计 8、BOOLEAN 计 1，
VARCHAR 计其 UTF-8 字节长度；该公式与 storage 的物理编码格式无关。
`kMaxVarcharBytes` 与 `kMaxRowLogicalBytes` 是共享上限，storage 做最终校验，超限返回 `kValueTooLarge`。

### 表与列元数据

```cpp
struct ColumnMeta {
    std::string name;
    Type type;
    // SQL v2 增加。C++ 聚合初始化的默认值 false 只用于兼容 SQL v1 的非空语义；
    // SQL 建表省略 NULL 约束时 semantic 必须显式填 true，二者不可互相推断
    // （见 SQLv2扩展契约 §4.1）。
    bool nullable = false;
};

struct TableMeta {
    TableId table_id;
    std::string table_name;
    std::vector<ColumnMeta> columns;  // 顺序即记录布局
};
```

ColumnId 等于列序，不需要额外存储；ALTER TABLE 不纳入，未来需要时再设计映射层。

## 2. CatalogView

```cpp
struct CatalogView {
    // 借用 core Catalog 中的表元数据数组，编译调用期间有效
    std::span<const TableMeta> tables;
};
```

compiler 通过线性查找表名或 TableId 获取结构。CatalogView 由 core 保证在调用期间有效，compiler 不持有、不修改。

## 3. SQL 初版语义边界

这部分定义跨模块必须一致的语义规则；具体文法与 parser 结构由 compiler 负责人决定。

### 支持的语句

- `CREATE TABLE`
- `INSERT INTO ... VALUES`
- `SELECT ... FROM ... [WHERE ...]`
- `DELETE FROM ... [WHERE ...]`
- SELECT 初版仅单表查询，无 JOIN、聚合、GROUP BY/ORDER BY、DISTINCT、子查询与列别名。
- 初版不支持 UPDATE、DROP、SHOW、ALTER，也不支持主键、唯一、默认值、外键、索引等列约束。
  其中 UPDATE 与 SELECT 的单表限制已由 SQL v2 补齐（见
  [SQL v2 扩展契约](SQLv2扩展契约.md) §9 与 §7）；DROP/SHOW/ALTER 与列约束仍不在范围内。
- 初版每条语句必须以 `;` 结束；没有“末条可省略分号”的例外。

### 标识符

- 关键字大小写不敏感。
- 表名、列名大小写不敏感，统一规范化为小写。
- 标识符为 ASCII：`[A-Za-z][A-Za-z0-9_]*`，长度 1..64；
  compiler 统一转为小写后，消息层与 Catalog 保存 `[a-z][a-z0-9_]*` 形式。
- SQL 关键字、重复表名/列名等语义检查由 compiler 负责；storage 在 create_table 消息层独立校验名称语法与唯一性，避免两侧标准不一致。

### 类型与表达式

- INT 与 VARCHAR 之间不做隐式转换。
- INT 支持 `= != < <= > >=`；VARCHAR 只支持 `=` 与 `!=`。
- VARCHAR 值必须为合法 UTF-8，长度按 UTF-8 字节数计；单个值超过 `kMaxVarcharBytes` 由 compiler 或 storage 报错。
- 支持 AND、OR、NOT；操作数是比较结果，比较结果是内部 BOOL，不进入 Value。
- 初版不包含算术表达式。
- INSERT 的 VALUES 只允许字面量；整数面向 INT，字符串面向 VARCHAR。
- INSERT 若提供列清单，必须是该表的全列，可改变顺序；省略列清单等于按建表列序全部插入。
  初版没有默认值与 NULL，不支持只插入部分列。

### compiler 实现一致性与资源边界

下列要求是公共契约在 compiler 内部实现时的强制约束，不因 lexer、parser、semantic、optimizer
或 planner 的内部拆分方式改变：

- SQL v2 第一阶段只接受非负字面量：`-1`、`-3.14` 不属于语法，不能靠词法/语义错误掩盖；
  `--` 仍然只表示单行注释。INT/INT64 边界必须可表示，超出 INT64 返回 `CompileStage::kLex`，
  赋值给具体列类型时的范围检查返回 `CompileStage::kSemantic`。
- compiler 不得生成超过 core 表达式递归上限 `256` 的合法 Plan。输入导致表达式超过该上限时，
  必须在生成 Plan 前返回编译错误；core 的 `kInternal` 深度检查只是防御性兜底，不能作为 compiler
  的资源限制替代。
- 标识符、字符串字面量和 SQL 文本的长度检查必须避免在拒绝前无界累积内存。字符串仍须遵守
  `kMaxVarcharBytes`；整段 SQL 文本上限已由公共常量 `kMaxSqlBytes` 固定为 1 MiB，`compile` 超限时
  返回 `CompileStage::kLex`。单条语句的独立上限暂不另设；整段超限由 `split_statements` 在复制语句前
  返回 `CompileStage::kLex`，不得抛出异常。
- compiler 的普通失败分别通过 `SplitStatementsResult`/`CompileResult` 返回，不能让异常越过公共 API；
  单条语句的 `CompileError.source`（含可选 `fix_it.range`）以该语句为基准，由 core 结合该语句的
  `SplitStatement.source` 换算为整段输入的绝对范围。

## 4. 可执行入口 ↔ core

### 产品行为

- 一个可执行文件，默认交互式 REPL，支持 stdin 批处理。
- stdin 连接到交互终端时进入 REPL；stdin 非交互时按整段批处理执行。
- REPL 以 EOF 退出（Unix 终端通常 Ctrl-D；Windows 控制台通常 Ctrl-Z 后回车），初版不提供 SQL 之外的元命令。
- 入口支持可选 `--data-dir <DIR>`，缺省使用当前目录下的 `tinydbms-data/`；该参数只用于打开数据库，不涉及 SQL 解析。
- 入口只负责读入文本、把文本交给 core、逐条展示 core 返回的结果与错误。
- 入口不拆句、不解析 SQL、不包含业务逻辑。
- `--data-dir` 最多出现一次且值不能为空；缺少值、重复出现、空值、未知参数或与 `--help/--version` 混用均为参数错误，退出码为 2。
- 批处理遇到 SQL/运行时错误时在 close 后返回 1；REPL 展示错误后继续下一行，EOF 后按累计错误标记和 close 结果返回 1；
  无错误时返回 0。

### REPL 的输入边界

初版交互模式按“行”提交：用户输入一行并回车后，该行作为一段文本交给 core。
一行内可以包含多条完整语句；跨行 SQL 暂不支持，列为后期优先升级项。
升级跨行时不能直接复用当前 split 接口；需要把协议扩展为返回完整语句、pending 文本与完整性状态
（例如 `SplitResult { statements, pending, need_more }`），由 core 持有缓冲，入口不自行解析 SQL。

### 消息与 Database API

```cpp
struct OpenDatabaseRequest {
    std::string data_dir;   // 已由入口补全的数据库目录，UTF-8 编码；不能为空
};

struct OpenDatabaseResult {
    std::optional<Error> error;
};

struct CloseDatabaseResult {
    std::optional<Error> error;
};

struct ExecuteScriptRequest {
    std::string text;   // REPL 一行，或 stdin 批处理的整段文本
    ScriptErrorPolicy error_policy{ScriptErrorPolicy::kStopOnFirstError};
    ExecutionMode mode{ExecutionMode::kExecute};
    // 单条语句在内存中物化的最大行数；必须 >= 1，默认值保持现行行为。
    // 只约束按行物化的节点（SeqScan、Join），不约束只收集 RecordId 的 DELETE/UPDATE。
    std::size_t max_query_rows{kMaxQueryRows};
    // 运行中取消令牌；默认从未请求取消，不传令牌时行为与现状一致。
    CancelToken cancel;
};

enum class ScriptErrorPolicy {
    kStopOnFirstError,   // 默认：首错即停
    kAnalyzeRemaining    // 首错后继续静态分析；后续语句仍不得执行
};

enum class ExecutionMode {
    kExecute,   // 默认：编译并执行
    kPlanOnly   // 只编译，把执行计划整理成文本返回；不调用 Storage、不修改 Catalog
};

enum class StatementStatus {
    kExecuted,
    kPlanOnly,
    kCompileError,
    kExecutionError,
    kExecutionIndeterminate,
    kAnalysisError,
    kAnalysisOnly,
    kSkippedExecution,
    kCancelled   // 运行中取消：当前语句在无副作用检查点结束，后续语句未开始
};

inline constexpr std::size_t kMaxStatementsPerScript = 4096;

// 单条语句在内存中物化的最大行数（SQL v2 的 JOIN/Sort/Aggregate 由 core 全量物化）
inline constexpr std::size_t kMaxQueryRows = 1 << 18;  // 262144

// 运行中取消令牌：只做置位 + 轮询，不注册回调，信号处理器可直接调用 request_cancel()
class CancelToken {
public:
    CancelToken();                                  // 初始未取消
    void request_cancel() const noexcept;           // 线程安全、幂等
    [[nodiscard]] bool cancel_requested() const noexcept;
private:
    std::shared_ptr<std::atomic<bool>> flag_;       // 拷贝共享同一标志
};
static_assert(std::atomic<bool>::is_always_lock_free);

// 逐语句结果只能经命名工厂构造，字段私有且只读。
class StatementResult {
public:
    static StatementResult executed(std::size_t statement_index, SourceRange source, ExecuteResult outcome);
    static StatementResult plan_only(std::size_t statement_index, SourceRange source, QueryResult plan);
    static StatementResult compile_error(std::size_t statement_index, SourceRange source, Error error);
    static StatementResult execution_error(std::size_t statement_index, SourceRange source, ExecuteResult outcome);
    static StatementResult execution_indeterminate(std::size_t statement_index, SourceRange source);
    static StatementResult analysis_error(std::size_t statement_index, SourceRange source, Error error);
    static StatementResult analysis_only(std::size_t statement_index, SourceRange source);
    static StatementResult skipped(std::size_t statement_index, SourceRange source);

    std::size_t statement_index() const noexcept;      // 分句后 0-based，连续
    const SourceRange& source() const noexcept;        // 脚本绝对范围
    StatementStatus status() const noexcept;
    const std::optional<ExecuteResult>& outcome() const noexcept;
};

struct ExecuteScriptResult {
    // 分句失败、语句数超限或致命中止时非空；普通语句错误进入 statements
    std::optional<Error> script_error;
    // 分句成功后覆盖全部已识别语句，按 statement_index 升序且连续
    std::vector<StatementResult> statements;
};

struct StorageStats {
    std::uint64_t fetch_count = 0;
    std::uint64_t hit_count = 0;
    std::uint64_t miss_count = 0;
    std::uint64_t eviction_count = 0;
    std::uint64_t dirty_flush_count = 0;
    double hit_rate() const noexcept;   // fetch_count == 0 时为 0
};

struct StorageStatsResult {
    std::optional<StorageStats> stats;  // 成功时必有值；失败时为空
    std::optional<Error> error;
};

class Database {
public:
    OpenDatabaseResult open(const OpenDatabaseRequest& request);
    CloseDatabaseResult close();
    ExecuteScriptResult execute_script(const ExecuteScriptRequest& request);
    StorageStatsResult storage_stats();
};
```

行为约定：

- Database 是 core 对入口与测试暴露的有状态对象，不是自由函数；
  每个实例持有自己的 Catalog 与生命周期状态，实例可移动、不可复制；
  移动后源对象为空；对 moved-from 对象调用 open/close/execute_script 均返回 `ErrorKind::kExecute`，析构必须安全。
- 入口创建 Database 对象并调用 open，正常退出前调用 close；execute_script 只在打开后调用。
- Database::open 内部负责 storage 的 open 与 Catalog 恢复；Database::close 负责 storage 的关闭与落盘收尾。
- `storage_stats()` 是只读观测：core 在同一把调用级互斥下转发 storage 的 demand buffer pool 快照，
  未打开（含 cleanup-pending）返回 `kExecute`，storage 错误映射为 `kStorage`，意外异常收敛为
  `kInternal`；任何失败都不携带部分快照，也不改变执行结果与退出码。
- 未打开数据库、重复打开或重复关闭等非法生命周期调用由 core 返回 Error。
- `close()` 发起关闭后，只有完整成功才释放 ownership。若 `close_storage` 返回错误或意外抛异常，
  对象离开 open 状态并进入 cleanup-pending，core 保留进程级占用标记；调用者只能重试 `close()`，
  清理成功或重试返回 `kInvalidRequest` 后才进入 unopened。
  析构时若仍打开或清理重试未完成，core 以 noexcept 做 best-effort 兜底 close_storage，
  该错误无法对外报告，析构不抛出异常。
- compiler/storage 的普通失败通过 Result 返回；若模块实现意外抛出异常，core 的公开方法不得让异常越过边界，
  普通调用转换为 `ErrorKind::kInternal`。若 storage 在执行、open 清理或 close 中意外抛异常，core 会
  best-effort 调用 `close_storage`、清空当前 Catalog 并使当前 Database 进入待清理状态；若清理调用本身
  抛异常则保留一次重试标记。该路径不能回滚已经发生的 CREATE/INSERT/UPDATE/DELETE 部分副作用，调用者必须先
  `close()`，之后再次 `open()` 才能重新恢复 Catalog。析构及移动赋值的 best-effort 清理捕获异常并保持 noexcept。
- 初版接受“Database 对象 + storage 单例”：storage API 仍是无句柄自由函数，
  同一进程同一时间只能打开一个数据库；第二个 Database::open 返回 Error，不影响已打开实例。
  storage 句柄化属于后续扩展，不在本轮范围。
- 空文本或只由完整注释组成的文本返回空 statements；未闭合字符串/块注释会作为语句返回并产生编译错误。
- `OpenDatabaseRequest.data_dir` 必须是非空 UTF-8 路径；CLI 未提供 `--data-dir` 时负责补为 `./tinydbms-data`。
- core 收到空字符串 `data_dir` 时返回 `ErrorKind::kExecute`，不调用 storage；storage 自身收到空路径时返回 `kInvalidRequest`。
- core 先调用 compiler 的 `split_statements`，再逐条“编译 → 执行”。
- `split_statements` 失败时直接转换为 core `ErrorKind::kCompile`；此时没有执行任何 Plan，不能调用
  `close_storage` 或使当前 Database 会话失效。
- CompileError.source（含可选 fix_it.range）相对单条语句；core 结合该语句的 SplitStatement.source.begin
  换算为整段输入的绝对范围后再对外返回。
- 某条语句以 Error 结束（独立 Error，或 CommandResult 携带 error）时进入失败状态；`kStopOnFirstError`
  下其后语句全部记 `kSkippedExecution`，`kAnalyzeRemaining` 下继续编译但不执行，两者都不再产生 Storage 副作用。
- INSERT/DELETE/UPDATE 在执行中发生 storage 错误且已有部分行成功时，core 返回携带 error 的
  CommandResult；无部分副作用可报告时，直接返回 Error。
- SELECT 扫描中发生 storage 错误时丢弃已收集的行，直接返回 Error，不再产生部分 QueryResult。
- DDL 成功执行后 core 立即更新 Catalog，再处理下一条语句。

### 脚本结果不变量

- `StatementResult` 的状态与 outcome 组合固定为：`kExecuted` 携带无错误的执行结果；
  `kPlanOnly` 携带单列 VARCHAR（列名固定为 `plan`）的 QueryResult；
  `kCompileError` 携带 `kCompile` Error；`kExecutionError` 携带 `kExecute`/`kStorage` Error
  或携带 error 的 `CommandResult`；`kAnalysisError` 携带 `kAnalysis` Error；
  `kExecutionIndeterminate`、`kAnalysisOnly`、`kSkippedExecution`、`kCancelled` 不携带 outcome。
- 取消不是错误：出现 `kCancelled` 时 `script_error` 必须为空，且 `statements` 仍覆盖分句后的
  全部语句（顺序与下标不变）。取消优先于 `ScriptErrorPolicy`：取消后不再编译剩余语句，
  也不产生 `kSkippedExecution` 或分析态。
- `kInternal` 只允许出现在 `script_error`，不允许出现在语句级 outcome。执行器返回 `kInternal` 时，
  未调用过 Storage 且未进入 cleanup-pending 的当前语句起全部记 `kSkippedExecution`；
  可能已产生副作用时当前语句记 `kExecutionIndeterminate`、其后记 `kSkippedExecution`。
- `script_error` 只承载三类：分句失败（`kCompile`）、语句数超过 `kMaxStatementsPerScript`
  （`kCompile` + `CompileStage::kLex`）、致命中止（`kInternal`，含 Compiler/Storage 违约抛异常、
  Core 内部不变量失败、影子 Catalog 建立/同步失败）。普通语句错误必须落入 statements。
- 分句失败或语句数超限时 statements 为空，Core 不编译、不执行、不调用 Storage；没有可信局部位置的
  脚本级错误统一使用空插入点 `{1,1,0}-{1,1,0}`。
- `kAnalyzeRemaining` 下影子 Catalog 只模拟 CREATE TABLE：编译成功且无需改变 Catalog、或成功应用时
  记 `kAnalysisOnly`；影子明确拒绝（TableId 耗尽、保留 ID、重复名称、非法元数据）记
  `kAnalysisError`。分析只改变脚本局部状态，运行时 Catalog、next_table_id 与 Storage 均不变，
  被拒绝的 CREATE 不消耗候选 TableId。

### 计划模式（ExecutionMode::kPlanOnly）

- 计划模式仍然分句、编译（含语义检查），但**不进入执行器**：core 不调用 Storage、不修改 Catalog、
  也不更新影子 Catalog，因此整段脚本零副作用。
- 每条编译成功的语句返回 `kPlanOnly`，结果是由 core 私有渲染器生成的单列 VARCHAR QueryResult
  （列名 `plan`，每行一段计划文本）。渲染只读 Catalog 解析人名，解析不到时退化为
  `table#N` / `slot#N` / `column#N`；渲染格式见 [Plan 整理输出设计](core-cli/Plan整理输出设计.md)。
- 分句失败、语句数超限、致命中止规则与执行模式完全一致；编译错误的位置与执行模式一致，
  `kCompileError` 之后是否继续取决于 `error_policy`。
- 计划模式下不产生 `kAnalysisOnly`/`kAnalysisError`：既然不进入执行器，就不需要影子 Catalog
  的"能否应用"判定，`kAnalyzeRemaining` 下首错之后编译成功的语句同样记 `kPlanOnly`
  （仍不执行），语义比"只分析"更准确。
- 零副作用的必然结果：同一脚本里 `CREATE TABLE t (...); SELECT * FROM t;` 的后一句会因表不存在
  而编译失败。这是期望行为，不做特殊处理。
- `kPlanOnly` 与 `kExecuted` 都携带结果，但语义不同：`kExecuted` 表示语句进入执行器并产生了结果，
  `kPlanOnly` 表示只生成了计划。展示层按查询结果渲染两者，调用方不得把 `kPlanOnly` 当作执行成功。
- Plan 违反 compiler 契约（空 root、空子节点、空操作数）时渲染器返回 `kInternal`，按致命中止处理，
  不把契约违反当作正常语句错误。

## 5. core ↔ compiler 消息

### SourceLocation 与 SourceRange

```cpp
struct SourceLocation {
    int line;                 // 从 1 开始
    int column;               // 从 1 开始，按 UTF-8 字节计数
    std::size_t byte_offset;  // 在所属源码文本内从 0 开始
};
```

诊断范围使用 `diagnostic.hpp` 中的 `SourceRange`（半开区间）：

```cpp
struct SourceRange {
    SourceLocation begin;  // 含 line/column/byte_offset 的起点
    SourceLocation end;    // 开区间终点，同样含 line/column/byte_offset
};
```

SourceRange 在契约中有三种语义：

- `SplitStatement.source`：语句在整段脚本中的绝对范围；
- `compile()` 返回的 `CompileError.source` 与 `fix_it.range`：相对单条 `statement.sql`；
- 用户可见 `Error.source`：core 换算后的脚本绝对范围；`split_statements()` 返回的错误范围
  本就相对整段输入，core 不平移。

坐标与端点规则：

- 范围统一为 `[begin, end)`，空插入点允许 `begin == end`；
- 行列 1-based、`byte_offset` 0-based；列与偏移按 UTF-8 字节计算，不声称是 Unicode 字符或终端显示宽度；
- 行按 `\n` 分割；`\r\n` 计一个换行且其中的 `\r` 不占列；独立的 `\r` 视为普通字节占一列；
  Tab 按一字节一列；
- `byte_offset` 取值域为 `0..text.size()`；非空区间必须满足 `begin.byte_offset < end.byte_offset`；
- 端点不得落在 `\r\n` 的两个字节之间，且行列与偏移必须指向同一段文本；
- core 在跨模块边界校验行列与偏移的一致性；违反契约按 `kInternal` script_error 处理，
  不使用其中任意一套坐标继续展示。

### 分句：split_statements

compiler 模块对外暴露无状态纯函数：

```cpp
struct SplitStatement {
    // 一条语句原文：从自身首字符到结尾分号，含前导空白/注释与语句之间的空白
    std::string sql;
    SourceRange source;    // sql 在整段输入中的绝对半开范围，与 sql 一一对应
};

struct SplitStatementsResult {
    std::variant<std::vector<SplitStatement>, CompileError> outcome;
};

// 输入整段 SQL 文本，成功时返回带绝对范围的语句列表；列表顺序即原文顺序
SplitStatementsResult split_statements(std::string_view text);
```

语义约定：

- 识别字符串（含 `''` 转义）、`--` 单行注释、`/* */` 块注释，以及作为语句分隔符的 `;`。
- 每条返回的 `sql` 保留从自身首字符到结尾分号的原文（含前导空白与注释），
  `source` 与 `sql` 一一对应；compile 只接收 `sql` 并报告相对范围，core 结合 `source` 换算绝对范围。
- 空输入返回空列表；仅由空白和“完整注释”（`--` 至行尾或 EOF、闭合的 `/* */`）组成的输入返回空列表。
- 只含空白与完整注释的分段不返回，连续分号之间的空语句同样被跳过。
- 未闭合字符串或块注释视为残缺语句，必须返回给 compile 报词法错误；
  此规则优先于上面的“纯注释丢弃”，不能把 `/* unfinished` 按纯注释吞掉。
- 最后一段没有分号的非空文本也作为一条语句返回；初版统一要求语句以分号结束，
  由 compile 报告缺少分号（语法错误）。
- 返回列表的顺序即原文顺序，`vector.size()` 就是语句数量，不需要额外计数字段。
- 分句失败只由两类原因触发：整段输入超过 `kMaxSqlBytes`，或分句结果违反契约
  （非法 `SourceRange`、`sql` 与 range 不一致等）。
- 输入超过 `kMaxSqlBytes` 时返回 `CompileStage::kLex`、空插入点 `{1,1,0}-{1,1,0}` 和
  `SQL text exceeds maximum length`，不得复制整段文本后再拒绝。
- `SplitStatementsResult` 中的 `CompileError.source` 相对整段输入；成功列表中的
  `SplitStatement.source` 是脚本绝对范围，两类坐标系不得混用。
  compiler 不得让分句失败的异常越过公共 API。
- 一旦分句失败，core 采用保守语义：statements 为空，整个脚本只返回一个 `script_error`，
  不逐句处理、不执行任何语句、不做启发式恢复；脚本级错误使用空插入点。

拆出的语句列表由 core 持有，compiler 调用完即忘，不保存任何状态。

### 相对范围换算

core 把 `compile()` 返回的语句相对 `SourceRange`（主诊断与 `fix_it.range` 共用同一套换算）
换算为脚本绝对范围：

```text
绝对 begin.byte_offset = statement.source.begin.byte_offset + relative.begin.byte_offset
绝对 end.byte_offset   = statement.source.begin.byte_offset + relative.end.byte_offset

绝对 begin.line = statement.source.begin.line + relative.begin.line - 1

绝对 begin.column =
    relative.begin.line == 1 时：statement.source.begin.column + relative.begin.column - 1
    relative.begin.line > 1 时：relative.begin.column
```

end 端点同理按 `relative.end` 换算。换算前必须校验 relative 范围落在该语句 `sql` 内、
行列与偏移一致，且 `sql.size()` 等于 `statement.source` 的字节跨度；违反契约按 `kInternal`
致命中止处理，不得把语句相对偏移当作脚本偏移展示。

### CompileRequest

```cpp
struct CompileRequest {
    std::string sql;      // 一条语句文本（来自 SplitStatement.sql）
    CatalogView catalog;  // 只读借用
};
```

### CompileError

```cpp
struct CompileError {
    CompileStage stage;                     // diagnostic.hpp：kLex / kSyntax / kSemantic
    SourceRange source;                     // compile() 相对单条 sql；split() 相对整段输入
    std::string message;
    std::optional<std::string> suggestion;  // 面向用户的可选建议
    std::optional<FixIt> fix_it;            // 机器可用的单处替换建议
};
```

`CompileErrorKind` 已删除，统一改用 `CompileStage`；不保留别名或双接口。每条语句本阶段最多
返回一个主诊断和一个可选 fix-it；低置信度建议可以不填。Compiler 公共函数不得抛异常。

### CompileResult

```

```

## 6. LogicalPlan

compiler 负责编译期：解析、类型检查、生成 Plan 与 Expr。
core 负责运行期：对 storage 返回的记录求值比较、AND/OR/NOT。
storage 不参与表达式。

Plan/Expr 的 C++ 形态不允许默认构造空树、不允许复制：
Binary/Unary 必须带非空子树构造；FilterNode/ProjectNode 的 child 与 QueryPlan 的 root 非空是调用不变量；
CompileResult 只能由 Plan 或 CompileError 构造，不存在“成功的空结果”。

这里的“调用不变量”是 Plan 生产者的前置条件，不要求公共构造函数返回错误；compiler 生成的 Plan 必须满足它。
core 的执行入口在解引用前校验这些指针，发现空节点返回 `ErrorKind::kInternal`，不得调用 storage。

### 顶层 Plan

```cpp
struct Plan {
    std::variant<
        CreateTablePlan,
        InsertPlan,
        DeletePlan,
        QueryPlan
    > kind;
};
```

### CreateTablePlan

```cpp
struct CreateTablePlan {
    std::string table_name;          // 尚无 ID，执行时由 core 分配
    std::vector<ColumnMeta> columns;
};
```

### InsertPlan

```cpp
struct InsertPlan {
    TableId table_id;
    std::vector<ColumnId> columns;   // 空 = 全列按建表列序；非空 = 全列的重排，缺列由 compiler 判为语义错误
    std::vector<std::vector<Value>> rows;  // VALUES 多行
};
```

rows 中每一行的值顺序与 columns 一致；columns 为空时与建表列序一致。
core 执行时先把列清单重排展开为建表列序的全行，再交给 storage。

合法 `InsertPlan` 的 `rows` 至少包含一行；空 `rows` 不是可执行的空插入，而是 compiler/Plan
契约违反，core 返回 `ErrorKind::kInternal` 且不得调用 storage。`columns` 非空时必须恰好
包含该表每个 `ColumnId` 一次；重复、缺失、越界或任一行长度不等于 `columns.size()` 均属于
无效 Plan。

### DeletePlan

```cpp
struct DeletePlan {
    TableId table_id;
    std::optional<Expr> predicate;   // nullopt = 无 WHERE，删除全部
};
```

### QueryPlan 与算子树

```cpp
struct QueryPlan {
    std::unique_ptr<PlanNode> root;
};

struct SeqScanNode {
    TableId table_id;
};

struct FilterNode {
    Expr predicate;
    std::unique_ptr<PlanNode> child;
};

struct ProjectNode {
    std::vector<ColumnId> outputs;   // SELECT 列表，* 已由 compiler 展开
    std::unique_ptr<PlanNode> child;
};

struct PlanNode {
    std::variant<SeqScanNode, FilterNode, ProjectNode> kind;
};
```

初版合法 QueryPlan 必须且只能包含一个 SeqScanNode；FilterNode/ProjectNode 只能沿单子树连接到它。
core 遍历算子树取得该 SeqScanNode 的 TableId，再根据输出 ColumnId 查 Catalog 生成结果列名；
零个或多个 SeqScanNode、越界 ColumnId 或跨表引用均属于无效 Plan，返回 `ErrorKind::kInternal`。

为保证 Filter 始终作用于完整物理行，compiler 生成的合法算子树从 root 到叶子只能是以下四种：

```text
SeqScan
Filter -> SeqScan
Project -> SeqScan
Project -> Filter -> SeqScan
```

因此 `FilterNode`、`ProjectNode` 各最多一个，Project 必须位于 Filter 外层；root 和所有 child
必须非空。没有 ProjectNode 时表示全列投影。存在 ProjectNode 时 `outputs` 至少一个元素，
ColumnId 可以重复但顺序必须保留；空 outputs、其他拓扑或额外节点均为无效 Plan。

### Expr

```cpp
struct Expr {
    std::variant<
        ColumnRef,
        Literal,
        Binary,
        Unary
    > kind;
};

struct ColumnRef {
    ColumnId column_id;
};

struct Literal {
    Value value;
};

struct Binary {
    std::variant<CmpOp, LogicOp> op;
    std::unique_ptr<Expr> lhs;
    std::unique_ptr<Expr> rhs;
};

struct Unary {
    UnaryOp op;   // 初版仅 NOT
    std::unique_ptr<Expr> operand;
};

enum class CmpOp {
    kEq, kNe, kLt, kLe, kGt, kGe
};

enum class LogicOp {
    kAnd, kOr
};

enum class UnaryOp {
    kNot
};
```

初版不包含算术表达式。Expr 的 C++ 落地需要递归包装类型，本文只规定逻辑形态。

compiler 必须在生成 Plan 时完成表达式的静态类型检查：ColumnRef 的类型来自 Catalog，Literal
的类型来自 Value；比较两侧必须是同类型 Value，INT 支持全部比较运算，VARCHAR 只支持 `=`/`!=`；
AND/OR 两侧及 NOT 操作数必须是 BOOL，Filter/Delete 的顶层表达式必须是 BOOL。core 在调用
storage 前再次执行同样的结构和静态类型预校验，防止非法 Plan 在空表上被掩盖。

compiler 生成的表达式树必须满足上述深度边界；core 的递归校验和求值仍保留 `256` 层防御性上限。
Plan 树遍历使用同一数值作为 core 侧防御性上限：校验与执行在进入第 256 层节点前返回
`ErrorKind::kInternal`，不递归溢出、不产生 Storage 副作用，也不能替代 compiler 的复杂度预算。

初版表达式无 NULL、函数或副作用。core 对 AND/OR 先求值两侧再应用逻辑运算，不采用短路；
这是为了让 Result/行数据异常的处理稳定，不改变合法表达式的结果。

## 7. core 内部行与用户输出

命名约定：

- `Record` 只用于 storage 边界：RecordId + 全行列值。
- core 执行器内部处理的行叫 `Row`。
- `RecordId` 由 storage 分配，对 core 不透明。

```cpp
using Row = std::vector<Value>;   // core 执行器内部与结果中的行

struct ColumnHeader {
    std::string name;
    Type type;
};

struct QueryResult {
    std::vector<ColumnHeader> columns;
    std::vector<Row> rows;
};

enum class ErrorKind {
    kCompile,
    kExecute,
    kStorage,
    kAnalysis,
    kInternal
};

struct Error {
    ErrorKind kind;
    std::optional<CompileStage> compile_stage;  // 仅 kCompile 携带
    std::optional<SourceRange> source;          // 脚本绝对范围；无法定位时为空
    std::string message;
    std::optional<std::string> suggestion;      // 仅 kCompile 可能携带
    std::optional<FixIt> fix_it;                // 仅 kCompile 可能携带
};

struct CommandResult {
    std::uint64_t affected_rows;   // CREATE 成功时为 0
    // 仅 INSERT/DELETE/UPDATE 部分行成功后 storage 出错时携带；
    // 此时 affected_rows 是错误前已成功执行的行数，core 停止后续语句
    std::optional<Error> error;
};

struct ExecuteResult {
    std::variant<QueryResult, CommandResult, Error> outcome;
};
```

成功时 `affected_rows` 的含义固定为：CREATE 为 0，INSERT 为实际请求行数，DELETE 为实际
删除行数，UPDATE 为实际替换行数。INSERT/DELETE/UPDATE 携带 error 时，`affected_rows`
是 storage 返回的可靠部分成功数量；没有可靠部分成功数量时返回独立 Error，不构造 CommandResult。

core API 在 `Error` 中携带 `CompileStage`，使词法/语法/语义类别保持机器可读；仍不携带
`StorageErrorKind` 字段。转换时必须保留源错误的可读消息，但调用方不得依赖消息文本判断细分类别；
若未来需要稳定区分 Storage 细分类别，必须单独扩展公共契约。

字段不变量：

| `kind` | `compile_stage` | `source` | `suggestion` / `fix_it` |
|---|---|---|---|
| `kCompile` | 必有 | 必有 | 可选 |
| `kExecute` | 空 | 通常为空 | 空 |
| `kAnalysis` | 空 | 必有 | 空 |
| `kStorage` | 空 | 空 | 空 |
| `kInternal` | 空 | 致命中止时指向发生中止的位置；无法定位时为 `{1,1,0}-{1,1,0}` | 空 |

## 8. core ↔ storage 消息

### 生命周期

```cpp
struct OpenStorageRequest {
    std::string data_dir;   // 非空数据库目录，UTF-8 编码；由 core 传入
};

struct OpenStorageResult {
    std::optional<StorageError> error;
};

struct CloseStorageRequest {};

struct CloseStorageResult {
    std::optional<StorageError> error;
};
```

生命周期语义：

- core 的 Database::open 调用 open_storage，成功后才能调用其他 storage API；失败时 core 中止启动。
- core 的 Database::close 调用 close_storage，正常退出前必须执行。
- 成功返回表示操作已更新 storage 内部状态；正常 close_storage 后重启可见。
- data_dir 不存在时由 open_storage 创建目录；创建失败返回 `kIoError`。
- data_dir 存在但不是目录或不可访问时返回 `kIoError`。
- `data_dir` 为空字符串返回 `kInvalidRequest`；已存在但内容为空的目录视为新建数据库；
  目录非空但缺少或无法识别 storage 元数据时返回 `kCorrupt`，不得覆盖已有文件。
- open_storage 成功后，若后续 list_tables/Catalog 恢复失败，core 先调用 close_storage 清理，再中止启动；清理错误不覆盖主错误。
- data_dir 统一使用 UTF-8 字符串；Windows 入口负责把宽字符路径参数转换为 UTF-8，storage 内部再转换回原生路径。
- close_storage 只有完成统一落盘和资源释放后才进入 Closed。BufferPool、文件或 metadata
  收尾失败时返回错误并保留可重试状态：buffer pool 关闭前的失败可回到 Open，文件/metadata
  收尾失败保持 Closing；无论哪一类错误，core 都必须保留 owner 与清理重试状态，
  在重试成功前拒绝其他 Database open。
- close_storage 重试成功后，所有 cursor 失效并允许再次 open_storage；若调用本身抛出异常，
  core 不能推断 storage 是否已经结束，必须保留 cleanup-pending 和进程级占用标记，直到后续重试。
- storage 生命周期非法调用统一返回 `kInvalidRequest` 且不产生业务副作用：重复 open_storage、未打开时的
  list_tables/create_table/open_table/scan_next/close_cursor/insert/update_rows/delete_records/storage_stats
  均属于此类；重复 open_storage 不影响当前已打开实例。已成功 Closed 后的重复 close_storage
  是成功 no-op；Closing 中的重复 close_storage 是清理重试。
- `OpenStorageResult`/其他 storage Result 通过返回值表达普通失败；storage 实现不得让异常越过公共 API，
  发生意外异常时应转换为对应错误结果。core 的异常 catch 只能作为边界兜底，不能推断异常发生
  前后的副作用数量。
- 初版不支持两个进程同时打开同一 data_dir；storage 不提供文件锁或跨进程互斥，跨进程并发属于后续扩展。
- 初版不承诺逐次 fsync、进程崩溃或断电后的持久性；这些属于范围外的显式 flush 与崩溃恢复议题。

### 统计快照

```cpp
struct StorageStatsRequest {};

struct StorageStats {
    std::uint64_t fetch_count = 0;
    std::uint64_t hit_count = 0;
    std::uint64_t miss_count = 0;
    std::uint64_t eviction_count = 0;
    std::uint64_t dirty_flush_count = 0;
    double hit_rate() const noexcept;   // fetch_count == 0 时为 0
};

struct StorageStatsResult {
    std::optional<StorageStats> stats;   // 成功时必有值；失败时为空
    std::optional<StorageError> error;
};
```

- 只读快照：不改变任何存储状态，不抛异常；成功时 `stats` 必有值，失败时 `stats` 为空且 `error` 非空。
- 计数是 demand 口径的 buffer pool 访问，从最近一次成功 `open_storage` 起算，
  `close_storage` 成功收尾后随状态归零；预取 worker 的内部读写不计入，也不承诺未来计入。
- `fetch_count == 0` 时 `hit_rate()` 返回 0；否则等于 `hit_count / fetch_count`。
  core 与入口据此计算展示用的缺失率，不额外定义新口径。
- 未打开（含 Closing）返回 `kInvalidRequest`，不返回空快照；调用方必须在 `close_storage`
  之前取数，否则得到的是错误而不是会话末尾的计数。

### Result 不变量

- error 为空表示成功；error 非空表示操作在错误处停止。
- ListTablesResult：error 为空时 tables 是 storage 当前已持久化的全部表；error 非空时 tables 无效，core 应中止启动恢复。
  core 恢复 Catalog 时还必须检查每张表至少有一列，且每个列类型属于公共契约支持的
  `kInt`/`kBigInt`/`kDouble`/`kBoolean`/`kVarchar` 五种；违反该结构约束按 `ErrorKind::kInternal`
  处理，关闭 storage 后拒绝 open。
- CreateTableResult：错误时不得留下可被 list_tables 看到的半成品表；core 不更新 Catalog。
- OpenTableResult：error 为空时 cursor 必有值；错误时 cursor 为空。
- ScanNextResult：record 有值 = 成功返回一行；record 空且 error 空 = 扫描结束；error 非空时 record 无效。
- InsertResult：成功时 `rids.size() == rows.size()`；错误时 `rids` 只包含错误前已成功插入的行。
- DeleteResult：成功时 `deleted_count == rids.size()`；错误时 `deleted_count` 是错误前已成功删除的数量。
- DeleteRequest 的 `rids` 允许为空：在 table_id 有效且 storage 已打开时视为成功的零行删除；
  不存在的 table_id 仍返回 `kTableNotFound`。
- 游标无论正常结束还是出错中断，core 都应调用 close_cursor。
- scan_next 返回“record 为空且 error 为空”表示自然结束，但游标在 close_cursor 前仍有效；
  自然结束后再次 scan_next 仍返回自然结束，close_cursor 成功后再次使用该 cursor 返回 `kCursorInvalid`。
- close_cursor 成功后再次 close_cursor 返回 `kCursorInvalid`。
- close_cursor 一旦被调用即结束该 cursor 的使用权；即使返回 storage error，也必须使该 cursor
  不可再次使用。storage 正常实现不得从 close_cursor 抛异常。
- storage 对请求做基本校验：操作不存在的表返回 `kTableNotFound`；非法或已关闭的 cursor 返回 `kCursorInvalid`；
  INSERT 的行列数、列类型或逻辑载荷上限不符返回 `kInvalidRequest`/`kValueTooLarge`；
  `InsertRequest.rows` 为空返回 `kInvalidRequest`；有效表上的空 `DeleteRequest.rids` 仍是成功的零行删除；
  create_table 的 table_name/列名不符合 `[a-z][a-z0-9_]*` 且长度不在 1..64、列清单为空或列名重复返回 `kInvalidRequest`；
  create_table 使用与已有表重复的 TableId 或 table_name，或使用 system reserved ID/name，返回 `kInvalidRequest`；
  public insert/update_rows/delete_records 对 system table 返回 `kInvalidRequest`；
  delete_records 收到不属于该表或已失效的 RecordId 返回 `kInvalidRequest`。
- 错误优先级：同一语句先出现的错误优先；
  扫描已出错时 close_cursor 的后续错误不覆盖；
  扫描正常结束但 close_cursor 失败时，SELECT 丢弃已收集行并返回该错误，DELETE 中止且不执行删除。

上述 Result 组合是 storage 的正常返回不变量。若 core 收到违反不变量的组合：

- OpenTableResult 同时有 error 和 cursor，core 返回 `ErrorKind::kInternal`，但把 cursor 视为已取得并
  best-effort close 一次；
- OpenTableResult 同时无 error 和 cursor，core 返回 `kInternal`，不调用 close；
- ScanNextResult 同时有 error 和 record，core 返回 `kInternal`，不使用 record，并关闭已取得的 cursor；
- ScanNextResult 返回的 Record 行宽或列类型与 Catalog 不符时，core 视为 storage 违约：
  返回 `kInternal`，结束当前 Database 会话并通过 close_storage 清理，因为该表后续行的可信度
  无法确认。SELECT/DELETE/UPDATE 三条扫描路径行为一致；
- InsertResult/DeleteResult/UpdateResult 的数量字段违反成功结果不变量时，core 返回 `kInternal`，
  结束当前 Database 会话并通过 close_storage 清理，因为实际写入/删除/更新数量已不可确定；
- core 对每个已取得的 cursor 至多尝试一次 close；close 调用前即标记为已尝试，即使 close 抛异常也不重试。
- 若 `open_table` 已经产生 cursor 但在返回 `OpenTableResult` 前抛异常，core 无法取得 cursor ID；
  此时 core 只能 best-effort 调用 `close_storage`，storage 必须按生命周期规则回收该 cursor。
  若 INSERT/DELETE/UPDATE/CREATE 在产生部分副作用后抛异常，core 同样不能回滚，只能结束当前
  storage 生命周期并返回 `ErrorKind::kInternal`，由下一次 open 重新读取实际持久化状态。

## 9. 典型时序

### 启动

```text
入口解析 --data-dir → Database db; db.open(data_dir)
core → open_storage(data_dir) → storage
open_storage 失败 → 中止启动
core → list_tables → storage
list_tables 失败 → core → close_storage 清理 → 中止启动
storage → 返回 system table 与用户表的所有 TableMeta
core → 重建内存 Catalog（空库含 system TableId 0/1，首个用户 TableId 为 2；非空库取已存在最大值之后继续分配；
        候选值在 64 位计数器上比较，UINT32_MAX 本身仍可分配，超过 UINT32_MAX 后建表返回 Error）
```

### 关闭

```text
入口正常退出 → db.close()
core → close_storage → storage
storage 完成统一落盘与资源释放
```

### 多语句批处理

```text
入口解析 --error-policy（默认 stop）→ 把整段文本交给 core
core → split_statements(文本) → SplitStatement 列表（sql + source）或整段输入 CompileError
分句失败 → statements 为空 + script_error{kCompile}，不逐句处理
语句数超过 kMaxStatementsPerScript → statements 为空 + script_error{kCompile/kLex}，不调用 Storage
core 循环：
  用当前 CatalogView 编译当前语句的 sql
  成功且执行门打开 → 执行并放入 kExecuted；INSERT/DELETE/UPDATE 部分成功放入 kExecutionError
  成功但执行门已关闭（analyze）→ 影子 Catalog 记 kAnalysisOnly 或 kAnalysisError
  编译失败 → 放入 kCompileError 并关闭执行门
  执行失败 → 放入 kExecutionError 并关闭执行门
  致命中止（Compiler/Storage 违约、kInternal 等）→ 当前语句 kExecutionIndeterminate 或
      kSkippedExecution，其余记 kSkippedExecution，填 script_error{kInternal} 后结束脚本
  DDL 成功后更新 Catalog（真实执行）或影子 Catalog（分析态）
  处理下一条语句
stop 策略在首错后把剩余语句全部记 kSkippedExecution；analyze 策略继续编译但不执行
```

### CREATE TABLE

```text
core 分配 table_id
core → create_table(table_id, 表名, 列定义) → storage
storage 失败 → 不更新 Catalog，也不递增 next_table_id；候选 ID 可复用
storage 成功 → core 更新 Catalog，并将 next_table_id 更新为 table_id + 1
```

### SELECT

```text
core → open_table(table_id) → cursor
循环：
  core → scan_next(cursor)
  storage → Record（全行）
  core 把 Record 转成内部 Row，执行 Filter / Project
core → close_cursor(cursor)
close_cursor 成功 → core 组装 QueryResult
close_cursor 失败 → 丢弃已收集行，返回该 Error
```

### DELETE

```text
open_table + 循环 scan_next
core 对每条 Row 求值 WHERE，收集命中的 RecordId
close_cursor
close_cursor 成功后 → core → delete_records(table_id, rids) → storage
close_cursor 失败 → 中止，不执行删除
```

### UPDATE

```text
open_table + 循环 scan_next
core 对每条 Row 求值 WHERE，命中则用 SET 字面量生成 replacement 全行
（逐行校验行宽与列类型，违约按 storage 违约结束会话）
close_cursor
close_cursor 成功后 → core → update_rows(table_id, [{rid, replacement}]) → storage
close_cursor 失败 → 中止，不执行更新
update_rows 部分成功后失败 → CommandResult{updated_count, error}
```

UPDATE 不拼接 delete + insert，完整行替换由 storage 的 `update_rows` 负责；
RecordId 在替换后是否变化不属于 SQL 契约。

## 10. 已确认决策汇总

> 说明：本表记录各阶段确认过的决策，早期行以 SQL 初版为基线。SQL v2 已在以下方面取代初版结论：
> NULL（`std::monostate`）、确定性数值扩宽、`UPDATE` 与 `ORDER BY`/`INNER JOIN`/`GROUP BY` 语法、
> `QueryPlan` 的 Join/Sort/Aggregate 节点与 query-local `SlotId` 绑定，以及按类型计价的单行逻辑载荷
> （INT 4、BIGINT 8、DOUBLE 8、BOOLEAN 1、VARCHAR 按字节）。这些内容的权威描述是
> [SQL v2 扩展契约](SQLv2扩展契约.md) 与 `include/tinydbms/*.hpp`；表中相应行的“初版”限定词仍然只描述 v1 基线。

| 决策 | 结论 |
|---|---|
| NULL | 后期可选，初版不支持 |
| 标识符 | ASCII `[A-Za-z][A-Za-z0-9_]*`，规范化后 `[a-z][a-z0-9_]*`，长度 1..64 |
| TableId | uint32 类型；0/1 分别保留给 `tdb_sys_tables` / `tdb_sys_columns`，用户表从 2 开始；按最大值 +1 分配且不回绕，ID 耗尽后建表返回 Error |
| CREATE 失败与 TableId | storage 创建失败时不更新 Catalog、不消耗候选 TableId；成功后才递增 |
| TableId/ColumnId 区分 | 初版同为 uint32_t 别名，接受“靠命名与测试防混用”；不引入强类型包装 |
| 类型转换 | INT/VARCHAR 无隐式转换；VARCHAR 仅 `=`/`!=` |
| VARCHAR | 值必须为合法 UTF-8；字节数 ≤ 1024 |
| 大小上限 | 单行逻辑载荷 ≤ 4096（INT 计 4 + VARCHAR 按 UTF-8 字节数）；与物理编码无关；超限返回 kValueTooLarge |
| 分号规则 | 初版所有语句必须以 `;` 结束，无末条省略例外 |
| SQL 范围 | 初版仅 CREATE/INSERT/SELECT/DELETE；无 UPDATE/DROP/SHOW/ALTER 与列约束。UPDATE 与 ORDER BY/INNER JOIN/GROUP BY 已由 SQL v2 补齐；DROP/SHOW/ALTER 与列约束仍不在范围内 |
| 分句 | compiler 提供无状态 split_statements，成功返回带绝对 SourceRange 的 SplitStatement 列表；分句失败只由 kMaxSqlBytes 或契约违反触发，保守停止并用空插入点 |
| 分句持有方 | core 持有编译器返回的语句列表，逐条“编译 → 执行”；compiler 调用完即忘，不保存状态 |
| 诊断类型 | diagnostic.hpp 定义 SourceRange/FixIt/CompileStage；半开区间、行列 1-based、byte_offset 0-based、UTF-8 字节坐标 |
| CompileError | stage + 相对单条语句的 SourceRange + message + 可选 suggestion/fix-it；CompileErrorKind 已删除 |
| 错误位置 | CompileError.source / fix_it.range 相对单条语句；core 用 SplitStatement.source 换算为脚本绝对范围 |
| 脚本策略 | ScriptErrorPolicy：默认 kStopOnFirstError；kAnalyzeRemaining 只继续静态分析，后续语句不执行 |
| 语句状态 | 九态 StatementStatus（U5 起含 kCancelled）；kInternal 只允许出现在 script_error，不允许语句级 outcome |
| 运行中取消 | `ExecuteScriptRequest::cancel`（CancelToken：线程安全置位 + 轮询，可在信号处理器中调用）。检查点在语句开始前、扫描行循环、Join 内层循环与 Sort/Aggregate 行循环；INSERT 首版不设检查点。取消后当前语句与剩余语句记 `kCancelled`（不携带 outcome），`script_error` 保持为空，不产生 Storage 副作用，cursor 正常关闭；不请求取消时行为与现状一致 |
| 计划模式 | ExecuteScriptRequest.mode = kPlanOnly：只编译不执行，语句记 kPlanOnly 并携带单列 `plan` 文本结果；零副作用，编译错误与策略规则与执行模式一致 |
| script_error | 只承载分句失败、语句数超限与致命中止；statements 覆盖全部已识别语句且 index 连续 |
| 语句数上限 | kMaxStatementsPerScript = 4096，超限 fail-closed，statements 为空且无 Storage 调用 |
| 物化行数上限 | 单条语句在 core 内存中物化的行数 ≤ 请求的 `max_query_rows`（默认 `kMaxQueryRows` = 262144，按扫描与连接节点的行数计），超限返回语句级 `kExecute` 错误，不失效会话、不产生 script_error |
| 上限配置 | `ExecuteScriptRequest::max_query_rows` 为请求级配置，缺省即默认值；`0` 是调用方违约：core 在分句前拒绝整段脚本（script_error + `kExecute`，消息 `max_query_rows must be at least 1`），不调用 compiler/storage。上限按物化节点计，`WHERE` 过滤前的扫描行数同样计入；DELETE/UPDATE 与计划模式不受其约束 |
| 影子 Catalog | analyze 脚本局部副本，仅模拟 CREATE TABLE；不调用 Storage、不消耗运行时 next_table_id，被拒绝的候选不消耗 |
| 行列计数 | 行按 `\n`；CRLF 算一个换行；列按 UTF-8 字节计且从 1 开始，byte_offset 从 0 开始 |
| 批处理遇错 | 立即停止，返回已执行结果与该错误 |
| core API 形态 | core 暴露有状态 `Database` 对象（open/close/execute_script）；不是自由函数 |
| Database 生命周期 | 可移动不可复制；close_storage 返回错误或抛异常后进入 cleanup-pending 并保留占用标记；重试成功或返回 kInvalidRequest 后才释放 ownership；析构时 best-effort 兜底关闭且 noexcept |
| moved-from | 公开方法均返回 `ErrorKind::kExecute`；析构必须安全 |
| REPL 输入 | 初版按行提交，一行内可多条语句；跨行 SQL 为后期优先升级项 |
| storage 生命周期 | 无句柄单例；非法生命周期调用返回 `kInvalidRequest`；close_storage 失败可保留 Open/Closing 并必须重试；成功后才释放 cursor 和打开状态；空目录可新建，空字符串路径非法 |
| 跨进程并发 | 初版不支持两个进程同时打开同一 data_dir；无文件锁，后续扩展 |
| 持久化承诺 | 正常 close_storage 统一落盘后重启可见；排除显式 flush API、逐操作 fsync 与崩溃恢复 |
| ColumnId | 等于建表列序 0..n-1，不单独分配 |
| CatalogView | 借用式 `span<const TableMeta>` |
| 表达式 | compiler 编译期生成 Plan/Expr；core 运行期求值；storage 不参与 |
| 扫描 | 游标式全行返回，core 负责过滤与投影 |
| 错误优先级 | 扫描错误优先；扫描正常但 close_cursor 失败时 SELECT/DELETE 以该错误失败 |
| storage 校验 | 表/游标/行列数/类型/逻辑载荷/名称语法与 ID、表名唯一性由 storage 校验并分类报错 |
| 批量消息 | INSERT 一次多行；DELETE 一次一串 RecordId；失败即停并返回部分结果 |
| InsertPlan 空批次 | `rows` 不能为空；core 返回 `kInternal`，不调用 storage |
| QueryPlan 算子树 | 只允许 SeqScan、Filter->SeqScan、Project->SeqScan、Project->Filter->SeqScan |
| Query 投影 | 无 Project 表示全列；有 Project 时 outputs 非空，允许重复且保留顺序 |
| 表达式预校验 | core 在调用 storage 前校验结构、ColumnId 和静态类型；Filter/Delete 顶层必须 BOOL |
| 逻辑求值 | AND/OR 先求值两侧再运算；初版不采用短路，无 NULL/副作用 |
| 非法 storage Result | 违反字段组合返回 `kInternal`；已返回 cursor 时仍至多尝试 close 一次 |
| 部分失败表示 | INSERT/DELETE/UPDATE 部分成功时返回携带 error 的 CommandResult；无部分副作用时返回 Error |
| RecordId | storage 分配，对 core 不透明 |
